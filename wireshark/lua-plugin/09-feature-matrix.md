# 第六部分 · 横向对比：三个案例的 Feature Matrix

> 说明：这里按用户规则用 bullet list 而不是 markdown 表格来表达"矩阵"——因为要呈现的不只是"有/无"，还要说明"为什么有/为什么没有"，这类解释性内容用表格反而会被压缩得过于简略。

## 6.8 逐项对照

- **Proto**
  - 案例1（dns_dissector）：1 个 Proto（`mydns`）
  - 案例2（PostDissector 群）：每个示例各 1 个"伪协议" Proto，仅作挂载身份用
  - 案例3（RLS）：3 个 Proto（`RLS`/`RLS-3.1`/`RLS-3.2`），因为协议本身按版本分裂，天然对应多个身份

- **ProtoField**
  - 案例1：丰富，含普通字段、位域字段（bitmask）、值映射表（rcode/rrtype/class）
  - 案例2：01/04 有少量字段，02/03 几乎不用（02 只改列文本，03 只做只读展示）
  - 案例3：丰富，且按版本各自维护一套字段集合（3.1 比 3.2 多了 Mcc/Mnc/Nci 等蜂窝网络专属字段）

- **Preferences**
  - 案例1：有（debug 级别、端口、是否启用启发式），且实现了 `prefs_changed()` 同步 DissectorTable
  - 案例2：无——PostDissector 通常不需要用户配置，行为是固定的
  - 案例3：有（UDP 端口），但没有实现 `prefs_changed()`——**这是一个可以指出的改进空间**：如果用户改了端口 Preference，`rls.lua` 目前的 `init()` 只在 capture 打开/关闭时重新注册，不会响应 Preferences 变更事件

- **Expert Info**
  - 案例1：有，5 个（3 信息性 + 2 错误性），覆盖"畸形包"和"有趣的巧合"（transid==42 的彩蛋）
  - 案例2：无
  - 案例3：无——即便存在"未知版本号""解析失败"的分支，也只是改 Info 列文本，没有注册成可过滤的 Expert Info。这是案例3相对案例1的一个不足，可以作为"如果要改进这个插件，第一件事该做什么"的练习

- **Conversation**
  - 案例1：有，且演示了三代 API 写法
  - 案例2/案例3：都没有用——PostDissector 场景不需要（每包独立处理已有字段）；RLS 场景协议头部每个包都自带完整版本号，不需要靠会话记忆来"省一次判断"

- **Heuristic Dissector**
  - 案例1：有，且注释坦诚说明"实践中不会真的把 DNS 设成启发式，这里只是为了演示"
  - 案例2/3：都没有——PostDissector 天生排在所有 dissector 之后，跟"启发式识别"是两个不同维度；RLS 协议头部第一个字节是固定的 magic byte（0x03），直接查 `udp.port` 表或做一次简单前缀判断就足够，不需要"猜"

- **Tap / Listener**
  - 三个案例都没有用到——这提示一个结论：Tap/Listener 是"做统计/流量图"这一类需求专属的基础设施，跟"如何解析单个协议"关系不大，在教学/生产的协议 dissector 里都不常见（真正常用 Tap 的场景是 IO Graph、Conversation 统计窗口这类"分析类"功能）

- **PostDissector**
  - 只有案例2使用——这是它的定义性特征

- **Menu / GUI**
  - 只有案例2的第03个示例用到（`register_menu` + `TextWindow`）——其余场景不需要自定义 UI

- **DissectorTable（复用已有的 or 自建的）**
  - 案例1：复用已有的 `udp.port`
  - 案例2：不涉及（PostDissector 不挂 DissectorTable）
  - 案例3：既复用已有的 `udp.port`，又自建了一张全新的 `rls` 表——这是三个案例里唯一演示"如何自己创建 DissectorTable 供别人挂载"的案例

- **Subdissector / 转发给别的协议**
  - 案例1：没有——DNS 记录解析到"answers/authority/additional RRs"就故意停止了（注释写"parsing answers... is up to you"），没有再往下转发
  - 案例2：没有——PostDissector 只读不转发
  - 案例3：有，且是三层链条（RLS -> RLS-3.x -> nr-rrc/ip），是三个案例里唯一体现"深度分层转发"的

## 6.9 从矩阵里能读出的结论

```
+------------------------------------------------------------------+
|  结论1：没有任何一个"标准插件"会用满所有基础设施                    |
|  三个案例合起来才覆盖了第四部分列出的全部24项基础设施，              |
|  每个案例只用了跟自己的问题域真正相关的那一部分。                     |
|                                                                    |
|  结论2：用不用某个基础设施，是"协议特性"决定的，不是"插件档次"决定的  |
|  案例3是生产级插件，但没有用 Expert Info/Conversation/Heuristic——   |
|  因为 RLS 协议不需要它们，不代表这些基础设施不重要。                  |
|                                                                    |
|  结论3：越"教学向"的代码，越倾向于"为了演示而使用"某个特性             |
|  案例1的 Heuristic 就是这样的例子（作者自己在注释里承认）；           |
|  阅读真实插件时，要能分辨"这个特性是业务真的需要"还是"作者想秀一下"。   |
|                                                                    |
|  结论4：DissectorTable 有两种使用姿势，二者经常被初学者搞混           |
|  "挂到别人已有的表"(案例1/3都做了) 和 "自己建一张新表给别人挂"          |
|  (只有案例3做了)——后者是构建"可扩展、多版本、插件生态"的关键手法。     |
+------------------------------------------------------------------+
```

## 6.10 "何时该用什么"的判断准则

- 协议**有固定端口/类型标识** -> 用 `DissectorTable:add`，不需要 Heuristic
- 协议**没有固定端口，只能猜** -> 才需要 Heuristic Dissector，且务必做"尽量便宜、尽量保守"的检查
- 协议**内部会封装别的已知协议** -> 用 Subdissector（`Dissector.get(...):call(...)`），不要自己重新解析一遍
- 协议**本身会随时间/版本演进出多种格式** -> 考虑"多 Proto + 自建 DissectorTable 做版本路由"（案例3模式），而不是一个越写越长的 if/elseif
- 需求是**"看所有协议解析完之后的结果做汇总/改列"** -> 用 PostDissector，不要塞进某个具体协议的 dissector 里
- 需求是**"做流量统计/画图，不改变单个包的展示"** -> 用 Tap/Listener，不要用 PostDissector 硬凑
- 协议**有跨包才能确定的状态**（协商结果、序列号）-> 需要 Conversation（+自建缓存），否则每包都要重新猜一次
- 需要**"用户可调"的行为** -> 用 Preferences，并一定要实现 `prefs_changed()`，否则界面显示和实际生效会不一致（呼应案例3指出的改进空间）

下一部分（[10-development-workflow.md](10-development-workflow.md)）把这些判断准则串成一条"从零开始写一个新插件"该走的通用步骤。
