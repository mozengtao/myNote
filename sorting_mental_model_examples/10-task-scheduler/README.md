# 10. 任务调度（通用化替代 Linux Scheduler 专属示例）

> 核心心智模式：**动态维护最值/优先级，而不是整体重排。**

真实的任务调度器（无论是操作系统的 CFS，还是应用层的任务队列、消息中间件的消费者）
面对的是一个持续变化的任务集合：任务不断到达、完成、优先级或截止时间也可能随时变化。
如果每次调度决策都对全部任务重新排序一次，代价会随着任务数量增长而迅速失控。
真正高效的调度器只做两件事：

1. **快速回答"接下来该运行谁"** —— 这只需要局部有序（队首/堆顶），不需要全局有序。
2. **增量维护这份局部有序性** —— 一个任务状态变化后，只需要把它移动到新的正确位置，
   而不是重新排序整个集合。

原文档使用 Linux CFS 调度器（`task_struct`、`vruntime`、红黑树）作为范例，但那依赖
特定的内核数据结构与调度语境，脱离内核环境很难写出"可编译可运行"的等价代码。这里改用
三个更通用、语义等价的工程场景来传达完全相同的心智模式，三种语言都可以直接编译/运行验证。

## 示例列表

- **example-1-weighted-fair-scheduling**：模拟类似 CFS 的加权公平调度。运行队列按
  `vruntime`（虚拟运行时间）排好序，每次调度队首任务后，只需要把它的 `vruntime` 增加、
  再把它从队首重新插入到正确位置（`reinsert_head`），全程不需要对整个队列重新排序。
  权重越大的任务 `vruntime` 增长越慢，因而长期会被调度得更频繁——这正是"公平"的体现。

- **example-2-edf-deadline-scheduling**：用最小堆实现最早截止时间优先（EDF）调度。
  堆中存放的是任务指针/引用，插入和取出都是 `O(log N)`，且堆本身从不要求维护一个
  完整有序的序列——它只保证"堆顶永远是当前最优的那个"。

- **example-3-pick-next-without-full-resort**：最朴素的增量选择模式：不维护任何有序
  结构，每次调度前对"未完成"的任务做一次线性扫描（`O(n)`），原地标记完成状态。
  新任务可以随时追加、优先级可以随时变化，都不影响下一次选择的正确性。这说明"排序"
  并不是调度器的必需品——很多时候你需要的只是"选择"，而不是"排序"。

## 与整体心智模型的呼应

三个示例分别代表了同一目标的三种实现强度：

| 示例 | 数据结构 | 单次调度成本 | 适用场景 |
|---|---|---|---|
| 加权公平调度 | 近似有序数组/队列 | O(N)（重插入） | 任务数量少、更新频繁 |
| EDF 堆调度 | 二叉堆 | O(log N) | 任务数量大、需要频繁插入/弹出 |
| 增量选择 | 无序数组 | O(N)（全扫描） | 实现最简单，任务数量较小时足够 |

无论选择哪种实现，本质都是**用尽量小的增量操作维护"下一个最优选择"**，
而不是每次都对全部任务做一次完整排序。
