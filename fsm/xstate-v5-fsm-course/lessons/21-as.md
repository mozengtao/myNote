# 21 as：为什么 `{} as {...}` 这样写

> 上一课：[20 Literal Type](20-literal-type.md) · 下一课：[22 Arrow Function](22-arrow-function.md)

现在把前三课拆开的部件重新拼回去，完整看懂开头那句话：

```ts
events: {} as
  | { type: 'NEXT' }
  | { type: 'RESET' }
```

- `{ type: 'NEXT' }` 和 `{ type: 'RESET' }`：两个**对象类型**（第 18 课），字段 `type` 是**字面量类型**（第 20 课）。
- `|`：把两个对象类型连成一个 **Union**（第 19 课）。
- `{}`：一个**空对象值**。
- `as ...`：把这个空对象值**断言**成前面拼出来的 Union 类型——这就是本课要讲的最后一块拼图。

## 1 为什么需要

`types.events` 这个字段，本质上只是想告诉 TypeScript"这台机器的事件类型长什么样"，它不需要、也不应该提供一个真正的初始事件值（事件是运行时通过 `send()` 才会产生的东西，不像 Context 有明确的初始值）。但 TypeScript 里"声明一个类型给某个字段"通常需要一个值作为载体（比如变量声明 `let x: T`）。`setup({ types: {...} })` 的字段设计成"值的位置"，于是需要一种方式：**放一个无关紧要的占位值，但把它的类型强行指定成我们真正想要的类型**。这就是 `as`（类型断言）要解决的问题。

## 2 核心思想

**`as` 是"类型断言"：告诉 TypeScript"相信我，把这个值当成这个类型来看待"，常用于"值本身不重要，只是用来承载类型信息"的场景。**

## 3 ASCII 图

```
真实值:  {}          (一个空对象，运行时什么都不是)
             |
             |  as
             v
类型标注:  { type: 'NEXT' } | { type: 'RESET' }
             |
             v
TypeScript 之后把这个位置当作这个 Union 类型来处理
（但运行时，这个位置实际的值依然只是 {}）
```

## 4 JS 写法

纯 JS 没有类型断言这个概念——因为 JS 根本没有静态类型检查，`{}` 就是 `{}`，不需要"告诉"运行时它应该被当作什么类型：

```js
const events = {}; // 纯 JS，没有类型的概念，运行时就是个空对象，仅此而已
```

## 5 TS 写法

```ts
// 场景：我知道某个变量的真实类型比 TS 自动推断出的类型更精确，用 as 手动指定
const value = {} as { type: 'NEXT' } | { type: 'RESET' };

// value 在 TypeScript 看来，类型是 Union，即使它的真实值只是一个空对象 {}
// 这在运行时不会做任何检查或转换——as 只影响"编译期 TypeScript 怎么看待这个值"

// 另一个更常见、更直观的 as 场景：DOM 操作里常见
// const input = document.getElementById('username') as HTMLInputElement;
// getElementById 默认返回类型是宽泛的 HTMLElement，但你知道这个元素具体是 input，
// 用 as 告诉 TS："相信我，这里就是 HTMLInputElement"
```

**`as` 不会在运行时做任何类型转换或检查**——它纯粹是"说服编译器"的语法，运行时该是什么还是什么。这是理解 `as` 最重要的一点：它是编译期的"断言"，不是运行时的"转换函数"。

## 6 XState 中如何使用

```ts
import { setup, createActor } from 'xstate';

const playerMachine = setup({
  types: {
    context: {} as { volume: number },
    events: {} as
      | { type: 'PLAY' }
      | { type: 'STOP' }
      | { type: 'SET_VOLUME'; level: number },
  },
}).createMachine({
  id: 'player',
  initial: 'idle',
  context: { volume: 50 }, // 这里才是真正的初始 Context 值
  states: {
    idle: {
      on: {
        PLAY: { target: 'playing' },
        SET_VOLUME: {}, // 事件处理逻辑省略
      },
    },
    playing: {
      on: { STOP: { target: 'idle' } },
    },
  },
});

const player = createActor(playerMachine).start();
player.send({ type: 'SET_VOLUME', level: 80 }); // TS 全程知道 events 可能的形状
```

对照来看：`context: {} as { volume: number }` 里的 `{}` 只是"类型占位"，真正会被使用的初始值是下面 `context: { volume: 50 }` 里写的那个；而 `events: {} as ... | ...` 里的 `{}` **永远不会被真正使用**——因为事件对象总是通过 `send()` 在运行时创建的，`types.events` 纯粹只是给 TypeScript 提供"这台机器认识哪些事件形状"的信息，这里的 `{}` 从头到尾只是一个类型断言的"挂载点"，不承载任何真实数据。

## 7 TypeScript 语法拆解

```ts
{} as { type: 'NEXT' } | { type: 'RESET' }
```
从左到右读：`{}` 是一个空对象**表达式**（真实存在的值），`as` 关键字后面跟着一个**类型**（本例是第 19 课学的 Union 类型）。整个表达式的意思是"这个空对象，请 TypeScript 把它当作后面这个类型来对待"。

```ts
document.getElementById('x') as HTMLInputElement
```
另一个经典场景：`document.getElementById` 的返回类型 TypeScript 只能推断出宽泛的 `HTMLElement | null`，但如果你确切知道这个元素是 `<input>`，用 `as` 手动告诉编译器更精确的类型，方便之后直接访问 `.value` 这类 `HTMLInputElement` 特有的属性。

## 8 常见错误

**错误 1：以为 `as` 能把一个值"真正转换"成另一种类型（混淆断言和转换）。**

```ts
// ❌ as 不会做运行时转换，这行代码运行时 num 依然是字符串 "123"，只是 TS 类型层面当作 number 看待
const num = "123" as unknown as number;
console.log(typeof num); // 'string'，不是 'number'！
```
真正需要把字符串转成数字，应该用 `Number("123")` 或 `parseInt("123")` 这类运行时函数，不是 `as`。

**错误 2：用 `as` 断言成一个和真实值完全不兼容的类型，掩盖了本该在编译期被发现的错误。**

```ts
// ❌ 滥用 as 强行让不兼容的类型通过编译，掩盖了潜在的 bug
const value = "hello" as unknown as { type: 'PLAY' };
```
`as` 应该只用在"你确实比 TypeScript 掌握更多信息"的场景（比如 XState 的 `types` 占位用法），滥用会让类型系统形同虚设，把本该在编译期发现的问题带到运行时。

**错误 3：以为 `context: {} as {...}` 里的 `{}` 会成为真正的初始 Context。**

回顾第 5 课：`types.context` 只是类型声明，真正生效的初始 Context 是 `createMachine` 配置里单独的 `context: {...}` 字段。混淆这两处，容易误以为"改了 `types.context` 里的默认值就能改变初始状态"，实际上 `types.context` 里的值从未在运行时被使用。

## 9 为什么官方这样设计

XState v5 选择用 `{} as SomeType` 这种"占位值 + 断言"的写法来声明 `types` 里的各种类型（而不是提供一个专门的、只接受类型参数的 API），是为了保持和 `setup()` 后续调用 `.createMachine({...})` 时的写法风格一致——`types` 字段整体上看起来还是"一个普通的配置对象"，只是它的值在这里"恰好不重要，只有类型重要"。这样做的好处是不需要引入额外的、只此一处使用的特殊语法，`as` 是 TypeScript 本身早已存在的通用能力，XState 只是很自然地借用了它来解决"需要一个值的位置来挂载类型信息"这个具体问题。

## 10 一句话总结

**`as` 是编译期的类型断言，不做任何运行时转换；在 XState 的 `types` 字段里，它被用来"用一个不重要的占位值，挂载真正重要的类型信息"。**

## 11 设计思考（Design Thinking）

现在可以完整回答开头的问题了——**为什么 `events: {} as | { type: 'NEXT' } | { type: 'RESET' }` 要这样写，而不是别的写法？**

**方案 A（推荐，也就是 XState 的实际写法）**：用 `{} as Union类型` 声明事件类型，值本身是占位符，类型信息才是重点。

```ts
types: {
  events: {} as { type: 'NEXT' } | { type: 'RESET' },
},
```

**方案 B（错误尝试）**：试图给 `events` 提供一个"看起来更真实"的默认值，而不是用占位的空对象。

```ts
// ❌ 没有意义：事件不是"初始就存在"的东西，运行时永远通过 send() 产生新的事件值，
// 这里写成什么"默认事件"都不会被使用，反而容易误导阅读者以为这是有意义的初始数据
types: {
  events: { type: 'NEXT' } as { type: 'NEXT' } | { type: 'RESET' },
},
```

方案 B 虽然语法上也能过编译，但它掩盖了"这个值从不会被真正使用"这个事实，容易让阅读代码的人误以为 `{ type: 'NEXT' }` 是某种"默认事件"，产生不必要的困惑。方案 A 用一个明显"空空如也"的 `{}` 作为占位符，一眼就能看出"这里的重点是后面的类型，不是这个值本身"——这也是为什么官方文档和几乎所有 XState v5 示例都统一用 `{}` 而不是某个"看起来有内容"的对象作为占位值。

## 12 设计原则（Design Rules）

本课新增：

- **`as` 是编译期类型断言，不做运行时转换；`types` 里的 `{} as T` 是"用占位值挂载类型信息"的固定套路，不代表真实的初始数据。**
- **`types.context`/`types.events` 里的值仅供类型声明，真正生效的初始数据分别在 `context: {...}` 字段和运行时的 `send()` 调用里。**
- **不要滥用 `as` 掩盖类型不兼容的问题，它应该只用于"你确实比编译器掌握更多信息"的场景。**

完整清单见 [DESIGN-RULES.md](../DESIGN-RULES.md)。

至此，开头那句 `events: {} as | { type: 'NEXT' } | { type: 'RESET' }` 已经被完全拆解：Object（每个分支的形状）→ Union（多种可能）→ Literal（精确到具体字符串）→ as（用占位值挂载这份类型信息）。这四课建立的阅读方法，可以用来拆解你在 XState 文档里遇到的几乎任何类似写法。
