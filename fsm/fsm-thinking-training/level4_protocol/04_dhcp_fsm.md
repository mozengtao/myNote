# Lesson 04: DHCP客户端FSM (Level 4 - 网络协议)

## Step 1: 是否适合FSM

逐条检查DHCP客户端地址获取与续租这个问题的"FSM特征"。

- **是否存在有限状态?**
  是。RFC2131第4.4节及其附图定义了客户端侧的状态集合:INIT、SELECTING、REQUESTING、BOUND、RENEWING、REBINDING,以及用于"曾经有过租约、重启/切换网络后尝试快速复用"的INIT-REBOOT、REBOOTING。数量固定,且每个状态描述客户端"和IP地址租约之间关系的进展阶段"。

- **是否依赖历史状态?**
  是。最典型的例子是INIT和INIT-REBOOT的区别——两者看起来都是"准备重新申请地址",但INIT代表"没有任何可用的历史租约信息,从零开始";INIT-REBOOT代表"本地缓存里还留着上次的租约记录(比如笔记本电脑休眠后被唤醒,网卡驱动重新初始化),值得先尝试确认这个旧地址是否还能继续用"。要不要走INIT-REBOOT这条捷径,完全取决于"是否存在历史租约缓存"这一件事。

- **是否由事件驱动?**
  是,而且这一课的核心训练点是:**"租约"本身是一种带着时间属性的状态**,BOUND状态的结束不是由外部报文触发的,而是由租约自带的两个内部计时器T1、T2的到期触发的——这是"计时器驱动状态转移"在本系列课程里第三次出现(交通灯、BGP之后),但这次计时器和"租约剩余时间"这个业务数据本身直接绑定,值得专门比较。

- **是否同一个事件在不同状态行为不同?**
  是。"收到DHCPNAK(服务器拒绝确认)"这件事,在REQUESTING状态下意味着"这次申请失败,回到INIT重新走完整流程";在RENEWING/REBINDING状态下意味着"续租失败,必须放弃当前地址,回到INIT重新申请一个全新地址";在REBOOTING状态下意味着"旧地址已经不可用,回到INIT走全新流程"——虽然三处最终都回到INIT,但"发生NAK"这件事背后代表的业务含义(丢弃刚申请中的地址 vs 放弃已经在用的地址 vs 放弃缓存的旧地址)是不同的,值得在Action列里分别说明。

- **是否存在明确状态切换?**
  是,每一步(发现服务器、选择一个提供的地址、确认申请、进入正常使用、续租、重新绑定)都有明确的报文交互或计时器边界。

**适合FSM: ★★★★★**

理由:DHCP客户端状态机同样是RFC2131正文直接给出图示的正式规范内容。这一课比前面几课更值得注意的是"状态带着时间戳/剩余时长这种业务数据"的建模方式——纯粹的"状态名字"不足以完整描述BOUND状态到底还能持续多久,必须搭配租约的起止时间或者T1/T2剩余时间这样的伴随数据,这是`dataclass`在本系列课程里发挥价值的一个典型场景。

## Step 2: 发现状态

**引导性问题:**
- 一台还没有IP地址的设备,要经历哪几个阶段才能真正"能用网络"?
- "已经拿到一个IP地址,可以正常使用"和"这个IP地址还能用多久"是不是同一个维度的信息?
- 续租(renew)为什么要拆成RENEWING和REBINDING两个不同的状态,而不是"续租失败就重新申请"这么简单?
- 电脑休眠后重新联网,为什么不总是从头走一遍发现流程?这种"抄近路"的行为该怎么在状态机里体现?

**思考过程:**

先看主干流程:

1. **INIT** —— 客户端没有任何可用的地址信息(无历史租约,或历史租约已经彻底作废),准备从零开始申请。这是最"干净"的起点。
2. **SELECTING** —— 已经广播发送了DHCPDISCOVER,正在收集网络上可能有多台DHCP服务器各自返回的DHCPOFFER,等待客户端从中选择一个。
3. **REQUESTING** —— 已经选定了某一个服务器的Offer,并广播发送DHCPREQUEST正式表明"我要这个地址"(用广播而不是单播,是为了让其他曾经报价的服务器也知道自己的Offer没有被选中,可以释放预留的地址),等待被选中的服务器回复确认。
4. **BOUND** —— 收到DHCPACK确认,租约正式生效,客户端可以正常使用这个IP地址。这是"业务上正常工作"的稳定状态,但**这个状态并不是永久的**——每一份DHCP租约都带有一个明确的到期时间(lease time),这是理解DHCP状态机的关键:**BOUND不是"我拿到了地址,从此天下太平",而是"我拿到了一个有截止日期的临时使用权"**。

**为什么续租要拆成RENEWING和REBINDING两步,而不是"到期前统一续一次"?** 这里需要引入T1、T2两个计时器的设计初衷:
- **T1(默认是租约总时长的50%)** —— 到达T1时刻,客户端进入**RENEWING**,开始**单播**向"当初发放这个租约的那台服务器"发送DHCPREQUEST请求续租。选择单播是因为客户端明确知道自己是向哪台服务器续租,没必要打扰网络上的其他服务器。
- **T2(默认是租约总时长的87.5%)** —— 如果到了T1时刻发的单播请求一直没有得到明确答复(那台服务器可能已经下线、网络分区等),客户端不会傻等到租约彻底过期,而是在T2时刻进入**REBINDING**,把续租请求改成**广播**——意思是"原来那台服务器联系不上,只要网络上任何一台服务器愿意确认我继续用这个地址,我都接受"。
- 如果连广播的REBINDING阶段都得不到任何回应,直到租约彻底到期(100%),客户端只能放弃这个地址,回到INIT重新申请一个全新的。

**这三个阶段(RENEWING/REBINDING/彻底过期)本质上是同一个"续租失败风险"在不同紧迫程度下的递进反应**——单播续租失败的代价小(还有时间),所以先尝试范围最小、开销最小的方式;越接近过期,越放宽请求范围(从单播到广播),这是一种"逐步升级的容错策略",拆成独立状态正是为了让这种"升级节奏"能被精确描述和实现,如果合并成一个"续租中"状态,就没法表达"现在该用单播还是广播"这个关键区别。

**INIT-REBOOT和REBOOTING是为了什么场景存在?** 考虑一台笔记本电脑,上次联网时拿到过一个租约,本地还缓存着这个地址和相关信息(还没过期)。如果每次网卡重新初始化(比如从睡眠中唤醒、插拔网线)都要走一遍完整的DISCOVER→OFFER→REQUEST→ACK流程,既浪费时间也浪费网络上的广播流量。所以RFC2131专门设计了一条捷径:
- **INIT-REBOOT** —— 检测到本地存在一个尚未过期的历史租约缓存,决定"先赌一把这个地址还能用",直接广播发送带有该地址的DHCPREQUEST(不需要先发DISCOVER,跳过SELECTING阶段)。
- **REBOOTING** —— 等待服务器对这次"确认旧地址"的请求做出答复。如果收到DHCPACK,直接进入BOUND(相当于抄了近路);如果收到DHCPNAK(说明这个地址已经过期或者被别的设备占用了),必须老老实实回到INIT从头走完整流程。

这组状态的存在提醒我们:**一台状态机可以为"常见的快速路径"专门设计一条捷径分支,只要这条捷径最终依然能安全地汇合回主干流程(REBOOTING失败依然乖乖回INIT,而不是尝试绕过安全检查直接假装成功)**。

**确定的状态清单:**

| 状态 | 说明 | 互斥性 | 持续性 |
|---|---|---|---|
| INIT | 无可用地址信息,准备从零申请 | 与其余状态互斥 | 直到发送DISCOVER |
| SELECTING | 已广播DISCOVER,正在收集OFFER | 互斥 | 直到选定一个Offer并发送REQUEST |
| REQUESTING | 已广播REQUEST确认选择,等待ACK | 互斥 | 直到收到ACK/NAK或超时 |
| BOUND | 租约生效,正常使用地址(带租约到期时间) | 互斥 | 直到T1计时器到期或应用主动释放 |
| RENEWING | 单播向原服务器请求续租 | 互斥 | 直到收到ACK/NAK或T2计时器到期 |
| REBINDING | 广播向任意服务器请求续租 | 互斥 | 直到收到ACK/NAK或租约彻底到期 |
| INIT-REBOOT | 存在未过期的历史租约缓存,准备尝试复用 | 互斥 | 直到发送确认性REQUEST |
| REBOOTING | 已发送确认性REQUEST,等待服务器答复 | 互斥 | 直到收到ACK/NAK或超时 |

8个状态两两互斥,BOUND/RENEWING/REBINDING这条链路共享同一份"租约"数据(到期时间、T1、T2),只是随着时间推移不断升级续租的紧迫程度。

## Step 3: 寻找事件

**引导性问题:**
- 发送DHCPDISCOVER/DHCPREQUEST这些报文,是"事件"还是"动作"?
- T1和T2到期,和"租约彻底过期"这三个时间点,分别对应什么性质不同的事件?
- 收到多个DHCPOFFER,客户端要不要为每一个Offer的到达都触发一次状态转移?
- 用户主动断开网络/释放地址(DHCPRELEASE),算什么性质的事件?

**分析过程:**

- 客户端**主动发送**的报文(DISCOVER、REQUEST)是状态转移之后的**动作**,不是事件——真正的事件是促使客户端决定发送这些报文的原因(比如"进入了INIT状态,自动触发发送DISCOVER的动作")。这里要分清:是"进入某个状态后自动执行的动作"驱动了报文发送,而不是"发送报文"这个行为本身是一个需要被外部输入触发的事件。
- **收到DHCPOFFER**——虽然网络上可能有多台服务器,每台都发来了一个Offer,但只有"客户端已经决定选中其中一个,并广播了REQUEST"这一步才是真正驱动状态跳转的事件(`OfferSelected`);单纯"又收到了一个新的Offer"如果客户端已经做过选择,不会触发任何转移,只是被记录进候选列表(在SELECTING阶段收集阶段本身,可以简化为"收到至少一个Offer后经过一小段收集窗口,然后触发选择"这一逻辑,不必对每一个到达的Offer都定义单独的事件)。
- **T1计时器到期、T2计时器到期、租约彻底到期**——这是这一课要重点辨析的三个不同粒度的计时器事件,分别驱动BOUND→RENEWING、RENEWING→REBINDING(如果尚未收到回复)、REBINDING→INIT(彻底失败)三次不同的转移,三者不能合并成同一个"租约相关计时器超时"笼统事件,因为它们各自触发的后续动作(单播 vs 广播 vs 彻底放弃)完全不同。
- **收到DHCPACK**——在REQUESTING/RENEWING/REBINDING/REBOOTING这几个"正在等待服务器确认"的状态下都可能收到,但都统一走向BOUND(并且要用ACK里携带的新租约时间重新设置T1、T2),这是"同一事件、不同来源状态、相同目标状态"的例子(和BGP课程Step 3提到的情况类似,不必强行制造差异)。
- **收到DHCPNAK**——同样可能发生在REQUESTING/RENEWING/REBINDING/REBOOTING,但根据Step 1已经分析过的原因,虽然目标状态统一是INIT,Action列的具体处理(丢弃候选地址 vs 放弃使用中的地址)不同,这提示我们:**转移表允许"多个源状态收敛到同一目标状态",但不代表这些转移的Action都一样,必须逐条写清楚**。
- **应用主动释放(DHCPRELEASE)**——这是一种"人为触发"的事件,合法情况下只应该发生在BOUND/RENEWING/REBINDING这几个"当前持有有效地址"的状态,直接释放地址回到INIT,属于用户主动放弃而不是异常。

区分总结:
- **动作(不改变状态,由进入某状态后自动触发)**:进入INIT后自动发送DISCOVER、进入SELECTING选定Offer后自动发送REQUEST、进入BOUND后设置T1/T2计时器。
- **真正触发转移的事件**:`OfferSelected`、`RcvAck`、`RcvNak`、`T1Expires`、`T2Expires`、`LeaseExpires`、`AppRelease`、`HasCachedLease`(用于判断INIT该走向普通流程还是INIT-REBOOT捷径的决策条件,严格来说是一个"判定结果"而非网络输入,但对状态机而言同样是驱动转移的事件)。
- **应忽略的输入**:SELECTING阶段收到的"迟到"的额外Offer(已经选定过就不再重新评估,简化模型不支持"选择更优Offer后反悔"这种优化)。

**确定的事件清单:**

| 事件 | 说明 |
|---|---|
| DiscoverNeeded | 判定无可用历史租约,需要从零申请(用于INIT自动触发DISCOVER的内部决策) |
| HasCachedLease | 判定存在未过期的历史租约缓存,走INIT-REBOOT捷径 |
| OfferSelected | 已从收集到的Offer中选定一个,准备发送REQUEST |
| RcvAck | 收到服务器确认(DHCPACK) |
| RcvNak | 收到服务器拒绝(DHCPNAK) |
| T1Expires | 租约计时器T1到期,开始单播续租 |
| T2Expires | 租约计时器T2到期且尚未续租成功,改为广播续租 |
| LeaseExpires | 租约彻底到期且仍未续租成功 |
| AppRelease | 应用/用户主动释放地址 |

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| INIT | DiscoverNeeded | SELECTING | 广播DHCPDISCOVER |
| INIT | HasCachedLease | INIT-REBOOT | 准备复用历史缓存地址 |
| INIT-REBOOT | (进入即自动) | REBOOTING | 广播DHCPREQUEST(确认旧地址) |
| REBOOTING | RcvAck | BOUND | 复用旧地址成功,设置新的T1/T2 |
| REBOOTING | RcvNak / 超时 | INIT | 旧地址不可用,回到INIT走完整流程 |
| SELECTING | OfferSelected | REQUESTING | 广播DHCPREQUEST确认选择 |
| REQUESTING | RcvAck | BOUND | 租约生效,设置T1/T2计时器 |
| REQUESTING | RcvNak / 超时 | INIT | 申请失败,重新开始 |
| BOUND | T1Expires | RENEWING | 单播DHCPREQUEST向原服务器续租 |
| BOUND | AppRelease | INIT | 主动释放地址,发送DHCPRELEASE |
| RENEWING | RcvAck | BOUND | 续租成功,刷新租约时间并重设T1/T2 |
| RENEWING | RcvNak | INIT | 服务器明确拒绝续租,放弃地址重新申请 |
| RENEWING | T2Expires | REBINDING | 单播续租无响应,改为广播尝试 |
| REBINDING | RcvAck | BOUND | 续租成功,刷新租约时间并重设T1/T2 |
| REBINDING | RcvNak | INIT | 服务器明确拒绝续租,放弃地址重新申请 |
| REBINDING | LeaseExpires | INIT | 广播续租仍无响应且租约到期,放弃地址 |

表中省略了RFC2131里关于ARP冲突检测(客户端在正式使用地址前用ARP探测该地址是否已被占用)、DHCPDECLINE等边界流程,教学目的是覆盖"发现→选择→确认→绑定→(单播续租→广播续租→放弃)"以及"缓存复用捷径(INIT-REBOOT)"这条主干路径和关键失败路径。

## Step 6: Python实现

完整代码见同目录下的 `04_dhcp_fsm.py`。这一课的重点是用`dataclass`表达"租约"这种带时间属性的数据,并让状态转移和租约数据的更新绑定在一起。

**v1:Enum + match-case版**
`DHCPClientV1`除了`state`字段,还有一个`Lease | None`类型的字段表示当前持有的租约(`None`代表尚未持有任何地址)。`match`分支里处理RcvAck时会创建一个新的`Lease`对象并计算T1/T2到期时间。

**v2:Transition Table版**
把主干转移整理成字典,`(BOUND, T1Expires)`、`(RENEWING, T2Expires)`等计时器驱动的转移和`(SELECTING, OfferSelected)`这类报文驱动的转移共用同一张表、同一种查表逻辑——这进一步印证Level 4从TCP到OSPF到BGP再到DHCP一直在强调的观点:**计时器事件和网络事件在转移表层面没有任何特殊之处,不需要单独设计一套"计时器专用"的处理路径**。

**v3:State Pattern版**
用来体现"续租紧迫程度递进"这条逻辑——RENEWING和REBINDING两个状态类分别实现自己的`retry_scope()`方法(一个返回`"unicast"`,一个返回`"broadcast"`),让"这个状态该用什么范围发送续租请求"这个业务规则直接挂在状态类上,而不是靠调用方自己判断"现在是RENEWING还是REBINDING,所以该用哪种发送方式"。

**v4:通用FSM框架 + tick驱动**
和BGP那一课一样,用`tick(seconds)`模拟时间推进,自动根据租约的T1/T2/到期时间生成相应事件注入状态机,展示"BOUND状态一段时间后自动老化为RENEWING、REBINDING,最终如果没有服务器响应则彻底放弃"的完整生命周期。

运行`python3 04_dhcp_fsm.py`可以看到一次"申请地址成功→正常使用→续租成功"的完整周期,以及一次"INIT-REBOOT捷径复用历史地址成功"的演示。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**
如果不用FSM,DHCP客户端的状态大概率会退化成一堆布尔标志位加一堆时间戳比较(`if now > lease.t1_deadline and not renewed`),这类"用当前时间和几个截止时间比大小"的逻辑非常容易在边界条件上出错(比如恰好等于截止时间该算哪一边、T1和T2同时接近到期该怎么排优先级)。用FSM,"现在到底处于续租流程的哪一步"永远由state字段唯一确定,不需要每次都重新推算"现在时间和哪个截止时间比较后处于什么阶段"。

**"状态带时间属性数据"这种设计,给FSM实现带来了什么额外要求?**
纯粹的状态名字(比如"BOUND")不足以回答"这个状态还能持续多久"这个问题,必须搭配租约的到期时间这类伴随数据。这意味着在设计Transition/Action时,不能只考虑"要不要跳转状态",还要考虑"跳转/停留在这个状态时,伴随数据(截止时间、剩余时长)要不要被更新"——续租成功后重设T1/T2就是这样一个例子:状态其实还是回到了同一个BOUND,但伴随数据必须刷新,否则会立刻被误判为"又该续租了"。

**什么情况下FSM反而是负担?**
如果一个内部服务只是简单地从环境变量或配置文件读一次固定IP地址(不需要动态申请、不需要续租),那当然不需要任何状态机;即使需要动态获取地址,如果场景里"租约永不过期"或者"服务重启就重新申请,不关心续租"(某些容器化场景确实这样简化处理),那么RENEWING/REBINDING这两级递进的续租状态就是不必要的复杂度,可以直接砍掉,只保留INIT→BOUND两个状态。

**什么时候不应该使用FSM?**
如果续租失败的后果永远是"立刻停止工作并报警",不需要区分"单播重试"和"广播重试"这两级递进的容错策略,那么用一个简单的"最后成功续约时间 + 固定超时阈值"的判断就够了,不需要完整实现T1/T2两级计时器。

**为什么协议标准文档几乎总是直接给出状态图和状态表,这一现象说明了什么?**
DHCP的T1/T2两级递进策略,如果不通过状态图明确定义"哪个阶段该用单播、哪个阶段该用广播",不同厂商的客户端实现很可能会各自发挥,造成有的客户端过早开始广播骚扰网络、有的客户端续租过于保守导致频繁掉线。RFC2131用状态图把这套"逐步升级的容错节奏"精确固化下来,这正是协议标准存在的核心价值——不是记录"一种可行的实现",而是"钉死一种大家都要遵守的行为节奏",FSM恰好是表达"节奏"和"分级升级策略"最精确的工具。

## Step 8: FSM思维总结

```
==========
FSM识别口诀(DHCP篇)
==========
✓ 某些状态本身带着"有效期"这种时间属性,需要搭配伴随数据(dataclass)而不是裸的state字段
✓ 计时器事件可以有多个级别(T1/T2/彻底过期),分别对应"逐步升级"的不同容错策略
✓ 常见的"抄近路"场景(缓存/历史信息可复用)值得设计成独立的捷径分支,但必须能安全地汇合回主干失败路径
✓ 转移可以"多个源状态收敛到同一目标状态",但目标相同不代表Action相同,必须逐条确认
✓ 续租/续约类状态转移的关键不是"要不要跳状态",而是"伴随数据是否需要被刷新"
```

## Step 9: 迁移训练题

1. TLS/SSL的证书文件同样有"有效期"这个时间属性,并且很多系统会在证书到期前的某个提前量自动触发续期(比如Let's Encrypt的证书默认90天有效期,ACME客户端通常在到期前30天左右开始尝试续期)。如果用本课的思路建模一个"证书生命周期状态机",你预期会有几级"续期紧迫程度递进"的状态?是否也需要类似T1/T2这样的多级提前量?
2. Kubernetes里的Pod使用"探针(liveness probe/readiness probe)"判断容器是否健康,并且很多资源对象(如Lease、Endpoint)也有"续约"机制防止对象因为控制器崩溃而被误判为失效。如果为一个"Kubernetes Lease对象"的持有者建模一台续约状态机,它和DHCP客户端的BOUND/RENEWING/REBINDING这条链路有多大的结构相似性?
3. 手机的移动网络"位置更新(Location Update)"和"周期性附着(Periodic Attach/Registration)"机制,同样需要在信号覆盖不稳定的情况下,决定"多久没更新算失联""失联后要不要退避重试、按什么节奏重试"。如果要你为手机和基站之间的注册状态建模一台FSM,你觉得会不会也存在类似"T1/T2"这种分级超时升级的设计?

## 今天真正学会的一句话

当一个"正常工作"的状态本身带着明确的截止时间,而不是永久有效时,不要只满足于"到期后重新申请"这么简单的建模——想清楚"越接近截止时间,容错策略要不要跟着升级"(DHCP从单播续租到广播续租正是这种升级),往往能发现原本被合并成一个状态的"续租中"其实值得拆成好几个体现不同紧迫程度的独立状态。
