# Lesson 01: TCP连接状态机 (Level 4 - 网络协议)

## Step 1: 是否适合FSM

逐条检查TCP连接管理这个问题的"FSM特征"。

- **是否存在有限状态?**
  是,而且是本教程目前为止最"官方"的一个案例——RFC793在文本里直接给出了一张状态图和11个具名状态:CLOSED、LISTEN、SYN_SENT、SYN_RECEIVED、ESTABLISHED、FIN_WAIT_1、FIN_WAIT_2、CLOSE_WAIT、CLOSING、LAST_ACK、TIME_WAIT。数量固定,不存在"第12种状态",这是标准协议和玩具案例的一个重要区别:状态集合是被规范"钉死"的,任何实现都不能随意增删。

- **是否依赖历史状态?**
  是,而且依赖得很"深"。表面上FSM的承诺是"下一步只取决于当前状态",但TCP恰恰是最能体现这句话背后代价的例子:要让"当前状态"真正概括所有必要的历史信息,建模阶段必须想清楚很多容易混淆的情况——比如"收到对方FIN"这件事,如果发生在我还没主动关闭之前,应该进CLOSE_WAIT;如果发生在我已经主动关闭之后(FIN_WAIT_1),要看是否同时收到了对我FIN的ACK,分别进CLOSING或TIME_WAIT。状态名字本身就是"压缩过的历史"——CLOSING这个名字背后压缩的历史是"双方几乎同时发起了关闭"。

- **是否由事件驱动?**
  是,而且事件来源是三类混合的:应用层调用(主动打开/被动打开/主动关闭)、网络上收到的报文(带SYN/ACK/FIN/RST标志的段)、以及定时器(2MSL超时、重传超时)。这也是Level 4要强调的重点之一:工业级协议的FSM几乎从不是"只有一种事件来源"的干净模型。

- **是否同一个事件在不同状态行为不同?**
  是,而且是本教程里最典型的例子。"收到ACK"这一件事:在SYN_RECEIVED里意味着三次握手完成、进ESTABLISHED;在FIN_WAIT_1里意味着我方FIN被确认、进FIN_WAIT_2;在CLOSING里意味着关闭流程终于收敛、进TIME_WAIT;在LAST_ACK里意味着连接彻底结束、进CLOSED。同一个"RCV_ACK"事件,四种完全不同的目的地,完全由当前状态决定——这正是"必须用状态区分行为"而不能只用一个全局标志位的铁证。

- **是否存在明确状态切换?**
  是。每个状态的进入和离开都对应一个具体的报文到达或应用调用,没有"半个SYN_SENT"这种模糊过渡态。

**适合FSM: ★★★★★**

理由:TCP连接管理几乎是"协议设计者主动选择用FSM描述协议"的第一手证据——RFC793原文直接给出状态图,不是后人总结出来的。11个状态、几十条转移规则,如果不用FSM而是用一堆布尔标志位(`is_syn_sent`、`is_fin_sent`、`is_fin_acked`、`peer_fin_received`……)去拼凑等价逻辑,标志位组合的可能取值远超11种,大量组合是"不可能出现的非法状态",维护成本和出错概率都会指数级上升。这也是为什么几乎所有真实TCP协议栈实现(Linux内核`net/ipv4/tcp_input.c`等)内部都保留了和RFC793一致的状态命名。

## Step 2: 发现状态

**引导性问题:**
- 一条TCP连接从"不存在"到"数据双向传输"再到"彻底消失",必然要经历哪些阶段?
- 关闭一条连接为什么不能是一个瞬间动作("发个FIN,连接就没了"),而要拆成好几个状态?
- TCP是全双工的,"我不再发数据了"和"对方不再发数据了"是不是同一件事?如果不是,状态该怎么体现这个区别?
- 有没有状态是专门为了"应对某种同时发生的巧合情况"才存在的?

**思考过程:**

先看连接建立部分,这一段相对直觉:

1. **CLOSED** —— 连接不存在,这是默认起点也是最终归宿。
2. **LISTEN** —— 服务器执行了"被动打开"(调用`listen()`),等待远端发起连接。这是一个会持续存在的稳定状态,不是瞬间动作。
3. **SYN_SENT** —— 客户端执行了"主动打开",已发出SYN,等待对方的SYN+ACK。
4. **SYN_RECEIVED** —— 收到了对方的SYN(不管是LISTEN方收到SYN,还是SYN_SENT方在极少见的"同时打开"场景下也收到对方的SYN),已回复SYN+ACK,等待最终ACK确认三次握手完成。
5. **ESTABLISHED** —— 三次握手完成,双向数据传输的正常工作状态。

真正需要仔细想的是关闭部分。**如果关闭只是"发一个FIN,收到ACK,连接结束",为什么RFC793要为此专门定义6个状态(FIN_WAIT_1、FIN_WAIT_2、CLOSE_WAIT、CLOSING、LAST_ACK、TIME_WAIT)?**

关键在于TCP是**全双工**协议——一条连接其实是两条独立的数据流(我发给你、你发给我),关闭动作也是"半个方向、半个方向"分开进行的,这就是"半关闭(half-close)"语义。拆开来看:

- 假设是A主动发起关闭。A发送FIN,这只是关闭了"A→B"这个方向,并不代表B不能再往A发数据了。A此时进入**FIN_WAIT_1**(我方FIN已发出,等待对方确认)。
- B收到A的FIN后,B进入**CLOSE_WAIT**——注意这个状态的真实含义是"对方已经不会再给我发数据了,但我这边如果还有数据要发给对方,完全可以继续发",这正是全双工/半关闭最直观的体现。B不会因为收到FIN就立刻关闭自己这一侧。
- A收到"我方FIN被B确认"这个ACK后,进入**FIN_WAIT_2**——此时A已经彻底不能再发数据了,但仍然可以合法地接收B发来的剩余数据,直到B也发来FIN。这是又一个"我方已关闭、对方尚未关闭"的半关闭态,和CLOSE_WAIT正好是同一枚硬币的两面。
- B把自己该发的数据发完后,也调用关闭,发出FIN,进入**LAST_ACK**(等待A确认我这最后的FIN)。
- A收到B的FIN,回复ACK,进入**TIME_WAIT**;B收到这个ACK后进入**CLOSED**。

那**CLOSING**是为了什么?考虑一种巧合:双方几乎同时主动关闭——A处于FIN_WAIT_1(已发FIN,还没收到对方ACK)时,如果这时收到的不是"对我方FIN的ACK",而是"对方也发来了一个FIN"(说明对方也在同时关闭而不是被动响应),A就不能直接去FIN_WAIT_2,因为对方还没确认我的FIN。这种情况被单独建模成**CLOSING**状态——它的语义是"双方几乎同时发起了关闭,都在等待对方确认自己的FIN"。如果没有这个状态,同时关闭的场景要么会被错误地按半关闭流程处理,要么协议实现者只能用额外的标志位去区分"我是主动方还是遇到了同时关闭",这正好印证了Step 1里"依赖历史"的判断——CLOSING这个状态名本身就是"检测到了同时关闭"这段历史的压缩表示。

最后,**TIME_WAIT为什么不能直接跳到CLOSED?** 它存在两个工程原因:(1) A发出的最后一个ACK可能丢失,如果B没收到会重发FIN,A需要保持一段时间"记忆"以便重新回复ACK,而不是回一个RST吓到对方;(2) 防止本连接里滞留在网络中的迟到重复报文,被后续复用相同四元组(同一对IP+端口)的新连接误当成属于自己的数据。这两个原因都不是"业务逻辑",而是"网络本身不可靠"这个客观事实倒逼出来的状态——这提示我们:协议FSM里的某些状态,是为了容忍网络/时间的不确定性而存在的,不是为了描述业务流程。

**确定的状态清单:**

| 状态 | 说明 | 互斥性 | 持续性 |
|---|---|---|---|
| CLOSED | 连接不存在 | 与其余10个状态互斥 | 直到被动/主动打开事件发生 |
| LISTEN | 服务端等待连接请求 | 互斥 | 直到收到SYN或应用取消监听 |
| SYN_SENT | 客户端已发SYN,等待SYN+ACK | 互斥 | 直到收到响应或超时 |
| SYN_RECEIVED | 已收到SYN并回复SYN+ACK,等待最终ACK | 互斥 | 直到收到ACK或超时/收到RST |
| ESTABLISHED | 三次握手完成,双向数据传输 | 互斥 | 直到任一方发起关闭(FIN)或收到RST |
| FIN_WAIT_1 | 已主动发FIN,等待对方确认我方FIN | 互斥 | 直到收到ACK或对方的FIN |
| FIN_WAIT_2 | 我方FIN已被确认,等待对方也发FIN(半关闭:只收不发) | 互斥 | 直到收到对方FIN |
| CLOSE_WAIT | 已收到对方FIN并确认,但我方仍可继续发数据(半关闭:只发不收) | 互斥 | 直到本地应用也调用关闭 |
| CLOSING | 双方几乎同时发起关闭,互相等待对方确认自己的FIN | 互斥 | 直到收到对方对我方FIN的ACK |
| LAST_ACK | 被动关闭方已发出自己的FIN,等待最后的ACK | 互斥 | 直到收到ACK |
| TIME_WAIT | 主动关闭方已完成全部握手,等待网络中迟到报文消散 | 互斥 | 持续固定的2MSL时长后自动结束 |

11个状态两两互斥,且每一个都能清楚说出"从哪个事件进来、靠哪个事件离开",满足状态的定义。

## Step 3: 寻找事件

**引导性问题:**
- 真正会让连接从一个阶段跳到另一个阶段的,是"报文到达"本身,还是"报文里的某个标志位组合"?
- 收到一个携带数据但不带SYN/FIN的普通报文,算不算一个会触发状态转移的事件?
- 应用层调用(`connect()`、`listen()`、`close()`)算事件吗,还是只是触发事件的"外部原因"?
- 定时器超时算不算事件?TCP里有几种定时器,分别对应什么转移?

**分析过程:**

- 报文里的**标志位组合**(SYN、SYN+ACK、纯ACK、FIN、FIN+ACK、RST)才是状态机真正关心的输入,而不是"收到了一个报文"这种笼统描述——两个都收到了报文,一个带SYN、一个带纯ACK,会走向完全不同的转移,所以事件必须细分到标志位组合级别。
- **携带数据但不带控制标志位的普通报文**(比如ESTABLISHED状态下收到的正常数据段)不会触发状态转移,它只是被交给应用层读取的"动作",这属于TCP的可靠传输/数据搬运职责,和连接状态机是两回事——这是本课要着重区分的一点:数据平面的活动(确认号、窗口、重传)有自己的一套逻辑,不应该和连接状态机混在一起讨论,否则状态数量会失控。
- **应用层调用**(主动打开/被动打开/关闭)确实是事件,而且是这台状态机里"由本地主动触发"而非"网络被动触发"的那一类事件,和网络报文到达的事件性质不同,但对状态机来说没有区别——都是"输入",都通过转移表统一处理。
- **定时器超时**——TIME_WAIT状态里的2MSL计时器到期,是一个不折不扣的"事件",它触发TIME_WAIT到CLOSED的转移,而且这个转移完全不依赖任何报文到达。RFC793另外还定义了重传定时器,但那属于"某个已发送的报文迟迟没被确认,要不要重发"这个可靠性问题,不改变连接状态本身(重传的还是同一个SYN或FIN,状态不变),所以本课的转移表不把它单独列为一条转移规则,只在SYN_SENT/SYN_RECEIVED的超时兜底里体现"多次重传失败最终回到CLOSED"这一条。
- **RST(连接重置)**——这是一种应该被认真对待的"异常事件",在任何状态收到合法的RST,几乎都直接回到CLOSED,这和"收到FIN走正常关闭流程"是完全不同的两条路径,必须分开建模,不能把RST也塞进FIN的处理逻辑里。

区分总结:
- **动作(不改变连接状态)**:收到不带控制位的数据段并交给应用层、发送数据段、重传定时器触发的报文重发。
- **真正触发转移的事件**:`PASSIVE_OPEN`、`ACTIVE_OPEN`、`APP_CLOSE`、`RCV_SYN`、`RCV_SYN_ACK`、`RCV_ACK`、`RCV_FIN`、`RCV_FIN_ACK`(FIN和ACK在同一报文里的特殊情况)、`RCV_RST`、`TIMEOUT_2MSL`。
- **应忽略/不改变状态的输入**:ESTABLISHED态收到的普通数据段、无法识别的畸形报文(生产实现通常直接丢弃或回RST,教学模型里简化为忽略)。

**确定的事件清单:**

| 事件 | 说明 |
|---|---|
| PASSIVE_OPEN | 应用调用被动打开(如`listen()`) |
| ACTIVE_OPEN | 应用调用主动打开(如`connect()`) |
| APP_CLOSE | 应用调用主动关闭 |
| RCV_SYN | 收到对方的SYN段 |
| RCV_SYN_ACK | 收到对方的SYN+ACK段 |
| RCV_ACK | 收到对方对我方某个报文的确认(纯ACK) |
| RCV_FIN | 收到对方的FIN段 |
| RCV_FIN_ACK | 收到同时带FIN和对我方FIN确认的段(用于建模同时关闭收敛的一种简化路径) |
| RCV_RST | 收到连接重置段 |
| TIMEOUT_2MSL | TIME_WAIT计时器到期 |

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| CLOSED | PASSIVE_OPEN | LISTEN | 分配控制块,进入监听 |
| CLOSED | ACTIVE_OPEN | SYN_SENT | 发送SYN,启动重传定时器 |
| LISTEN | RCV_SYN | SYN_RECEIVED | 发送SYN+ACK |
| LISTEN | APP_CLOSE | CLOSED | 释放控制块,停止监听 |
| SYN_SENT | RCV_SYN_ACK | ESTABLISHED | 发送ACK,握手完成 |
| SYN_SENT | RCV_SYN | SYN_RECEIVED | 发送SYN+ACK(同时打开场景) |
| SYN_SENT | 重传超限/RCV_RST | CLOSED | 放弃连接尝试 |
| SYN_RECEIVED | RCV_ACK | ESTABLISHED | 三次握手完成 |
| SYN_RECEIVED | APP_CLOSE | FIN_WAIT_1 | 发送FIN(握手未完成前提前关闭) |
| SYN_RECEIVED | RCV_RST | LISTEN / CLOSED | 被动方回到LISTEN继续等待;主动方直接CLOSED |
| ESTABLISHED | APP_CLOSE | FIN_WAIT_1 | 发送FIN,进入主动关闭流程 |
| ESTABLISHED | RCV_FIN | CLOSE_WAIT | 回复ACK,标记对方已停止发送 |
| ESTABLISHED | RCV_RST | CLOSED | 异常终止连接 |
| FIN_WAIT_1 | RCV_ACK | FIN_WAIT_2 | 我方FIN已被确认 |
| FIN_WAIT_1 | RCV_FIN | CLOSING | 双方同时关闭,等待对方确认我方FIN |
| FIN_WAIT_1 | RCV_FIN_ACK | TIME_WAIT | 对方FIN与对我方FIN的确认一并到达,直接进入等待收尾 |
| FIN_WAIT_2 | RCV_FIN | TIME_WAIT | 回复ACK,双向关闭完成,进入收尾等待 |
| CLOSE_WAIT | APP_CLOSE | LAST_ACK | 本地数据也发完,发送我方FIN |
| CLOSING | RCV_ACK | TIME_WAIT | 对方确认了我方FIN,进入收尾等待 |
| LAST_ACK | RCV_ACK | CLOSED | 对方确认了我方FIN,连接结束 |
| TIME_WAIT | TIMEOUT_2MSL | CLOSED | 2MSL时间到,安全销毁连接记录 |
| (任意含established的状态) | RCV_RST | CLOSED | 收到重置,立即异常终止,不走正常关闭流程 |

表中省略了大量RFC793定义的边界情况(如收到不合法序列号段的处理、同时打开路径下SYN_RECEIVED的细分),教学目的是覆盖主干路径(建立、单方主动关闭、同时关闭)和关键异常/超时路径(RST、2MSL超时)。

## Step 5: ASCII状态图

为了避免把11个状态和几十条箭头挤在一张图里相互交叉、反而看不清楚,这里仿照大多数教材的做法拆成"建立阶段"和"关闭阶段"两张图——这本身也是一种值得学习的工程实践:**复杂状态图可以按"阶段"拆分展示,只要在文字里说明两张图通过ESTABLISHED这个状态衔接**。

**建立阶段:**

```
+--------+   passive OPEN     +--------+
| CLOSED | -----------------> | LISTEN |
+--------+                    +--------+
    |                             |
    | active OPEN                 | RCV_SYN
    | (send SYN)                  | (send SYN+ACK)
    v                             v
+-----------+   RCV_SYN      +--------------+
| SYN_SENT  | -------------> | SYN_RECEIVED |
+-----------+  (send SYN+ACK)+--------------+
    |                             |
    | RCV_SYN_ACK                 | RCV_ACK
    | (send ACK)                  |
    v                             v
    +------------> +-------------+ <------------+
                    | ESTABLISHED |
                    +-------------+
```

**关闭阶段(从ESTABLISHED出发,分主动关闭方/被动关闭方两条支路,以及同时关闭支路):**

```

                    | ESTABLISHED |
                    +-------------+
        APP_CLOSE       |        |   RCV_FIN
      (send FIN)         |        |   (send ACK)
                v        v
    +------------+      +------------+
    | FIN_WAIT_1 |      | CLOSE_WAIT |
    +------------+      +------------+
     |      |                |
     |      | RCV_FIN        | APP_CLOSE
     |      | (send ACK)     | (send FIN)
RCV_ACK    v                v
     |  +---------+     +----------+
     |  | CLOSING |     | LAST_ACK |
     |  +---------+     +----------+
     v      |                |
+------------+   RCV_ACK      | RCV_ACK
| FIN_WAIT_2 |      |         |
+------------+      v         v
     |          +-----------+ +--------+
     | RCV_FIN  | TIME_WAIT | | CLOSED |
     | (send ACK)+-----------+ +--------+
     v                |
```

## Step 6: Python实现

完整代码见同目录下的 `01_tcp_fsm.py`。

**v1:Enum + match-case硬编码版**
用`Enum`定义11个状态和10个事件,单个类里用`match (state, event)`直接列出所有分支。这一版的价值在于"逐字对照RFC793状态图",每一个`case`都能直接映射到Step 4表格里的一行,适合第一遍读代码时验证自己对标准的理解是否有遗漏。缺点也很明显:11个状态×10个事件的组合空间很大,`match`语句会变得很长,而且"这台状态机到底支持哪些转移"这个问题,只能通过读完整个match体才能回答,没法只看数据就知道全貌。

**v2:Transition Table版(数据驱动)**
把转移规则整理成`dict[tuple[TCPState, TCPEvent], TCPState]`加一个动作说明,这份表格几乎可以逐行对照Step 4的Markdown表格——这正是"协议标准文档本身就是用状态表描述转移规则"和"代码用字典实现转移表"这两者高度同构的地方。新增一条RFC793里没覆盖到的边界转移,只需要往字典里加一行。

**v3:State Pattern版**
每个状态是一个类,自己知道"收到某个事件该去哪"。这一版特别适合体现CLOSE_WAIT和FIN_WAIT_2这两个"半关闭"状态的语义差异——因为语义差异明显,分别用类表达比放进同一张表格里更容易读出"这个状态到底允许做什么"(比如CLOSE_WAIT类可以有一个`can_send_data() -> True`的方法,FIN_WAIT_2类返回`False`,这种"状态自带能力查询"的写法是State Pattern相对Transition Table的一个优势)。

**v4:通用FSM框架**
复用Level 1~3课程里已经搭好的`State`/`Event`/`Transition`/`FSM`引擎结构,只需要提供TCP自己的状态枚举、事件枚举和转移表,就能直接跑起来。这一版用来验证"通用FSM框架"是否真的通用——如果TCP这种工业级、状态数量和转移规则都远超前面案例的协议也能直接套用同一套框架,说明这套抽象是合格的。

运行`python3 01_tcp_fsm.py`可以看到一次完整的"三次握手→数据传输→四次挥手(含同时关闭分支演示)"的模拟过程。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**
设想不用FSM,而是用一组布尔标志位描述连接状态:`syn_sent`、`syn_received`、`established`、`fin_sent`、`fin_received`、`fin_acked`……理论上要表达11种合法状态,至少需要4个独立标志位(2^4=16种组合),但这16种组合里只有11种是RFC793定义的合法状态,另外5种是"永远不该出现,一旦出现说明代码有bug"的非法组合(比如"fin_sent=True但syn_received=False"这种没握手完就直接发FIN的荒谬情况)。用FSM,非法组合从设计层面就不存在,因为状态本身是一个封闭的枚举,不是几个标志位的自由组合;用标志位,你必须在每处代码里手动防御这些非法组合,而且随着标志位增多,防御代码的复杂度是组合爆炸级别的。

**什么时候FSM反而是负担?**
如果只是写一个"发一个SYN,等ACK,超时就报错"的简单探测脚本(不需要处理被动打开、不需要处理半关闭、不需要处理同时关闭),那确实不需要把11状态的完整FSM搬过来——教学之外的很多"迷你TCP-like协议"(比如某些嵌入式设备上极简的私有握手协议)会主动裁剪掉自己用不到的状态和转移,这是合理的工程取舍,只要裁剪前先看清楚"我确实不会遇到这些边界场景",而不是图省事直接跳过。

**什么时候不应该使用FSM?**
如果你只是在应用层"使用"一个已经封装好的TCP socket(比如Python的`socket`模块、或者一个HTTP客户端库),你完全不需要在自己的代码里重新实现这11个状态——操作系统内核已经帮你维护好了。这也是本课要和Level 3第3课(应用层视角的TCP连接状态机)对照的原因:那一课站在"我是这个socket的使用者"的角度,只需要关心`CONNECTING → CONNECTED → CLOSING → CLOSED`这种粗粒度的自己代码可控的状态,不需要,也不应该,重新实现内核已经实现过的11状态机;本课站在"我要理解/实现协议本身"的角度,才需要这11个状态的完整语义。**同一个"TCP连接"这件事,在不同的抽象层次上,值得建模的状态数量是不同的**——这本身就是一个重要的FSM设计原则:状态机的粒度应该匹配你所在的抽象层,而不是无脑照抄下层协议的全部状态。

**协议标准文档几乎总是直接给出状态图和状态表,这一现象说明了什么?**
说明协议设计者本身就是用FSM语言在思考和交流协议行为的——状态图不是事后总结出来方便讲课用的教具,而是设计阶段用来"穷举所有场景、避免遗漏边界情况"的正式工具。这也解释了为什么"看到协议/系统规范文档,先找里面有没有状态图"是训练FSM识别直觉的一个很好的经验法则:规范的作者往往已经替你完成了Step 1~4的工作,你要做的是理解它、而不是重新发明它。

## Step 8: FSM思维总结

```
==========
FSM识别口诀(TCP篇)
==========
✓ 关闭一个双向通道不是瞬间动作,"全双工"往往意味着需要成对的半关闭状态
✓ 同一个事件(如收到ACK)在不同状态下走向完全不同的下一状态,是FSM存在的最强信号
✓ 某些状态是为了压缩/记录历史而存在的(CLOSING记录"同时关闭"这段历史)
✓ 某些状态是为了容忍网络的不确定性而存在的(TIME_WAIT不是业务逻辑,是网络工程妥协)
✓ 建模粒度要匹配你所在的抽象层——用的人和实现的人,该关心的状态数量并不一样
```

## Step 9: 迁移训练题

1. QUIC协议(运行在UDP之上、被HTTP/3使用)的连接建立和关闭也有自己的一套状态语义(比如它把握手和加密协商合并在更少的往返里),如果要你重新画一遍QUIC连接的FSM,你预期状态数量会比TCP多还是少?为什么?（提示:先想清楚QUIC试图解决TCP的哪些"慢"的问题,这会不会同时减少某些历史依赖）
2. TLS握手(ClientHello → ServerHello → ... → Finished)本质上是不是一个FSM?如果是,它的"半关闭"语义(TCP里的CLOSE_WAIT/FIN_WAIT_2)在TLS层面有没有类似的对应物(提示:TLS的`close_notify`)?
3. SCTP(流控制传输协议)同样有自己的关联(association)状态机,并且明确设计了"多宿主(multi-homing)"和"四次握手防止SYN洪泛"等TCP没有的特性。如果只从状态命名和转移表来看,你预期SCTP的状态机会比TCP更简单还是更复杂?列出你认为SCTP大概率会引入的、TCP没有的新状态或新事件。

## 今天真正学会的一句话

当一个"关闭"或"断开"动作本质上是在断开一个全双工/双向的通道时,不要把它想象成一个瞬间的开关,而要问自己"两个方向各自的关闭进度是否需要分开记录"——TCP用FIN_WAIT_2和CLOSE_WAIT这对状态告诉我们:真正复杂的从来不是"状态", 而是"状态背后到底在压缩记录哪一段历史"。
