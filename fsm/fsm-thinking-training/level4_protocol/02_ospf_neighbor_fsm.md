# Lesson 02: OSPF Neighbor FSM (Level 4 - 网络协议)

## Step 1: 是否适合FSM

逐条检查OSPF邻居关系管理这个问题的"FSM特征"。

- **是否存在有限状态?**
  是。RFC2328第10.1节直接定义了8个邻居状态:Down、Attempt、Init、2-Way、ExStart、Exchange、Loading、Full。每个状态代表"和某一个特定邻居之间的关系进展到了哪一步",数量固定。

- **是否依赖历史状态?**
  是。比如同样是"收到了对方的Hello报文",在Down状态下的含义是"邻居关系刚被发现",在Init状态下的含义是"对方也看到了我(双向通信确认)",这个区分本身就依赖"之前是不是已经确认过对方存在"这段历史。再比如ExStart之后能不能进入Exchange,依赖"数据库描述报文的主从关系是否协商成功"这段发生在ExStart期间的历史,不是凭空发生的。

- **是否由事件驱动?**
  是,事件既有报文到达(收到Hello、收到DBD报文、收到LSR/LSU/LSAck),也有内部判定结果(协商完成、交换完成、加载完成),还有定时器(不活跃计时器超时)。

- **是否同一个事件在不同状态行为不同?**
  是。"收到对方发来的Hello报文,且Hello里已经列出了我的Router ID"(这在OSPF里叫2-WayReceived)这件事,在Init状态下会推进到2-Way或ExStart(取决于是否需要建立邻接关系);但如果连接已经在Full状态,收到的普通Hello报文只是用来"续命"不活跃计时器,并不会触发任何状态跳转。

- **是否存在明确状态切换?**
  是,每一步进展(从"发现邻居"到"双向确认"到"主从协商"到"数据库同步"到"完全邻接")都有明确的触发条件和明确的边界。

**适合FSM: ★★★★★**

理由:和TCP一样,OSPF的邻居状态机也是RFC原文直接定义的正式规范内容,不是事后总结。更值得强调的一点是它揭示了一种和TCP不同的建模视角——**"每一个邻居关系,都是一台独立的状态机实例"**,这是本课要重点训练的直觉,下一节详细展开。

## Step 2: 发现状态

**引导性问题:**
- 一个路由器要和它的每一个邻居分别建立关系,那么"状态"应该挂在路由器本身,还是挂在"路由器-邻居"这一对关系上?
- 从"完全不知道对方存在"到"完全同步了链路状态数据库",中间必须经过哪些不可跳过的阶段?
- 为什么"发现对方存在"和"确认对方也发现了我"要分成两个不同的状态,而不是一步到位?
- ExStart、Exchange、Loading这三个和"同步数据库"相关的状态,为什么不能合并成一个"正在同步"状态?

**思考过程:**

先回答第一个问题,这是OSPF这一课最重要的建模洞察:**一台路由器可能同时连接着好几个邻居路由器(比如在一段以太网上,一台路由器可能同时和五六个邻居路由器建立关系)。"状态"如果只挂在路由器自己身上(比如一个全局变量`self.state`),就没办法同时表达"和邻居A已经Full,和邻居B还在ExStart"这种再正常不过的局面**。所以OSPF的设计里,每一个邻居关系(neighbor adjacency)都维护一台完全独立的状态机实例,路由器本身不是一台状态机,路由器是"一堆邻居状态机的容器"。这和TCP不一样吗?其实TCP也是这样——每一条TCP连接都是独立的状态机实例,只是TCP的"连接"概念本身就隐含了这一点,不需要特别强调;而OSPF因为经常在广播网络(以太网)上一次性面对多个邻居,这种"每个对象实例一台FSM"的建模思路会体现得格外明显,值得单独拎出来训练直觉。

再看具体状态是怎么被发现的:

1. **Down** —— 还没收到过这个邻居的任何Hello报文,这是默认起点(注意:这不代表"链路down了",而是"这台状态机还没和对方建立过任何联系"的初始态)。
2. **Attempt**(仅用于NBMA等需要手动配置邻居地址的网络类型)—— 已经主动尝试联系对方(定时发送Hello),但还没收到过回复。这个状态在最常见的广播网络(以太网,靠组播自动发现邻居)上通常不会经过,教学模型里会保留它但简化处理。
3. **Init** —— 收到了对方的Hello报文,但对方的Hello报文里列出的"我见过的邻居列表"还没有包含我的Router ID,说明这是"单向"的:我看到了对方,但不确定对方是否看到了我。
4. **2-Way** —— 收到对方的Hello报文,里面已经列出了我的Router ID,说明双向通信被确认。**关键问题来了:确认双向通信之后,是不是就该立刻开始同步数据库了?** 答案是不一定——OSPF为了控制广播网络上邻接关系的数量(N个路由器两两建邻接会产生O(N²)条邻接和大量冗余的LSA洪泛),引入了DR(指定路由器)/BDR(备份指定路由器)机制:一台路由器只需要和DR、BDR建立完整的邻接关系(继续往ExStart推进),和其他"路人"邻居保持在2-Way就够了(不需要同步数据库,只用于路由计算时确认拓扑)。**所以2-Way本身就是一个"故意停留、不一定继续推进"的稳定状态**,这是它和Init的本质区别:Init是"必然会继续判断"的过渡态,2-Way是"可能长期停留"的稳定态。
5. **ExStart** —— 决定要和这个邻居建立完整邻接关系了,开始协商"数据库描述报文交换时谁是主(Master)、谁是从(Slave)",以及初始的DD序列号。这一步存在的原因是:接下来Exchange阶段要可靠、有序地交换一大堆数据库描述报文,必须先确定一个类似"谁先发、谁应答"的主从关系,否则会出现两边同时抢着发送导致的混乱。
6. **Exchange** —— 双方按照ExStart协商好的主从关系,交换数据库描述(DBD)报文——注意,这里交换的只是"我有哪些LSA的摘要信息",不是完整的LSA内容,目的是让双方各自判断"对方有哪些我没有的LSA"。
7. **Loading** —— 双方各自根据上一步比对出的差异,通过链路状态请求(LSR)/链路状态更新(LSU)报文,把摘要指向的完整LSA内容实际拉取过来,补全自己的链路状态数据库。
8. **Full** —— 数据库已经完全同步,这个邻接关系正式建立完成,可以参与最短路径计算了。

**为什么ExStart/Exchange/Loading不能合并成一个"正在同步"状态?** 因为三者的失败/重试语义不同,而且这三个阶段各自等待的"完成信号"完全不同(ExStart等待主从协商成功;Exchange等待DBD序列号交换完毕且序列号不出现不匹配;Loading等待所有请求出去的LSA都收到了应答)。如果合并成一个状态,一旦同步中途出错(比如序列号不匹配SeqNumberMismatch),协议就没法精确表达"应该退回到哪一步重新开始"——RFC2328里明确规定,遇到序列号不匹配或收到非法的LSR,要退回ExStart重新协商主从关系,而不是退回Down从头开始,拆分成三个状态使这种"精确回退"成为可能。

**确定的状态清单:**

| 状态 | 说明 | 互斥性 | 持续性 |
|---|---|---|---|
| Down | 尚未与该邻居建立过任何联系 | 与其余状态互斥(针对同一个邻居实例) | 直到收到对方Hello或主动发起联系 |
| Attempt | (NBMA等网络类型)已主动尝试联系,尚无回应 | 互斥 | 直到收到Hello或重试超限回退Down |
| Init | 已收到对方Hello,但尚未确认双向通信 | 互斥 | 直到确认双向或不活跃计时器超时 |
| 2-Way | 双向通信已确认,可能长期停留(非DR/BDR邻居) | 互斥 | 直到决定建立完整邻接(选为DR/BDR相关)或超时 |
| ExStart | 正在协商DBD交换的主从关系与初始序列号 | 互斥 | 直到协商完成或序列号不匹配需重来 |
| Exchange | 正在交换数据库描述摘要 | 互斥 | 直到摘要交换完毕 |
| Loading | 正在按摘要差异拉取完整LSA内容 | 互斥 | 直到所有请求都收到应答 |
| Full | 数据库已完全同步,邻接关系正式生效 | 互斥 | 直到不活跃计时器超时或链路故障 |

8个状态两两互斥,且每一个都能清楚说出自己在"和这一个特定邻居"的关系进展中的确切含义。

## Step 3: 寻找事件

**引导性问题:**
- 是"收到了一个报文"本身重要,还是"这个报文里携带的信息内容"重要?
- 定时器在OSPF邻居管理里扮演什么角色?一共有几种?
- 状态机内部自己判断出来的结论(比如"主从协商完成了""所有LSA都拉取完了"),算不算一种事件?
- 收到一个格式错误或者不属于这个邻居的报文,应该怎么处理?

**分析过程:**

- 单纯"收到一个Hello报文"这件事本身并不足以驱动所有转移——关键要看Hello报文里的具体字段。比如"HelloReceived"这个事件的语义就是收到Hello本身(用于确认活着/重置不活跃计时器);而"2-WayReceived"是一个更精确的事件,专门表示"收到的Hello报文里已经包含我的Router ID",两者虽然都源自同一个Hello报文,但代表的信息粒度不同,必须拆成两个不同的事件,否则无法表达"Init到2-Way"这条关键转移。
- OSPF邻居FSM里有明确的**不活跃计时器(InactivityTimer)**——如果在规定的死亡间隔(RouterDeadInterval)内一直没收到对方任何Hello,判定邻居失联,直接退回Down。这是货真价实的"超时即事件",而且这个事件的转移目标非常统一:不管当前处于哪个状态(哪怕已经Full),一旦不活跃计时器到期,都直接掉回Down——这是一种"跨越所有状态的通用退化事件",在设计转移表时值得专门标注,而不是在每个状态里重复写一遍。
- **主从协商完成(NegotiationDone)**、**摘要交换完毕(ExchangeDone)**、**所有请求LSA都已收到(LoadingDone)**——这三个都不是直接从网络报文里"读出来"的原始信号,而是状态机内部逻辑对多个报文累积处理之后得出的"结论性事件"。这提示我们:**事件不一定是外部输入的原始信号,也可以是内部逻辑判断产生的"派生事件"**,只要这个判断结果确实会驱动状态跳转,它就应该被建模成一个事件,而不是悄悄地散落在某个报文处理函数的深处。
- **序列号不匹配(SeqNumberMismatch)** 和 **收到非法的链路状态请求(BadLSReq)** 是两个专门为异常路径定义的事件,它们的效果相同:退回ExStart重新开始主从协商。把这两种不同的错误原因统一映射到同一个"重来"目标状态,但仍然保留两个不同的事件名字,是为了在日志/调试时能区分"到底是哪种异常"导致的重试,这是协议设计上"事件粒度服务于可观测性,而不只是服务于转移逻辑"的一个例子。
- **1-WayReceived**(收到对方Hello,但列表里已经没有我的Router ID了,说明之前建立的双向确认失效了)——这个事件会把状态从任何"2-Way及以上"的状态直接打回Init,同样是一种"跨状态的统一退化事件"。
- 不属于这个邻居实例的报文(比如报文里的邻居标识和这台状态机绑定的邻居不符)根本不会被路由到这台状态机上处理,这属于"多台独立状态机之间的分发逻辑",不是某一台状态机内部要考虑的事件,应该忽略,不建模进转移表。

区分总结:
- **动作(不改变邻居状态)**:收到Full状态下的常规Hello只刷新计时器、周期性发送自己的Hello。
- **真正触发转移的事件**:`HelloReceived`、`Start`(用于Attempt路径)、`TwoWayReceived`、`NegotiationDone`、`ExchangeDone`、`LoadingDone`、`AdjOK`(决定是否要与2-Way邻居升级为完整邻接)、`SeqNumberMismatch`、`BadLSReq`、`OneWayReceived`、`InactivityTimer`、`KillNbr`(链路故障等强制中断)。
- **应忽略的输入**:不属于当前邻居实例的报文、格式错误但可安全丢弃的报文(生产实现会记录日志,教学模型简化为忽略)。

**确定的事件清单:**

| 事件 | 说明 |
|---|---|
| HelloReceived | 收到对方Hello报文(用于Down/Attempt阶段的发现,以及日常刷新计时器) |
| TwoWayReceived | 收到的Hello报文中已列出本机Router ID,双向通信确认 |
| AdjOK | 判定需要与该2-Way邻居建立完整邻接(如对方是DR/BDR) |
| NegotiationDone | ExStart阶段主从关系与初始序列号协商完成 |
| ExchangeDone | 数据库描述摘要交换完毕 |
| LoadingDone | 所有请求的LSA均已收到 |
| SeqNumberMismatch | DBD序列号不匹配,需退回ExStart重新协商 |
| BadLSReq | 收到无法满足的链路状态请求,需退回ExStart重新协商 |
| OneWayReceived | 收到的Hello报文中已不再列出本机Router ID,双向确认失效 |
| InactivityTimer | 死亡间隔内未收到对方任何Hello,判定失联 |
| KillNbr | 链路故障等原因强制中断该邻居关系 |

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| Down | HelloReceived | Init | 记录邻居存在,启动/重置不活跃计时器 |
| Down | Start (NBMA) | Attempt | 主动定时发送Hello尝试联系 |
| Attempt | HelloReceived | Init | 转入常规发现流程 |
| Init | TwoWayReceived (无需建立完整邻接,如非DR/BDR的以太网邻居) | 2-Way | 记录双向通信确认 |
| Init | TwoWayReceived (需要建立完整邻接) | ExStart | 开始主从协商 |
| 2-Way | AdjOK | ExStart | 决定升级为完整邻接,开始主从协商 |
| ExStart | NegotiationDone | Exchange | 主从关系确定,开始交换DBD摘要 |
| Exchange | ExchangeDone (无需再拉取LSA) | Full | 数据库已一致,邻接建立完成 |
| Exchange | ExchangeDone (存在差异需拉取) | Loading | 发送LSR请求缺失的LSA |
| Exchange | SeqNumberMismatch / BadLSReq | ExStart | 退回重新协商主从关系 |
| Loading | LoadingDone | Full | 所有LSA已同步,邻接建立完成 |
| Loading | SeqNumberMismatch / BadLSReq | ExStart | 退回重新协商主从关系 |
| (2-Way及以上任意状态) | OneWayReceived | Init | 双向确认失效,退回单向已知 |
| (任意状态) | InactivityTimer | Down | 判定失联,清空已同步的数据库摘要状态 |
| (任意状态) | KillNbr | Down | 链路故障等强制中断 |

表中省略了RFC2328里针对NBMA网络DR/BDR选举细节的大量边界条件,教学目的是覆盖"发现→双向确认→按需建立完整邻接→数据库同步三段式(ExStart/Exchange/Loading)→Full"这条主干路径,以及超时和序列号异常这两类关键的失效路径。

## Step 6: Python实现

完整代码见同目录下的 `02_ospf_neighbor_fsm.py`。

**v1:Enum + match-case版**
每台邻居状态机对应一个`OSPFNeighbor`实例,`handle`方法内部用`match`处理。这一版重点是先把"每个邻居一个实例"这个建模决定落到代码结构上——构造函数需要传入`neighbor_router_id`,提醒自己这不是全局状态。

**v2:Transition Table版**
把状态转移整理成字典,额外增加一个"通用退化事件表"(`InactivityTimer`、`KillNbr`对任意状态都生效),查表时先检查通用事件、再查具体状态转移,这是对"某些事件与当前状态无关、全局生效"这种情况的一种典型数据驱动处理方式。

**v3:State Pattern版**
用来体现Exchange/Loading阶段"到底该不该继续升级邻接"这类每个状态内部略有差异的逻辑判断(比如是否需要拉取LSA)。

**v4:通用FSM框架 + 多实例管理**
除了复用通用FSM引擎外,这一版额外演示"一台路由器同时维护多个邻居FSM实例"的管理容器(`OSPFRouter`持有一个`dict[router_id, GenericFSM]`),用代码直接印证Step 2里"路由器不是一台状态机,是一堆邻居状态机的容器"这句话。

运行`python3 02_ospf_neighbor_fsm.py`可以看到一台路由器同时和两个邻居交互、其中一个推进到Full、另一个仍停在2-Way的过程。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**
如果不用FSM,而是用一堆"是否已双向确认""是否已协商主从""是否已交换完摘要""是否已拉取完LSA"这些布尔标志位去描述一个邻居的进展,一旦这台路由器同时维护几十个邻居(在大型二层网络里很常见),每个邻居都要单独维护一整套标志位组合,代码里到处都是"如果邻居A的xxx标志位为真且yyy标志位为假"这种判断,极易在"到底该用哪个邻居的哪个标志位"上出错。用FSM,每个邻居是一个独立、干净的状态机实例,状态本身就是"当前进展"的唯一真相来源(single source of truth),不需要多个标志位互相佐证。

**"每个对象实例一台FSM"这种建模思路,什么时候特别重要?**
当你的系统里存在"多个相同类型、但进展互相独立的关系/连接/资源"时——比如OSPF的每个邻居、TCP的每条连接、后面Level 5会讲到的Kubernetes里每个Pod的状态——这时候"状态"天然应该挂在"关系/连接/资源"这个对象上,而不是挂在"管理这些对象的中心组件"上。一个常见的设计错误是把这类状态做成中心组件上的一个全局字典或者一堆并行数组,而不是让每个对象自己持有一个完整的状态机实例——后者在代码组织和并发安全上通常都更清晰。

**什么时候FSM反而是负担?**
如果你的系统里"关系"的数量永远是1(比如一个只会跟固定的一个上级节点通信的简单心跳客户端),那么"每个对象一台FSM"这个设计原则就用不上,退化成普通的单实例FSM即可,不需要额外设计"多实例管理容器"这一层。

**什么时候不应该使用FSM?**
如果只是要写一个"定时检测某个IP是否可达"的简单探测脚本(纯粹的成功/失败,没有中间协商阶段),不需要引入ExStart/Exchange/Loading这种精细分级的状态,一个"UP/DOWN"的二值状态或者干脆一个布尔量就够了——不要仅仅因为"这是网络协议场景"就机械套用一整套复杂邻居FSM。

**协议标准文档几乎总是直接给出状态图和状态表,这一现象说明了什么?**
和TCP一样,OSPF的RFC同样在文本里直接给出邻居状态转移图。这进一步印证了Step 1总结的经验法则:当你面对一份协议/系统规范,发现它本身就在用状态图和状态表描述行为时,几乎可以确定这个问题域"天然适合FSM",你的任务是准确理解规范定义的状态语义,而不是自己另起炉灶设计一套不同的状态划分。

## Step 8: FSM思维总结

```
==========
FSM识别口诀(OSPF邻居篇)
==========
✓ 当系统里存在"多个同类但互相独立的关系"时,状态应该挂在"每一个关系实例"上,而不是挂在管理者身上
✓ 某些状态是"故意停留、不一定继续推进"的稳定态(2-Way),不要误以为所有中间状态都必然会自动推进到终态
✓ 内部逻辑判断出的结论(协商完成、交换完毕)也可以被建模成事件,不必是原始外部信号
✓ 存在"跨越所有状态的统一退化事件"(超时、强制中断)时,用专门的通用规则表达,而不是在每个状态里重复写
```

## Step 9: 迁移训练题

1. IS-IS(另一种链路状态路由协议,和OSPF地位类似但细节不同)也维护邻居邻接关系,并且同样区分"广播网络"和"点到点网络"两种不同的邻接建立方式。如果你要为IS-IS的邻接状态机建模,你预期"每个对象实例一台FSM"这条原则依然成立吗?点到点网络下是否还需要类似DR/BDR选举导致的"故意停留在2-Way"这种设计?
2. 一个分布式系统里,主节点(leader)需要和每个从节点(follower)维护独立的"心跳健康状态"(比如Raft协议里leader对每个follower都单独维护nextIndex/matchIndex等复制进度)。这是不是"每个对象实例一台FSM"思路的另一个应用场景?如果是,状态该怎么划分?
3. 蓝牙(Bluetooth)设备的配对/连接过程中,一台主设备(central)可能同时和多个外围设备(peripheral)处于不同的连接阶段(有的还在扫描发现、有的在配对认证、有的已连接完成)。套用本课的建模思路,你会怎么划分"每个外围设备连接"的状态?这和OSPF邻居FSM的相似之处和不同之处分别是什么?

## 今天真正学会的一句话

当系统里出现"我要同时和好几个同类对象分别维持关系,而且每一段关系的进展互不影响"时,不要试图用一个全局状态或一堆并行标志位去凑合,而要问自己"能不能让每一个对象实例自己持有一台完整的状态机"——OSPF邻居FSM给出的答案永远是肯定的。
