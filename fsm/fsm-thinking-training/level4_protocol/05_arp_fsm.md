# Lesson 05: ARP (Level 4 - 网络协议) —— 一个"该不该用FSM"的反例

## Step 1: 是否适合FSM

前四课(TCP、OSPF、BGP、DHCP)都以"★★★★★"收尾,容易让人产生一种错觉:"只要是网络协议,就一定该用重量级FSM"。这一课专门用ARP(地址解析协议,RFC826)来打破这种错觉——逐条检查下来会发现,ARP在两条最关键的判据上明显偏弱。

- **是否存在有限状态?**
  勉强算是。如果一定要给"某个IP地址的缓存条目"划分状态,大概可以划出"没有缓存(NO_ENTRY)""已发出请求、等待应答(PENDING)""已解析、缓存有效(RESOLVED)"这三种。数量确实有限,但请注意——这几乎是能想到的**最少**的、任何"请求-应答-缓存"模式都会自然具备的阶段划分,称不上是ARP协议本身设计出的精巧状态集合。

- **是否依赖历史状态?**——**这是ARP和前四课最本质的区别,答案是基本不依赖。**
  回忆TCP的CLOSING状态:它的存在是为了记录"双方几乎同时发起了关闭"这段历史,如果不记录这段历史,协议就无法正确处理后续报文。再回忆DHCP的INIT-REBOOT:它记录的是"本地是否存在未过期的历史租约缓存"。而ARP呢?**决定"现在该做什么"的唯一依据,只是"当前是否有一条有效的缓存条目",不需要知道这条缓存条目是第一次请求得到的、还是重试第三次才得到的、还是曾经失效过又重新解析出来的**。换句话说,ARP缓存条目的"未来行为"只取决于"现在是否命中缓存"这一个瞬时判断,不需要压缩更早的历史进这个状态里——这正是"依赖历史"这条判据里最弱的一种情况:表面上有历史(时间在流逝、请求发生过),但状态本身不需要靠"记住"这段历史来决定后续行为。

- **是否由事件驱动?**
  是,但驱动方式非常单薄:发起请求(因为要发数据但没有缓存)、收到应答、请求超时、缓存过期。四种驱动加起来,情节比TCP、OSPF、BGP、DHCP任何一课都简单得多。

- **是否同一个事件在不同状态行为不同?**——**这是第二条明显偏弱的判据。**
  回忆TCP:"收到ACK"这一件事在SYN_RECEIVED、FIN_WAIT_1、CLOSING、LAST_ACK四个状态下分别导致四种完全不同的后果。而ARP呢?"收到一个ARP应答报文",在PENDING状态下的反应是"写入缓存,转到RESOLVED";在RESOLVED状态下收到一个针对同一IP的应答(比如对方主动发的Gratuitous ARP刷新)的反应也不过是"刷新缓存内容,仍然停留在RESOLVED"——**两种情况下的行为几乎是同一件事(写入/刷新缓存映射),没有出现"同一事件走向截然不同的处理逻辑"这种情况**。这和TCP里"收到ACK"能导向四个完全不同状态的情形有本质区别。

- **是否存在明确状态切换?**
  存在,但切换的判断条件极其简单(有没有缓存、请求有没有超时),不涉及需要仔细辨析的复杂边界情况。

**适合FSM: ★★☆☆☆(轻量级/部分适合)**

理由需要分两层说清楚,这也是这一课最重要的结论:

1. **就RFC826定义的ARP协议本身而言**,它的核心行为可以完全用一个"缓存字典 + 每条记录的时间戳"来实现:查表命中就直接用,不命中就广播请求、收到应答后写入表并记录时间戳,定期清理超过一定时长没有刷新的记录。这套逻辑用一个`dict[IP, (MAC, timestamp)]`配合一次简单的时间比较就能完整表达,不需要显式定义状态类、转移表或者State Pattern这类专门为"复杂状态语义"准备的重型工具。**这正是本课要训练的核心识别能力:当"下一步做什么"只取决于一个简单的布尔判断(有没有命中缓存)而不需要区分好几种不同来路、不同历史的情形时,FSM提供的"结构化"价值是有限的,轻量级的缓存结构完全够用,甚至更直接、更容易读懂。**
2. **但如果把视野扩大到生产系统的真实实现**,情况会变得微妙——Linux内核的邻居子系统(不管是IPv4的ARP还是IPv6的邻居发现)实际上确实实现了一套叫NUD(Neighbor Unreachability Detection,邻居不可达检测)的状态机,包含INCOMPLETE、REACHABLE、STALE、DELAY、PROBE、FAILED等好几个状态,用来优化"什么时候才值得重新发起一次探测确认对方还活着",避免缓存"假阳性地长期认为一个早已离线的邻居仍然可达"。**这里的关键教训是:NUD这套复杂状态机,不是ARP协议(RFC826)本身要求的,而是操作系统实现者为了性能和可靠性优化,主动选择叠加上去的工程复杂度**。这也解释了本课星级判断要分层——协议规范层面ARP很轻量,但如果你的目标是写一个生产级别、需要精细控制"重新探测节奏"的邻居管理模块,那确实可能值得引入接近NUD的复杂状态机;如果只是想正确实现"地址解析"这个基本功能,不需要这么做。

## Step 2: 发现状态

**引导性问题:**
- 一个IP地址的地址解析结果,在任意时刻只可能处于哪几种"客观情况"?
- "已经发过请求,正在等回复"和"从来没查询过这个地址"是不是同一回事,需不需要区分?
- 重试次数(比如已经重发了2次请求)算不算一个独立的状态?
- 一条缓存记录"新鲜"和"过期"之间,是否存在需要单独建模的中间过渡态?

**思考过程:**

先列出候选:

1. **完全没有缓存** —— 候选,合格。这是最初始的情况,查表未命中。
2. **已发出请求、正在等待应答** —— 候选,合格。这段时间不能算作"没有缓存"(已经在处理中,不该重复发起新请求),也不能算作"已解析"(还没有可用的映射),必须单独区分。
3. **已解析、缓存有效** —— 候选,合格。这是正常工作状态,查表命中直接返回。
4. **重试次数(第1次请求/第2次请求/第3次请求)** —— 容易被误当成独立状态,但仔细想:重试次数变化时,"客观行为"并没有发生本质变化——不管是第1次还是第3次重试,系统的行为都是"再发一次请求、继续等",唯一的区别是"还能不能再试"这个即将到达的边界。这和交通灯课程里"倒计时数字不是独立状态,是状态的属性"是同一类判断——重试次数应该作为PENDING状态内部的一个计数属性,而不是拆分成PENDING_1/PENDING_2/PENDING_3三个状态。
5. **缓存"新鲜"与"过期"之间的中间态** —— 有些工程实现(比如前面提到的NUD)确实会引入STALE(过期但还没验证失效)、DELAY、PROBE这些中间态,用来实现"先假设还能用,同时后台悄悄验证"的优化策略。但对于教学基线模型(对应RFC826本身的语义)而言,这种精细分级不是必需的——一条缓存记录要么还在有效期内可以直接使用,要么已经过期需要重新查询,二值判断已经足够描述ARP协议规定的行为,中间态属于"锦上添花的工程优化",本课基线模型不纳入(但会在Step 9迁移题里让读者对比思考)。

**确定的状态清单(基线模型,对应RFC826核心语义):**

| 状态 | 说明 | 互斥性 | 持续性 |
|---|---|---|---|
| NO_ENTRY | 没有该IP的缓存映射 | 与其余状态互斥 | 直到需要向该IP发送数据触发请求 |
| PENDING | 已广播ARP请求,等待应答(内部携带重试计数,不单独拆状态) | 互斥 | 直到收到应答或重试耗尽 |
| RESOLVED | 已获得有效的IP-MAC映射,可直接使用 | 互斥 | 直到缓存有效期到期 |

只有3个状态,比TCP的11个、OSPF的8个、BGP的6个、DHCP的8个都要少得多——这个数量上的直观差距,本身就是"轻量级"判断的一个佐证。

## Step 3: 寻找事件

**引导性问题:**
- 发送ARP请求这个动作,是被哪个真正的"事件"触发的?
- 收到一个ARP应答报文,如果这个应答对应的IP我根本没有发起过请求(比如主动的Gratuitous ARP),该怎么处理?
- 请求超时和缓存过期,是不是同一种性质的"计时器事件"?它们的作用范围一样吗?
- 一次请求失败要不要立刻放弃,还是应该重试几次?重试次数用完之后呢?

**分析过程:**

- **需要向某个IP发送数据,但本地没有缓存**——这是触发"发起解析请求"的真正事件,发送ARP请求本身是这个事件之后执行的动作。
- **收到ARP应答**——需要按"是否与本地某条PENDING记录对应"区分处理:如果对应,正常写入缓存并转入RESOLVED;如果不对应(比如收到的是一次没有人请求过的Gratuitous ARP,通常用于该主机宣告自己的地址,或者是检测IP冲突),按照惯例,收到这类"未经请求的通告"如果本地已有该IP的缓存记录,大多数实现会选择刷新它(避免使用陈旧映射);如果本地根本没有缓存这个IP,通常直接忽略,不会凭空创建一条新记录(避免被伪造的Gratuitous ARP污染缓存)——这是一个典型的"应忽略的输入"案例,值得专门指出。
- **请求超时**——如果规定时间内没有收到应答,是否要立刻放弃?不是,通常会有一个较小的重试次数上限(比如重试3次),重试次数属于PENDING状态内部的计数属性,不产生新的状态,只有"重试耗尽仍未收到应答"才会真正触发"放弃解析、回到NO_ENTRY(并可能向上层报告目标不可达)"这个状态转移。**请求超时(未耗尽重试)和请求超时(已耗尽重试)是同一个原始信号在附加了"计数判断"这个简单条件之后,分裂成的两种不同后果**——这提示我们:有些"事件"其实是"原始信号 + 一个简单计数器阈值判断"的组合,不需要为计数过程本身单独建模状态。
- **缓存过期**——这是另一种独立的计时器事件,和"请求超时"性质不同:请求超时发生在PENDING阶段(还没拿到结果),缓存过期发生在RESOLVED阶段(已经拿到结果、但结果的有效期到了),两者触发的动作也不同(前者是"放弃这次尝试",后者是"这条已经生效过的映射不再被信任,需要重新验证")。

区分总结:
- **动作(不改变状态)**:PENDING状态下的重试计数递增并重发请求(只要还没到重试上限)。
- **真正触发转移的事件**:`NeedResolve`(需要解析但无缓存)、`ReceivedReplyMatchingPending`、`RetriesExhausted`、`CacheAgeout`。
- **应忽略的输入**:与任何PENDING记录不匹配、且本地也没有该IP缓存的Gratuitous ARP通告(基线模型选择忽略,不主动创建缓存条目)。

**确定的事件清单:**

| 事件 | 说明 |
|---|---|
| NeedResolve | 需要向某IP发送数据但无缓存,触发广播ARP请求 |
| ReceivedReplyMatchingPending | 收到与当前PENDING记录匹配的ARP应答 |
| RetriesExhausted | 重试次数用尽仍未收到应答 |
| CacheAgeout | 已解析的缓存记录到达有效期上限 |

事件数量同样是本课最少的一课——这也从侧面印证Step 1的判断。

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| NO_ENTRY | NeedResolve | PENDING | 广播ARP请求,重试计数置0 |
| PENDING | ReceivedReplyMatchingPending | RESOLVED | 写入IP-MAC映射,记录缓存有效期起始时间 |
| PENDING | (未超时,重试计数<上限) | PENDING | 重发ARP请求,重试计数+1(自环,不算独立转移) |
| PENDING | RetriesExhausted | NO_ENTRY | 放弃本次解析,可向上层报告目标不可达 |
| RESOLVED | CacheAgeout | NO_ENTRY | 缓存失效,清除映射 |
| RESOLVED | (收到匹配的Gratuitous ARP刷新) | RESOLVED | 刷新映射内容与有效期(自环) |

这张表只有4行"真正的转移"(其余是自环),这本身也是"轻量级"的一个数字佐证——对比TCP转移表的20多行、OSPF的14行、BGP的18行、DHCP的16行,ARP的转移表短得多,进一步验证了较低的星级评价不是主观臆断,而是有具体的复杂度对比支撑的。

## Step 6: Python实现

完整代码见同目录下的 `05_arp_fsm.py`。**这一课的Python实现刻意保留了v1~v4四个版本,是为了让读者亲眼对比"轻量级问题硬套重型实现"会是什么样子**——尤其是v3(State Pattern)在只有3个状态、且状态间差异极小的场景下,会显得非常笨重。

**v1:Enum + match-case版**
和前几课一样,直接映射转移表。由于状态和事件都很少,这个版本本身已经足够清晰。

**v2:Transition Table版**
同样直接映射Step 4表格。这里能明显感觉到:相比TCP/OSPF/BGP/DHCP那几课,搭建这张表所花的"心智力气"小了一个数量级——这正是"该不该上转移表"这件事本身也有成本、需要与问题复杂度相匹配的直接体验。

**v3:State Pattern版**
特意实现出来,用于对比。读者会发现:三个状态类之间的差异极小(RESOLVED类和NO_ENTRY类除了返回的下一状态几乎没有任何独特的行为需要封装),为了这么小的差异去创建三个独立的类、一个Protocol接口,是明显的"为了用模式而用模式"。**这一版存在的教学意义,恰恰是让读者直观感受到Step 7要讨论的"什么时候FSM是负担"。**

**v4:轻量级替代方案 —— 直接用缓存字典+时间戳**
这是这一课真正想推荐的写法:不定义任何`State`枚举、不写转移表,只用一个`dict[str, ARPCacheEntry]`(`ARPCacheEntry`是一个携带MAC地址和过期时间的`dataclass`)加一个查询函数,查询时先看缓存是否命中且未过期,未命中或过期则模拟发起解析。这一版故意不套用"通用FSM框架",用来对比"什么时候FSM框架不是必须品,一个恰当的数据结构就能优雅解决问题"。

运行`python3 05_arp_fsm.py`可以同时看到v1~v3的FSM版本和v4的轻量级版本得到完全一致的行为结果,以此直观证明:**多花的代码量并没有换来实际能力上的提升**。

## Step 7: 复杂度分析

**为什么这一次,"轻量方案"比FSM更好?**
ARP缓存管理的核心诉求就是"命中就用、不命中就查、查到就存、过期就丢"——这本质上是一个**缓存(cache)问题**,而不是一个需要精细区分"进展到了协商流程的第几步"的**流程编排问题**。缓存问题的天然工具是"键值存储 + 过期时间戳",这个工具本身已经能优雅表达"有效/无效"这个二元状态,再叠加一层显式的FSM结构,只是把同一件事用更冗长的方式重新说了一遍,没有带来新的表达能力。

**"轻量级判断"应该看什么具体信号?**
对比本课和前四课,可以总结出几个具体、可操作的信号(而不是"感觉简单"这种模糊判断):
1. 转移表的"真正转移"行数很少(本课只有4行),大部分候选转移是自环;
2. 状态之间的行为差异很小,State Pattern实现出来后,各个状态类的方法体几乎一样;
3. 不存在需要"记住走过哪条路径"的状态(不需要靠状态名字压缩历史,像CLOSING、Connect/Active、INIT-REBOOT那样);
4. 同一个事件在不同状态下的处理逻辑本质相同(都是"写入/刷新缓存"),没有出现真正意义上的分支爆炸。

**NUD(生产系统的复杂化)什么时候值得引入?**
当"缓存过期后简单粗暴地重新发起完整请求"这个策略在工程上不够好时——比如在数据中心内网,如果每次缓存刚好过期都要重新走一次完整的ARP广播请求-应答,会在流量较大时产生不必要的广播风暴和短暂的解析延迟。NUD通过引入STALE(先假设还能用,同时后台重新验证)等中间态,把"缓存到期"这件事从"硬性阻塞"变成"软性异步刷新",这是用状态机的复杂度换取更好的性能和用户体验的一次典型权衡——但这权衡只有在流量规模、性能要求达到一定门槛之后才划算,不是所有场景都需要。

**这一课想让读者练成的核心判断力是什么?**
不要看到"网络协议"四个字就默认套用重型FSM。判断标准永远是回到Step 1的五条特征本身,而不是问题的"领域标签"(网络/业务/游戏)。ARP这一课证明:哪怕是网络协议,只要状态数量少、历史依赖弱、事件行为差异小,轻量级的数据结构完全可能是更好的答案。

## Step 8: FSM思维总结

```
==========
FSM识别口诀(ARP反例篇)
==========
✓ 当"下一步做什么"只取决于一个简单的布尔命中判断,而非需要区分好几种不同来路的历史时,别急着上FSM
✓ 转移表里如果大部分是自环、真正的跨状态转移寥寥无几,这是"轻量级"的强烈信号
✓ 同一事件在不同状态下的处理逻辑本质相同(没有分支爆炸),说明状态的区分度不够,不必强行拆分
✓ "这是网络协议"不等于"该用重型FSM"——判断依据永远是特征本身,不是问题所在的领域标签
✓ 生产系统里出现的额外复杂度(如NUD),要分清是协议规范要求的,还是工程优化主动引入的
```

## Step 9: 迁移训练题

1. DNS客户端的解析缓存(先查本地缓存,未命中则向DNS服务器查询,查到后按TTL缓存一段时间)在结构上和ARP高度相似。请你按本课的分析框架过一遍五条判据,判断DNS解析缓存是否也应该归入"轻量级/不太需要复杂FSM"这一类?如果DNS解析器还要处理"递归查询中间经过多级服务器转发、CNAME链式跳转、查询失败后切换到备用DNS服务器重试"这些情况,你的判断会不会改变?
2. IPv6的邻居发现协议(NDP,RFC4861)针对和ARP几乎同样的"地址解析"问题,但在标准文档正文里就直接定义了NUD状态机(INCOMPLETE、REACHABLE、STALE、DELAY、PROBE),这和IPv4的ARP(RFC826完全没有定义这类状态机,是各厂商自行选择要不要在实现里叠加)形成了鲜明对比。请你查阅或推测一下:IPv6设计者为什么会认为这套复杂状态机的价值大到值得写进协议标准正文,而不是像ARP一样留给具体实现自行决定?
3. 一个简单的进程内LRU缓存(Least Recently Used Cache),同样具备"命中直接用、不命中触发加载、加载完写入、超过容量或过期后淘汰"这样的行为模式。请你判断:这类通用缓存组件的核心逻辑,是否也应该归为本课总结的"轻量级、不建议上FSM"这一类?如果这个缓存还需要支持"后台异步刷新(stale-while-revalidate)"这种模式,判断会不会发生变化?

## 今天真正学会的一句话

不要因为一个问题贴着"网络协议"的标签,就默认它需要一台像TCP那样复杂的状态机——真正决定要不要上FSM的,永远是"状态数量、历史依赖程度、同一事件在不同状态下的行为差异"这几条具体特征本身;ARP告诉我们,当这几条特征都很弱的时候,一个诚实的缓存字典加一个时间戳,比一台精心设计的状态机更清楚,也更好维护。
