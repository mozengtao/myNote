# Lesson 03: 自动门 (Level 1 - 生活场景)

本课的核心目标: 理解"超时事件"——很多人第一次学FSM时,会默认"事件"都是外部输入(按了按钮、传感器测到东西),但真实系统里有一大类关键事件是**由时间流逝本身触发的,没有任何外部actor做了任何事**。自动门在无人经过一段时间后自动关闭,就是这种"定时器驱动的自主转移"最直观的例子。

## Step 1: 是否适合FSM

- **是否存在有限状态?**
  是。自动门在物理上只有"关闭""正在打开""已打开""正在关闭"这几种模式,不存在第五种。

- **是否依赖历史状态?**
  依赖程度较浅,和交通灯类似:下一步该怎么走基本只取决于"现在处于哪个模式",不需要携带复杂的历史数据(不像电梯需要记住方向和队列)。

- **是否由事件驱动?**
  是,但这正是本课要重点拆解的地方——自动门被**两类性质完全不同的事件**驱动:
  1. **外部输入事件**: 传感器检测到有人靠近或经过(`PERSON_DETECTED`)、检测到关门过程中有障碍物(`OBSTRUCTION_DETECTED`)。这类事件由"外面发生了什么"触发。
  2. **内部时间事件**: 门开着超过一定时长、始终没有人经过,定时器到时,门应该自动关闭(`CLOSE_TIMER_EXPIRED`)。这类事件不是任何人或任何传感器"做了什么"触发的,而是"什么都没发生、但时间到了"触发的——这是一种很容易被初学者忽略的事件来源。
  如果只考虑第一类事件,会漏掉整个"自动关门"的核心逻辑;必须把"时间流逝到某个阈值"本身当作系统里的一等事件来源,这正是本课要建立的直觉。

- **是否同一个事件在不同状态行为不同?**
  是。`PERSON_DETECTED` 在CLOSED状态下的反应是"开始开门";在OPEN状态下的反应是"重置关门倒计时,继续保持开着"(不是重新开门,因为已经开着);在CLOSING状态下的反应是"安全优先,立刻反转方向重新打开"。同一个事件名字,三种完全不同的反应。

- **是否存在明确状态切换?**
  是。开、关、正在开、正在关,四种模式之间的切换都是电机限位开关触发的离散信号,边界清晰。

**适合FSM: ★★★★★**

原因:自动门具备FSM的全部基础特征,并且是学习"超时事件如何融入状态机"的最佳入门案例——它的状态少、历史依赖浅,能让学习者把全部注意力集中在"如何把定时器也当成一等事件来源"这一个核心概念上,不会被电梯那种复杂的历史依赖分散注意力。

## Step 2: 发现状态

**引导性问题:**
- 自动门在完成一次"开门-通行-关门"的过程中,经历了哪几个明显不同的阶段?
- 哪些阶段是电机正在运动、哪些阶段是电机静止?
- 哪些阶段会一直保持,直到某个明确事件发生才结束?
- 有没有什么"看起来像是需要单独建模的状态",但其实只是某个已有状态的一种特殊情形?

**思考过程:**

先列出候选项:

1. "门完全关闭,静止" —— 候选,CLOSED。
2. "门正在打开,电机运转中" —— 候选,OPENING。
3. "门完全打开,静止,等待有人通行或超时" —— 候选,OPEN。
4. "门正在关闭,电机运转中" —— 候选,CLOSING。
5. "门开合的角度(比如开到37%)" —— 容易被误认为需要精细建模,但和交通灯的倒计时数字一样,这是一个连续变化的物理量,不是离散模式,应该是数据(电机位置传感器的读数),不是状态。
6. "关门倒计时还剩几秒" —— 同上,是数据,不是状态。
7. "检测到障碍物,反转方向重新打开" —— 这是本课最值得深入讨论的候选项。第一反应可能是"应该单独建一个叫BLOCKED或OBSTRUCTED的状态",但仔细看:检测到障碍物之后,门的实际物理行为是什么?——电机反转,朝"打开"方向运动,这跟OPENING状态的物理行为**完全一样**(电机驱动门往开的方向走)。既然对外表现的行为(电机转动方向、门的运动趋势)是一样的,就没有必要为"因为什么原因触发了开门"这件事单独建一个状态——原因是"事件",不是"状态"。所以"检测到障碍物"应该被处理成一个**从CLOSING指向OPENING的转移事件**,而不是一个新状态。这是本课刻意设计的辨析点:**不要把"触发转移的原因"误当成"需要新增的状态"**,如果转移之后的行为和某个已有状态完全一样,就应该复用已有状态,而不是为每一种"原因"都新建一个状态。
8. "门是否损坏/卡住无法运动" —— 真实存在的故障场景,但超出本课基础模型范围(可以作为扩展练习,加一个FAULT状态)。

**确定的状态清单:**

| 状态 | 说明 | 互斥性 | 持续性 |
|---|---|---|---|
| CLOSED | 门完全关闭,电机静止 | 与其余三个状态互斥 | 持续到检测到有人 |
| OPENING | 门正在打开,电机朝开方向运转 | 同上 | 持续到电机限位开关报告"已完全打开" |
| OPEN | 门完全打开,电机静止,关门倒计时在运行 | 同上 | 持续到倒计时到时,且中途会因检测到人而被重置 |
| CLOSING | 门正在关闭,电机朝关方向运转,障碍物传感器保持激活 | 同上 | 持续到电机限位开关报告"已完全关闭",且中途会因检测到障碍物/有人而被打断 |

## Step 3: 寻找事件

**引导性问题:**
- 有哪些事件是"外面发生了什么"触发的(传感器/外部输入)?
- 有哪些事件根本不是外部输入触发的,而是"时间到了"触发的?
- 一个事件在某个状态下发生,是应该真正改变状态,还是只是"续期"当前状态的持续时间?
- 有哪些信号在某些状态下出现是完全不合理的(传感器异常/逻辑bug),应该被当成异常处理?

**分析过程:**

- "传感器检测到有人靠近/经过" —— 外部输入事件,称为 `PERSON_DETECTED`。它的效果因当前状态而不同:CLOSED时是真正的转移(开始开门);OPEN时只是"续期"(重置倒计时,不改变状态本身);CLOSING时是安全触发的转移(反转为开门)。
- "电机限位开关报告已完全打开" —— 外部输入事件(来自电机自身的传感器,而不是"人"),称为 `FULLY_OPEN`,是OPENING结束的唯一合法方式。
- "电机限位开关报告已完全关闭" —— 同理,`FULLY_CLOSED`,是CLOSING正常结束的方式。
- "关门倒计时到时,期间始终没有检测到人" —— **这是本课的核心事件**,称为 `CLOSE_TIMER_EXPIRED`。它不是任何传感器测到了什么东西,而是"OPEN状态维持的时间超过了预设阈值,且没有被任何PERSON_DETECTED重置过"。要正确实现这个事件,系统必须在**进入OPEN状态时启动一个定时器**,在**每次PERSON_DETECTED发生时重置这个定时器**,并在**定时器真正到时、且当前仍处于OPEN状态时**,才产生这个事件——这意味着"启动定时器""取消/重置定时器"本身也是需要在转移的Action里显式管理的操作,而不是理所当然自动发生的。这正是初学者最容易漏掉的一点:**超时事件需要状态机主动管理定时器的生命周期,而不只是被动等待一个"事件"从天而降**。
- "关门过程中检测到障碍物" —— 外部输入事件,称为 `OBSTRUCTION_DETECTED`,只在CLOSING状态下有意义,效果是安全优先反转为开门。
- "门已经CLOSED,却收到CLOSE_TIMER_EXPIRED" —— 这在正常工况下不应该发生(说明进入CLOSED时没有正确取消上一个定时器,是一个bug信号),应作为**异常输入**记录并忽略。
- "门是CLOSED或OPENING时,却收到OBSTRUCTION_DETECTED" —— 障碍物传感器理论上只在CLOSING时会被启用,其余状态下收到这个信号也是异常,应记录并忽略。

**区分总结:**
- **动作(不改变状态)**:OPEN状态下的 `PERSON_DETECTED`(只重置倒计时,不切换状态)、OPENING状态下再次收到 `PERSON_DETECTED`(门已经在开,无需额外处理)。
- **真正触发转移的事件**:CLOSED下的 `PERSON_DETECTED`、OPENING下的 `FULLY_OPEN`、OPEN下的 `CLOSE_TIMER_EXPIRED`(超时事件)、CLOSING下的 `FULLY_CLOSED` / `OBSTRUCTION_DETECTED` / `PERSON_DETECTED`。
- **应忽略/报错的异常输入**:CLOSED状态下收到 `CLOSE_TIMER_EXPIRED`(定时器管理bug)、非CLOSING状态下收到 `OBSTRUCTION_DETECTED`。

**确定的事件清单:**

| 事件 | 来源 | 说明 |
|---|---|---|
| PERSON_DETECTED | 外部输入(人体/红外传感器) | 检测到有人靠近或在门区域内 |
| FULLY_OPEN | 外部输入(电机限位开关) | 门已运动到完全打开位置 |
| FULLY_CLOSED | 外部输入(电机限位开关) | 门已运动到完全关闭位置 |
| OBSTRUCTION_DETECTED | 外部输入(安全传感器) | 关门过程中检测到障碍物 |
| CLOSE_TIMER_EXPIRED | **内部定时器(超时事件)** | OPEN状态持续超过预设时长,且未被重置 |

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| CLOSED | PERSON_DETECTED | OPENING | 启动开门电机 |
| OPENING | FULLY_OPEN | OPEN | 停止电机,**启动关门倒计时定时器** |
| OPENING | PERSON_DETECTED | OPENING(保持,自环) | 忽略,门已经在开,无需额外动作 |
| OPEN | PERSON_DETECTED | OPEN(保持,自环) | **重置(续期)关门倒计时定时器**,门继续保持打开 |
| OPEN | CLOSE_TIMER_EXPIRED | CLOSING | 启动关门电机 —— **本课核心转移:纯由时间驱动,没有任何外部输入** |
| CLOSING | FULLY_CLOSED | CLOSED | 停止电机,**确保关门倒计时定时器已取消** |
| CLOSING | OBSTRUCTION_DETECTED | OPENING | 立即反转电机方向,重新开门(安全优先) |
| CLOSING | PERSON_DETECTED | OPENING | 视为等同于检测到障碍物,反转重新开门 |
| CLOSED | CLOSE_TIMER_EXPIRED(异常) | 保持CLOSED | 记录异常日志(定时器未被正确取消,属于bug信号),忽略 |
| CLOSED / OPENING / OPEN | OBSTRUCTION_DETECTED(异常) | 保持原状态 | 记录异常日志,忽略 |

请特别注意表中两处加粗的"定时器管理"动作——它们不是"顺便做一下"的小事,而是这张表能不能正确工作的关键前提:如果进入OPEN时忘记启动定时器,门永远不会自动关闭;如果PERSON_DETECTED时忘记重置定时器,门可能会在有人还在通行时突然关闭;如果离开CLOSED进入OPENING时,没能确保旧定时器被取消,就会出现表中最后一行描述的异常信号。

## Step 6: Python实现

完整代码见同目录下的 `03_auto_door.py`。这一课在实现上要重点解决一个问题:如何在代码里让"定时器到时"真正表现成一个"事件",而不是一个被动的时间流逝。四版实现都用一个简化技巧——用一个显式的 `tick(seconds)` 方法模拟时间前进,内部倒计时归零时,由状态机自己产生 `CLOSE_TIMER_EXPIRED` 事件并处理它,这样"时间驱动"和"外部输入驱动"在代码结构上被统一成同一种"事件处理"入口,而不是两套不同的机制。

**v1:简单版(Enum + match-case,倒计时是实例属性)**
状态用Enum表示,倒计时秒数是一个实例属性,每次 `tick()` 调用时手动减少,减到0时手动触发"超时逻辑"。这一版能清楚看到"进入OPEN时要不要启动倒计时""PERSON_DETECTED时要不要重置倒计时"这些定时器管理逻辑,和状态切换逻辑混在同一段代码里,读起来需要格外小心才能确认"这里到底有没有正确管理定时器"。

**v2:Transition Table版(把"定时器管理"作为标准Action的一部分)**
转移表中的Action函数被统一设计成"可以启动定时器、可以取消定时器、也可以什么都不做",这样"定时器该不该被启动/取消"这件事变成了表里显式写出来的一部分,而不是分散在各个方法里"顺便"处理的细节。相比v1,这一版能让人一眼看出:哪些转移会启动定时器、哪些会取消、哪些完全不涉及定时器。

**v3:State Pattern版(每个状态自己管理"进入/离开时的定时器责任")**
给每个状态类加上 `on_enter(context)` 和 `on_exit(context)` 两个生命周期钩子:OPEN状态的 `on_enter` 负责启动定时器,`on_exit` 负责确保定时器被取消(即使是因为收到CLOSE_TIMER_EXPIRED本身而离开,也统一走这个出口逻辑,避免遗漏)。这种"状态自己负责进入和离开时该做什么收尾工作"的写法,是State Pattern处理"资源生命周期管理类状态机"(定时器、连接、锁)时的标准做法,能显著降低"忘记取消定时器"这类bug的概率。

**v4:通用FSM框架片段(升级版:支持on_enter/on_exit钩子和内部事件)**
在Lesson 02框架基础上,给 `FSM` 引擎增加进入/离开状态时的钩子调用,并允许Action内部再次调用 `fsm.fire(...)` 产生"内部事件"(比如定时器到时后自己往自己身上发一个事件),这样"超时驱动的自主转移"和"外部输入驱动的转移"可以复用同一套 `fire()` 入口,状态机本身不需要关心事件的来源是"外部传感器"还是"内部时钟"。这一版框架的演化动机和Lesson 02一样:遇到新的案例特征(这里是"需要管理定时器生命周期"),发现现有框架表达不出来,于是有针对性地扩展框架,而不是重新发明一套。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**
自动门如果用if-else写,最容易犯的错误就是"定时器管理逻辑"散落在好几个地方:开门完成的地方要记得启动定时器,检测到人的地方要记得重置定时器,门关闭完成的地方要记得取消定时器——如果这几处逻辑分散在不同的函数里,很容易在某次改动时漏掉一处(比如新增了一个"紧急开门"按钮,却忘记在对应分支里取消定时器),导致门在不该关的时候自动关闭。FSM把"所有转移以及每个转移附带的定时器操作"集中在一张表或几个状态类里,复查"定时器管理是否完整"这件事,只需要检查这一张表,而不用去搜整个代码库里所有"可能影响门状态"的地方。

**什么情况下FSM反而是负担?**
如果这扇"自动门"其实只是一个"按一下开关就开、再按一下就关"的手动推拉门电动辅助装置,没有超时自动关闭、没有障碍物检测,只有两个状态(开/关)和一个事件(按开关),那么用得上的可能只是一个布尔变量和一次取反操作,FSM的表结构和生命周期钩子反而是不必要的复杂度。

**什么时候不应该使用FSM?**
通用判断标准:
1. 系统里根本不存在"需要持续一段时间、可能被中途打断/续期"的阶段,所有转移都是瞬时的、一次性的;
2. 定时器/超时逻辑极其简单(比如只有一个固定延迟,没有"续期"或"被打断"的需求),用一次性的 `sleep` 或单个 `Timer` 回调就能解决,不需要为此专门建模状态;
3. 系统对"时间"的处理只是日志记录或统计用途,不参与决定"下一步该做什么"。

本课的自动门明显不落在这个边界内:它同时存在"可被打断的运动阶段(CLOSING可以被安全信号打断)"和"可被续期的等待阶段(OPEN的倒计时可以被反复重置)",这两种需求单靠零散的定时器回调很难保证正确性和可读性,正是FSM(尤其是带生命周期钩子的版本)最擅长处理的场景。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 事件不一定来自"外部输入"——"时间到了、且没有被打断"本身就是一等事件
✓ 一旦出现"超时事件"，就要检查:这个状态的定时器在哪里启动、
  在哪些情况下会被重置、在哪些情况下必须被取消，三者缺一都是隐患
✓ 转移发生的原因(比如"检测到障碍物")不一定要变成新状态——
  如果转移之后的行为和已有状态完全相同，应该复用已有状态
✓ 同一个事件在"可被打断的运动状态"里(如CLOSING)和"稳定等待状态"里
  (如OPEN)往往有完全不同的处理策略(打断 vs 续期)
→ 应该考虑FSM
```

## Step 9: 迁移训练题

1. 手机屏幕的自动锁屏:无操作超过设定时长会自动锁屏,但期间任何触摸或按键都会重新计时,来电时还会有特殊行为——这个场景该怎么判断?
2. 一个自动浇花系统:土壤湿度低于阈值时开始浇水,浇水持续固定时长后停止,但如果水箱在浇水过程中检测到没水了需要提前停止并报警——这个场景里,哪些事件是"外部输入"、哪些是"超时"、哪些是"异常打断"?
3. 一个网页/APP的"验证码倒计时重新发送"按钮:发送后60秒内按钮禁用并显示倒计时,60秒后恢复可点击;如果用户在倒计时期间关闭页面又重新打开,倒计时该怎么处理——这是否依然适合用FSM,以及"时间"在这里应该怎么建模?

## 今天真正学会的一句话

看到"过一段时间没人理它,它自己会做一件事"这种描述时,要立刻意识到这是一个"超时事件",必须像对待外部输入一样认真设计它的触发条件、以及"什么情况下这个倒计时要被重置或取消"——遗漏定时器的生命周期管理,是这一类FSM最容易出错、也最难在事后调试出来的地方。
