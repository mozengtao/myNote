# Lesson 01: 交通灯 (Level 1 - 生活场景)

## Step 1: 是否适合FSM

先别急着写代码,逐条检查交通灯这个案例的"FSM特征"。

- **是否存在有限状态?**
  是。交通灯只有"红灯亮""黄灯亮""绿灯亮"三种可见输出,不存在第四种颜色,也不存在"红黄同时亮且持续"这种稳定态(黄灯闪烁提示除外,那是另一套逻辑)。有限、可枚举,这是第一个信号。

- **是否依赖历史状态?**
  是,但依赖的方式很"浅"。交通灯下一步该亮什么颜色,只取决于"现在亮的是什么颜色",不需要知道"三个周期之前是什么颜色"、也不需要知道"已经等了几个乘客"。这种"只依赖上一个状态、不依赖更早历史"的情况,正是最适合用简单FSM(而不是要额外携带一堆历史变量)建模的信号。

- **是否由事件驱动?**
  是,但驱动方式比较单一:几乎全部由"定时器到时"这一种事件驱动(红灯计时结束、绿灯计时结束、黄灯计时结束)。如果这套系统还要接入"行人按钮请求""传感器检测到车流量"这些外部事件,事件种类会变多,但目前这一课先看最基础版本:固定周期切换。

- **是否同一个事件在不同状态行为不同?**
  是。"计时结束"这个事件在红灯状态下的反应是"切到绿灯",在绿灯状态下的反应是"切到黄灯",在黄灯状态下的反应是"切到红灯"。同一个事件名字,但转移目标完全不同,取决于当前处于哪个状态——这正是FSM最典型的特征之一。

- **是否存在明确状态切换?**
  是。红→绿→黄→红,每一次切换都是瞬间的、离散的,不存在"红灯正在变成绿灯"这种中间模糊态。切换点非常清晰,适合用状态图描述。

**适合FSM: ★★★★★**

原因:交通灯几乎是FSM教学案例里的"标准模板"——状态数量少且互斥、转移只依赖当前状态和一个简单事件(计时到)、没有需要额外携带的复杂上下文。用if-else写这三个状态的循环切换当然也能工作,但一旦要加入"行人请求""夜间模式(黄灯闪烁)""故障检测(全红/全灭)"等扩展,FSM的结构优势会迅速显现。这一课我们先在最干净的场景里建立直觉,后面几课再逐步加复杂度。

## Step 2: 发现状态

**引导性问题:**
- 当前系统在物理上会经历哪几个"阶段"?
- 哪些阶段是互斥的(不能同时出现)?
- 哪些阶段具有"持续性"(会在一段时间内保持不变,而不是瞬间发生)?
- 哪些阶段会一直保持,直到某个特定事件发生才改变?
- 有没有什么"看起来是状态,其实只是状态的属性"?

**思考过程:**

先把所有可能被当成"状态"的候选项都摆出来,再一个个筛:

1. "红灯亮" —— 候选。持续一段时间(比如30秒),期间没有别的灯亮,互斥,合格。
2. "绿灯亮" —— 候选。同上,合格。
3. "黄灯亮" —— 候选。持续时间短(比如3秒),但仍然是一段"持续期",合格。
4. "倒计时数字(比如还剩15秒)" —— 容易被误认为状态,但其实不是。倒计时数字每秒都在变,如果把每一个数字都当成一个独立状态,状态数会爆炸成无限个。倒计时应该是"红灯状态"内部的一个计数属性(state的数据,不是state本身),而不是单独的状态。
5. "车辆是否在路口" —— 也容易被误认为状态,但这是"环境信息",不是交通灯本身的状态。这一课的交通灯是固定周期的,不感应车流,所以这个信息暂时不参与建模。
6. "灯是否损坏" —— 这是个真实存在的场景(故障态),但在本课的"固定周期交通灯"范围内暂不考虑,如果要扩展可以加一个"Fault"状态,但那是下一步的加强练习,不属于本课基础模型。

筛选标准:一个候选是不是"真正的状态",要看它是否满足——(a) 在这个阶段系统的对外行为是稳定不变的,(b) 该阶段会持续到某个明确事件发生才结束,(c) 和其他候选阶段互斥。倒计时数字不满足(a)(每秒都不同,行为一直在变),车辆信息在本模型里不影响灯的输出行为,所以都被排除。

**确定的状态清单:**

| 状态 | 说明 | 互斥性 | 持续性 |
|---|---|---|---|
| RED | 红灯亮,禁止通行 | 与GREEN、YELLOW互斥,任意时刻只有一个灯亮 | 持续到红灯计时结束(定时器到时事件) |
| GREEN | 绿灯亮,允许通行 | 同上 | 持续到绿灯计时结束 |
| YELLOW | 黄灯亮,准备停止 | 同上 | 持续到黄灯计时结束 |

三个状态两两互斥、都具有持续性、都会一直保持到"计时结束"这个事件发生,完全符合状态的定义。

## Step 3: 寻找事件

**引导性问题:**
- 什么事情真正导致灯的颜色发生了改变?
- 有没有一些输入看起来像事件,但其实只是"动作"或"提示",并不改变灯的颜色?
- 有没有一些输入应该被直接忽略?
- 一个事件在系统里可能有几种不同的来源,但对状态机来说是否可以归纳成同一个逻辑事件?

**分析过程:**

- "红灯定时器到时" —— 真正的事件。它是"红灯→绿灯"转移的直接触发者。
- "绿灯定时器到时" —— 真正的事件。触发"绿灯→黄灯"。
- "黄灯定时器到时" —— 真正的事件。触发"黄灯→红灯"。
- "行人按下请求按钮" —— 这是一个"动作输入",在本课的固定周期模型里,交通灯不响应行人按钮(那属于感应式信号灯的扩展场景),所以这个输入应该被**忽略**,不改变状态,也不产生任何转移。
- "维护人员手动打开控制箱查看状态" —— 这是纯粹的"观察动作",不影响灯的运行,不是事件,甚至不需要建模。
- "系统上电初始化" —— 这不是"转移事件",而是"进入初始状态"的动作,严格来说属于FSM的"初始化"环节而非某个状态内部的转移事件,但我们会在代码里把它处理成"构造时进入RED状态"。
- 三个"定时器到时"看起来是三个不同的事件(RED_TIMER_EXPIRED、GREEN_TIMER_EXPIRED、YELLOW_TIMER_EXPIRED),但仔细想:它们的"事件语义"其实是同一个抽象概念——"当前阶段的持续时间已到"。为了让状态图更清晰、转移表更统一,我们可以统一抽象成一个事件 `TIMER_EXPIRED`,由状态机根据"当前处于哪个状态"来决定下一步去哪——这正好呼应了Step 1里"同一事件在不同状态下行为不同"的判断。

区分总结:
- **动作(不改变状态)**:维护人员查看状态、系统日志记录当前灯色。
- **真正触发转移的事件**:`TIMER_EXPIRED`(定时器到时)。
- **应忽略的无效输入**:行人按钮请求(在本课基础模型中)、任何未定义的信号。

**确定的事件清单:**

| 事件 | 说明 |
|---|---|
| TIMER_EXPIRED | 当前颜色对应的持续时间计时结束 |

是的,基础版本只有一个事件——这恰恰说明这个案例足够"干净",适合作为FSM入门的第一课。

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| RED | TIMER_EXPIRED | GREEN | 关闭红灯,点亮绿灯,启动绿灯计时器(设定绿灯持续时长) |
| GREEN | TIMER_EXPIRED | YELLOW | 关闭绿灯,点亮黄灯,启动黄灯计时器(设定黄灯持续时长) |
| YELLOW | TIMER_EXPIRED | RED | 关闭黄灯,点亮红灯,启动红灯计时器(设定红灯持续时长) |
| RED / GREEN / YELLOW | 任何未定义信号(如行人按钮) | 保持原状态 | 忽略输入,不做任何动作(在日志中可选记录一条"忽略"提示) |

非法输入的处理策略是"保持原状态并忽略",而不是报错或抛异常——因为交通灯是安全关键系统,遇到未知输入时"什么都不做、维持当前安全状态"远比"报错崩溃"更合理。这本身也是一种需要在设计阶段就明确下来的策略选择。

## Step 5: ASCII状态图

```
        +-----------------------+
        |                       |
        v                       |
     +-------+  TIMER_EXPIRED  +-------+
     |  RED  | --------------> | GREEN |
     +-------+                 +-------+
        ^                          |
        |                          | TIMER_EXPIRED
        |                          v
        |   TIMER_EXPIRED     +--------+
        +-------------------- | YELLOW |
                              +--------+
```

三个状态首尾相连,形成一个单向循环:RED -> GREEN -> YELLOW -> RED,循环往复,没有分支,没有回头路。这种"单向环"结构在状态图里非常常见,也是最容易验证正确性的一类结构(只要保证环上每一步转移都对,整个系统就不会跑出预期之外的状态)。

## Step 6: Python实现

完整代码见同目录下的 `01_traffic_light.py`,这里说明每一版的设计动机。

**v1:简单版(Enum + match-case硬编码)**
用 `Enum` 定义三个状态,在一个类里用 `match` 语句直接写"如果当前是RED,收到TIMER_EXPIRED就切到GREEN"这种硬编码逻辑。这是最直觉的写法,优点是直白、容易读懂第一遍;缺点是转移规则和"怎么执行动作"的代码混在一起,状态一多、事件一多,`match` 分支会迅速膨胀,而且没有办法在不读代码的情况下"看一眼就知道全部转移规则"。

**v2:Transition Table版(数据驱动)**
把"转移规则"从代码逻辑里抽出来,变成一个字典:`{(当前状态, 事件): (下一状态, 动作函数)}`。这样做的好处是:
- 转移规则变成了数据,可以被打印、被单独测试、甚至可以从配置文件加载,不需要改代码逻辑本身;
- 新增一个转移,只需要往字典里加一行,不需要改动`match`分支的结构;
- 非法输入的处理("找不到对应的转移")变成了统一的"字典查不到key"逻辑,而不是要在每个分支末尾都写一遍"else忽略"。

相比v1,v2把"决定去哪"和"怎么执行"两件事情拆开了,这是从"写死的流程"到"可配置的规则"的关键一步。

**v3:State Pattern版(每个状态是一个类)**
把RED、GREEN、YELLOW分别实现成三个类,每个类自己实现"收到TIMER_EXPIRED该怎么办、该进入哪个状态"。这种模式在"每个状态的行为差异很大、每个状态内部逻辑复杂(比如某个状态要额外做传感器读取、要做异常处理)"时特别有用,因为每个状态类只需要关心自己的逻辑,新增状态不会影响别的状态类。对交通灯这么简单的场景其实有点"过度设计"(三个状态的逻辑几乎一样,只是切换目标不同),但依然值得实现一遍,用来对比感受"什么时候这种模式才真正划算"。

**v4:通用FSM框架片段**
抽象出 `State`(状态标识)、`Event`(事件标识)、`Transition`(一条转移规则)、`FSM`(通用状态机引擎,负责接收事件、查表、执行动作、切换状态)几个基础构件,任何案例只要定义好自己的状态枚举、事件枚举和转移表,就可以直接复用这个引擎,不需要重新实现"怎么根据(state, event)找下一个state"这套逻辑。这一版的价值在于——当你发现自己在第二、第三个案例里又要重写一遍"根据当前状态和事件查表、执行动作、切换状态"的样板代码时,就应该把这部分抽出来变成框架,而不是每次复制粘贴。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**
在交通灯这个案例里,如果全部用if-else写,大概会是这样:
```python
if current_color == "red" and timer_expired:
    current_color = "green"
elif current_color == "green" and timer_expired:
    current_color = "yellow"
elif current_color == "yellow" and timer_expired:
    current_color = "red"
```
看起来也不复杂,对吧?但问题在于——一旦加入"行人按钮在红灯期间可以提前结束绿灯等待""夜间模式改为黄灯闪烁""检测到红外故障时进入全红保护态"这些真实需求,if-else的判断条件会变成"多个布尔变量的组合判断"(`if current_color == "red" and timer_expired and not pedestrian_waiting and not is_night_mode and not fault_detected`),条件组合会指数级增长,而且"当前到底允许从哪个状态转移到哪个状态"这件事完全隐藏在一堆嵌套的if里,没人能一眼看出全貌。FSM(尤其是转移表)把"允许的转移"显式列出来,新增一种模式时只需要加表项,而不用去梳理所有已有条件判断的组合是否冲突。

**什么情况下FSM反而是负担?**
如果这个交通灯永远只有"红→绿→黄→红"这一种固定循环,不会有任何扩展需求,那写一个只有4行的if-elif循环反而比"定义Enum、写转移表、写FSM引擎"要轻量得多——为3个状态、1个事件的场景搭一整套State Pattern类或者通用框架,属于典型的"为了用设计模式而用设计模式"。本课后面实现的v3、v4,更多是为了训练"识别什么时候该用什么复杂度的实现",而不是说这个场景真的需要v4。

**什么时候不应该使用FSM?**
通用判断标准:
1. 状态之间的转移逻辑可以用一两个简单的布尔表达式说清楚,不涉及"取决于历史"或"同一事件不同状态不同反应"的复杂度;
2. 状态本身没有清晰的边界(比如"进度条从0%到100%"这种连续变化的量,不适合硬拆成有限个离散状态);
3. 团队里没人需要长期维护这段逻辑、也不会有后续扩展(一次性脚本)。

本课的交通灯案例本身"接近但没有跨过"这个边界:三个状态、一个事件、单向循环,如果永远不扩展,确实是if-else也能轻松胜任的规模;但现实中的交通灯几乎必然会遇到"加感应""加故障保护""加特殊模式"这些扩展需求,一旦扩展,FSM的结构优势立刻体现出来。这也是为什么这一课依然选择用FSM来讲——它是"刚好在边界上,但大概率会被推过边界"的典型例子。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 系统只有几种"稳定、互斥"的输出模式(红/绿/黄),而不是连续变化的量
✓ 下一步该怎么变,只取决于"现在是什么状态",不需要翻查更早的历史
✓ 同一个事件(计时到)在不同状态下会走向完全不同的下一状态
✓ 一旦引入新模式(感应、故障、特殊时段),if-else的条件组合会迅速失控
→ 应该考虑FSM
```

## 今天真正学会的一句话

当你发现"下一步该做什么,只取决于现在处于哪个阶段,而这些阶段两两互斥、且都会一直保持到某个明确事件发生才改变"时,这就是在向你发出"用FSM建模"的信号——哪怕现在用if-else也能写对,FSM能让"所有允许的转移"变成一张一眼可查的表,而不是散落在条件判断里的隐藏规则。
