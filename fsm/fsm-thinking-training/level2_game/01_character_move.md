# Lesson 01: 人物移动 (Level 2 - 小游戏)

## Step 1: 是否适合FSM

先别急着建模,逐条对照FSM的判断特征,看这个"人物移动"问题到底有没有资格用状态机描述。

- **是否存在有限状态?**
  是。一个2D/3D平台游戏角色在移动系统里,肉眼可数的"姿态"是有限的:站立不动、走、跑、上升(跳跃中)、下降(下落中)。不存在"无穷多种移动姿态"——即使加上蹲下、翻滚,也仍然是有限枚举,不会随时间无限增长。这满足"有限状态"的最基本要求。

- **是否依赖历史状态?**
  是,而且这是本案例最容易被忽视的一点。举例:玩家松开跳跃键后角色开始下落,此时"是否允许再跳一次"这件事,不能只看当前输入,必须知道"我是从Jump状态掉下来的,还是从平台边缘走下来的(没有主动跳跃)"——这决定了是否要给一次"二段跳"机会。同样,"落地之后应该进入Idle还是Walk还是Run",不看当前有没有按方向键就无法确定,而这本质上是"当前状态"(Falling)与"当前输入"共同决定下一状态,不是简单的输入到动作的映射。这就是历史状态在起作用:**下一步该做什么,取决于"我现在在哪个状态",不是只看这一帧的按键。**

- **是否由事件驱动?**
  是。真正驱动状态变化的是"事件"而不是"每帧都在变化的连续量"。按下方向键、松开方向键、按下跳跃键、到达跳跃顶点、落地——这些都是可以被明确检测到的、离散的时间点,天然是事件,不是每帧都在缓慢漂移的数值。

- **是否同一个事件在不同状态行为不同?**
  是,这是最强的信号。"按下跳跃键"这个同一个输入事件:
  - 在 `Idle` / `Walk` / `Run`(都在地面上)状态下 → 触发起跳,进入 `Jump`。
  - 在 `Jump` / `Fall`(已经在空中,且本案例不设二段跳)状态下 → 被直接忽略,什么也不发生。

  同一个物理按键事件,根据"当前处于哪个状态",产生了完全不同的结果(转移 vs 忽略)。如果不用状态机,你只能写一堆 `if 在地面上 and 按下跳跃键` 这样散落各处的条件判断,状态机则把"当前在哪个状态"作为一等公民,天然解决了这个问题。

- **是否存在明确状态切换?**
  是。角色的移动姿态之间不是渐变模糊的——"站立→行走"有明确的临界点(方向键第一次被按下),"行走→奔跑"有明确的临界点(加速键按下的那一帧),"跳跃→下落"有明确的临界点(垂直速度从正变负,即到达抛体顶点),"下落→落地"有明确的碰撞检测事件。这些切换点都能被精确地指出"发生在哪一帧",不是连续渗透的。

**适合FSM: ★★★★★**

原因:人物移动是FSM教学里最经典的案例之一,五条特征全部满足,而且第4条(同一事件在不同状态下行为不同——跳跃键在地面/空中含义不同)体现得非常干净,没有任何模糊地带。唯一需要提醒的是:移动**速度**、**朝向**、**位置坐标**这些是连续数值(数据),不是状态本身,不要把"数据"和"状态"混在一起——这正是Step 2要重点厘清的。

## Step 2: 发现状态

先带着这些引导性问题去看这个系统:

- 当前系统有哪些"阶段"?角色在任意时刻处于哪种"姿态"?
- 哪些阶段是互斥的(不可能同时成立)?
- 哪些阶段不能同时存在(比如不可能同时"站立"又"奔跑")?
- 哪些阶段具有"持续性"(会一直保持,直到某个事件把它打破,而不是这一帧算完就消失)?
- 哪些阶段会一直持续到下一个事件到来,而不是自动在下一帧变化?

### 思考过程:把"可能被误认为状态"的东西先摆出来

在真正列状态清单之前,先把容易和"状态"搞混的候选项拿出来逐一审判:

1. **移动方向(向左/向右/向前/向后)**——这是**数据**,不是状态。角色朝哪个方向移动,只影响位置/朝向这些连续数值的计算方式,不会让角色进入一种"不同性质"的行为模式。"向左走"和"向右走"在状态机层面是同一个状态(`Walking`),只是内部存的方向数据不同。如果给每个方向都建一个状态(`WalkingLeft`、`WalkingRight`……),转移表会毫无必要地膨胀,而且左右互换根本不该触发"状态切换"的语义(不需要 `enter`/`exit` 那种仪式性的进入退出逻辑)。

2. **移动速度(当前速度值)**——同样是**数据**。速度是一个随时间连续变化、由物理引擎(加速度、摩擦力)驱动的量,不是离散的"阶段"。把速度当状态,你会发现状态数量趋近于无穷(1.0m/s、1.1m/s、1.2m/s……),这是典型的"想把连续量硬塞进离散状态"的误区。

3. **是否在地面上(is_grounded)**——这是一个**布尔标志位,但它和状态高度耦合,值得单独讨论**。乍看之下它像是独立于移动状态之外的另一个维度,但仔细想:`is_grounded=True` 时角色只可能是 `Idle`/`Walk`/`Run` 之一,`is_grounded=False` 时只可能是 `Jump`/`Fall` 之一——也就是说,`is_grounded` 完全可以由"当前处于哪个状态"反推出来,它不是一个需要独立维护的正交变量,而是状态集合的一个**衍生属性**。所以最终设计里,不需要单独的 `is_grounded` 字段,用 `state in {JUMP, FALL}` 就能判断是否在空中。这是一个典型的"看起来像状态之外的额外维度,实际上是状态的函数"的陷阱。

4. **朝向(面朝左/面朝右)**——纯**视觉/渲染层数据**(用于决定贴图是否水平翻转),和移动逻辑的状态机完全无关,不参与任何转移判断,不需要建模进这台状态机。

5. **"正在下落还是正在上升"这两者是否要合并成一个 `Airborne` 状态?**——这是一个需要做设计取舍的问题,而不是有唯一正确答案。如果游戏逻辑里"上升阶段"和"下降阶段"的行为完全一样(比如都允许空中位移控制、都不允许二次跳跃),合并成一个状态是可以的,会更简单。但本案例特意保留两个独立状态(`Jump`/`Fall`),因为:
   - 二者的**触发方式不同**(`Jump` 由主动按键触发,`Fall` 可能由"没有跳跃、直接从平台边缘走出"这种被动方式触发,即没有对应的 `Jump` 阶段)。
   - 播放的**动画不同**,如果只有一个 `Airborne` 状态,还得在状态内部用速度符号去判断该播哪个动画,这其实是把"状态转移逻辑"重新用 if-else 藏回状态内部,违背了引入FSM的初衷。
   - 因此拆成两个独立状态,是"同一个阶段该拆细到什么颗粒度"的一次典型判断——**颗粒度取决于:这两个阶段在触发条件、允许的转移、外部可观察行为(动画/音效)上是否有本质区别**,只要有一项不同,就值得拆。

### 确定的状态清单

| 状态 | 说明 | 互斥性 | 持续性 |
|------|------|--------|--------|
| `Idle` | 站立不动,在地面上,当前没有移动输入 | 与其余4个状态互斥,同一时刻只能处于其一 | 会一直保持,直到方向键按下、跳跃键按下、或脚下地面消失 |
| `Walking` | 在地面上,按住方向键,未按加速键 | 同上 | 保持到方向键松开(→Idle)、加速键按下(→Running)、跳跃键按下(→Jump)、或地面消失(→Fall) |
| `Running` | 在地面上,按住方向键且按住加速键 | 同上 | 保持到加速键松开(→Walking)、方向键松开(→Idle)、跳跃键按下(→Jump)、或地面消失(→Fall) |
| `Jumping` | 主动起跳后、垂直速度为正(仍在上升)的空中阶段 | 同上 | 保持到到达抛体顶点/垂直速度转负(→Falling),期间跳跃键再按下会被忽略(不支持二段跳) |
| `Falling` | 垂直速度为负(下降中)的空中阶段,可能来自 `Jumping` 顶点之后,也可能来自地面消失时的直接坠落 | 同上 | 保持到检测到落地碰撞(→Idle/Walking/Running,取决于落地瞬间是否仍按着方向键) |

五个状态互斥且穷尽——任意时刻角色必然恰好处于其中一个,不存在"既不是Idle又不是别的"的空白态,也不存在两个状态同时成立的情况。这正是判断"状态清单是否设计完整"的一个简单自检法:**互斥 + 穷尽**。

## Step 3: 寻找事件

先带着这些引导性问题去看输入和世界的变化:

- 什么事情导致状态改变?
- 哪些输入只是"动作"(执行了某个效果,但不改变角色所处的阶段)?
- 哪些输入真正改变了状态?
- 哪些输入应该被忽略(不产生任何效果)?
- 有没有"不是玩家按键、但确实是事件"的东西(比如物理碰撞检测的结果)?

### 分析过程

先把候选输入/信号列出来,然后分类:

| 候选输入/信号 | 分类 | 理由 |
|---------------|------|------|
| 按下方向键(从没按到按) | **真事件** `move_pressed` | 在 `Idle` 会触发 `Idle→Walking`,是明确的状态转移触发点 |
| 松开方向键(从按到没按) | **真事件** `move_released` | 在 `Walking`/`Running` 会触发回到 `Idle`,同样是转移触发点 |
| 持续按住方向键(每帧都按着) | **动作,不是事件** | 每帧检测"是否仍按着"不产生状态转移,只是驱动位置数据持续更新(移动)。真正重要的是"按下"和"松开"这两个**边缘(edge)**,不是"持续按住"这个**电平(level)**——这是判断"输入到底是不是事件"的一个通用技巧:**只有状态发生变化的那个瞬间才是事件,状态没变化的持续过程只是动作。** |
| 按下加速键(Shift) | **真事件** `run_modifier_on` | 仅在 `Walking` 状态下有意义,触发 `Walking→Running`;在 `Idle`/空中状态下按加速键,不产生任何转移 → 应被忽略 |
| 松开加速键 | **真事件** `run_modifier_off` | 仅在 `Running` 状态下有意义,触发 `Running→Walking` |
| 按下跳跃键 | **条件性事件** `jump_pressed` | 在地面状态(`Idle`/`Walking`/`Running`)下是真事件,触发进入 `Jumping`;在空中状态(`Jumping`/`Falling`)下**应被忽略**(本案例不支持二段跳)——这正是Step 1里"同一事件不同状态不同行为"的落地实现 |
| 到达抛体顶点(垂直速度由正变负) | **真事件,但不是玩家输入,是物理计算结果** `apex_reached` | 由每帧的速度计算得出,一旦检测到符号翻转就是一个明确的边缘事件,触发 `Jumping→Falling` |
| 脚下地面消失(没有主动跳跃,直接从平台边缘走出) | **真事件,由碰撞检测/射线检测产生** `ground_lost` | 触发 `Idle`/`Walking`/`Running` → `Falling`。注意这个事件和"跳跃"完全不同来源,却导向同一类目标状态,教学要点是:**同一个目标状态,可以由完全不同的事件触发**,不要把"能到达Falling"简单等价于"一定是跳出来的" |
| 检测到落地(碰撞/射线检测) | **真事件** `landed` | 触发 `Falling`/`Jumping` → `Idle`/`Walking`/`Running`,具体落到哪个要看落地瞬间的方向键/加速键状态(这是一个带"守卫条件"的转移,见Step 4) |
| 空中时按方向键(改变水平移动方向) | **动作,不是事件** | 大多数平台游戏允许"空中控制"(air control),即在 `Jumping`/`Falling` 期间仍可以左右改变水平速度——但这只改变**数据**(水平速度值),不引发任何状态转移。这是一个很好的反例,提醒大家:**"这个输入有效果" 不等于 "这个输入触发了状态转移"**,它完全可能只是在修改当前状态内部的数据 |

### 确定的事件清单

- `move_pressed` —— 方向键按下的边缘
- `move_released` —— 方向键松开的边缘
- `run_modifier_on` —— 加速键按下的边缘(仅在Walking下生效)
- `run_modifier_off` —— 加速键松开的边缘(仅在Running下生效)
- `jump_pressed` —— 跳跃键按下的边缘(仅在地面状态下生效,空中被忽略)
- `apex_reached` —— 物理计算得出的"开始下落"信号
- `ground_lost` —— 碰撞/射线检测得出的"脚下没地了但没主动跳"信号
- `landed` —— 碰撞/射线检测得出的"落地"信号

**应忽略的无效输入**:空中状态下的 `jump_pressed`;`Idle`/空中状态下的 `run_modifier_on`/`run_modifier_off`(没有对应转移定义,原样丢弃,不产生任何副作用)。

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| Idle | move_pressed | Walking | 记录移动方向,播放走路动画 |
| Idle | jump_pressed | Jumping | 施加向上初始速度,播放跳跃动画 |
| Idle | ground_lost | Falling | 播放下落动画(极少见,如脚下平台被瞬间移除) |
| Walking | move_released | Idle | 播放站立动画 |
| Walking | run_modifier_on | Running | 播放奔跑动画 |
| Walking | jump_pressed | Jumping | 施加向上初始速度,保留水平速度,播放跳跃动画 |
| Walking | ground_lost | Falling | 播放下落动画(走出平台边缘) |
| Running | run_modifier_off | Walking | 切回走路动画 |
| Running | move_released | Idle | 播放站立动画 |
| Running | jump_pressed | Jumping | 施加向上初始速度(可带一定水平冲量加成),播放跳跃动画 |
| Running | ground_lost | Falling | 播放下落动画(冲出平台边缘) |
| Jumping | apex_reached | Falling | 切换到下落动画 |
| Jumping | jump_pressed | **Jumping(忽略)** | 无动作(不支持二段跳) |
| Jumping | move_pressed / move_released | **Jumping(忽略状态转移)** | 仅更新水平速度数据(空中控制),不切状态、不切动画 |
| Falling | landed **且** 未按方向键 | Idle | 播放落地→站立动画 |
| Falling | landed **且** 按住方向键、未按加速键 | Walking | 播放落地→走路动画 |
| Falling | landed **且** 按住方向键且按加速键 | Running | 播放落地→奔跑动画 |
| Falling | move_pressed / move_released | **Falling(忽略状态转移)** | 仅更新水平速度数据(空中控制) |
| (任意地面状态) | run_modifier_on/off,但当前不满足前置条件(如Idle下按加速键) | **原状态(忽略)** | 无动作,直接丢弃该输入 |

可以看到 `landed` 这一行被拆成了三条,靠"守卫条件(guard)"——落地瞬间的按键状态——来决定具体落到哪个状态。这是"同一事件、同一起始状态,但下一状态还需要参考额外数据"的典型写法,状态机依然成立,只是转移函数从 `(state, event) → next_state` 变成了 `(state, event, guard_data) → next_state`。

## Step 6: Python实现

### v1: 最简单版本(Enum + match-case,逻辑写在一个类里)

用一个 `MoveState` 枚举表示五个状态,角色类里维护 `state` 字段,每收到一个事件就调用一个大的 `match` 语句,按 `(当前状态, 事件类型)` 手写分支逻辑。

这是绝大多数人写游戏角色控制器的第一版代码,好处是直观、能马上跑起来;缺点是所有转移规则硬编码在一个方法体内,状态越多、事件越多,这个方法就越长,而且"哪些转移是合法的"必须读代码才能知道,没有一份可以脱离代码单独审查的"转移清单"。

### v2: Transition Table(数据驱动)

把v1里散落在 `match` 分支中的规则,抽成一张显式的表:`dict[(State, Event), tuple[State, Callable]]`(或者 `(state, event) -> (next_state, action_name)`)。事件处理函数变成通用的"查表→执行动作→切换状态"三步,不再需要为每个新状态/新事件写新的 `if`/`match` 分支,只需要往表里加一行。

相比v1的改进:**转移规则第一次变成了"数据"而不是"代码逻辑"**,可以被单独打印出来审查、单元测试覆盖所有 `(state, event)` 组合是否都有明确的行为(哪怕是"忽略"),也更接近Step 4那张表格本身——代码结构和设计文档结构第一次对上了号。

### v3: State Pattern(每个状态是一个类)

当每个状态"进入时要做的事"(比如播放对应动画、重置某些计时器)、"退出时要做的事"、"如何处理某个事件"都变得复杂、状态之间行为差异很大时,继续用一张扁平的转移表会让 `Action` 那一列塞满越来越复杂的回调函数,失去可读性。

State Pattern把每个状态实现成一个类(`IdleState`、`WalkingState`……),各自实现 `on_enter`、`on_exit`、`handle_event` 方法,状态自己知道"我在什么情况下要变成谁",FSM本身只负责持有"当前是哪个状态对象"并把事件转发给它。这是绝大多数商业游戏引擎(Unity Animator的状态机、Unreal的AnimGraph/Behavior Tree节点)里角色状态机的实际实现方式,原因是角色状态的"进入/退出副作用"(播放动画、锁定输入、启用/关闭碰撞体积)往往比"要切换到哪个状态"本身还复杂,值得给每个状态一个独立的类来承载这些副作用代码。

### v4: 可复用的通用FSM框架片段

抽出 `State`、`Event`、`Transition`、`FSM` 这几个与"移动"这个具体案例无关的抽象概念,做成一个可以被其他任何案例(攻击、NPC、Boss……)复用的最小框架:`FSM` 持有一张 `(state, event) -> Transition` 的表,`Transition` 里带 `target` 和可选的 `guard`(守卫条件函数,对应Step 4里"落地时依据按键分流"的场景)与 `action`(转移时执行的副作用)。

**什么时候值得引入框架,而不是每次手写v2/v3那样的代码?** 当你发现自己在**第二个、第三个案例**里又重新写了一遍"查表→检查guard→执行action→切换state→调用新状态的enter"这套逻辑时,说明这套逻辑本身已经足够通用、和"移动"这个具体业务无关,值得往上提一层,抽成框架,让后续案例只需要提供"状态清单+事件清单+转移表",而不是重新发明一遍FSM引擎本身。反过来,如果只有一个孤立的、以后大概率不会有"第二个类似案例"的小状态机,引入框架反而是过度设计。

完整代码见同目录 `01_character_move.py`。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**

本案例最有说服力的证据是Step 1第4条:`jump_pressed` 这同一个事件,在5个状态里有2种截然不同的结果(地面态触发转移,空中态被忽略)。如果不用状态机,你需要在游戏主循环的输入处理代码里写:

```python
if jump_pressed and (state == IDLE or state == WALKING or state == RUNNING):
    ...
```

这类判断会散落在代码的各个角落(处理跳跃键的地方、处理方向键的地方、处理加速键的地方各写一份"当前是不是在地面上"的检查),状态本身(“在不在地面上”)没有一个统一的、单一的存储位置和单一的修改入口。FSM把"当前状态"收敛成一个变量、把"如何切换"收敛成一张表,新增一个状态(比如后续加"蹲下 Crouch")只需要往表里加行,而不用去代码库里搜出所有"检查是否在地面"的地方,一一确认要不要给蹲下也加一份判断。

**什么情况下FSM反而是负担?**

如果这个角色的移动系统**从始至终只有"Idle/Walk"两个状态、一个方向键事件**,那么为它建一整套Transition Table + State Pattern类是过度设计——两三行 `if moving: ... else: ...` 就能解决,反而更好读。FSM的收益随着"状态数 × 事件数"以及"同一事件在不同状态下行为差异"的复杂度增长才会显现,状态少、行为单一的时候,FSM框架本身的间接层(查表、调度、guard)反而增加了阅读代码时的跳转次数。

**什么时候不应该使用FSM?通用判断标准,以及本案例是否接近这个边界**

通用标准:如果一个系统里,"下一步该做什么"主要取决于**连续变量的数值计算**(比如物理积分、插值、连续调参),而不是"离散阶段之间的跳变",就不该强行套FSM——你会发现"状态"和"数据"的边界很模糊,状态数量趋于无穷或者需要频繁按数值区间新增状态,这就是滥用FSM的信号(Step 2里"移动速度""移动方向"就是这类反例,已经被排除在状态之外)。

本案例本身**不接近这个边界**——五个状态清晰、互斥、事件离散,是FSM的舒适区。但它确实提醒我们:一个真实的角色移动系统,是"FSM(离散姿态) + 连续物理计算(速度/位置积分)"的**组合**,不是单纯的FSM,也不是单纯的物理模拟。识别直觉的关键在于:**把离散的姿态切换部分交给FSM,把连续的数值计算部分留在状态内部的update逻辑里**,不要试图用状态机去描述速度是1.0还是1.01这种连续量。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 同一个物理按键(如跳跃键),在不同状态下必须产生不同结果(转移/忽略) → 强烈提示需要FSM
✓ "按下"和"松开"是事件(边缘),"持续按住"是动作(电平)——别把每帧的输入检测当成事件
✓ 能用"if 变量 in {A, B}"反推出来的布尔标志(如is_grounded),是状态的衍生属性,不要单独建模
✓ 连续数值(速度、方向、坐标)是数据,不是状态,状态数量必须是有限且可枚举的
✓ 同一目标状态可以有多个不同来源的事件触发(跳跃到达顶点 vs 走出平台边缘,都到达Falling)
→ 应该考虑FSM
```

## 今天真正学会的一句话

**输入不是直接映射到"该做什么动作",而是先映射到"我现在处于哪个阶段",阶段本身才决定了同一个输入到底该被执行、被忽略、还是被记录成数据——分清"改变状态的事件"和"只改变数据的动作",是本课最该内化的直觉。**
