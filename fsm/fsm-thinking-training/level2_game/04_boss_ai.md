# Lesson 04: Boss AI (Level 2 - 小游戏)

本课和前三课有一个关键的不同:前三课的判断题是"该不该用FSM",本课的判断题是**"该用几层FSM"**——这是一个前三课都没遇到过的新维度。请带着这个心态往下读。

## Step 1: 是否适合FSM

先按老规矩过一遍五条特征:

- **是否存在有限状态?** 是。Boss在战斗流程里的行为姿态(待机/预警/攻击/受创/阶段转换/死亡)是有限的。
- **是否依赖历史状态?** 是,而且比前三课更突出:Boss当前"该表演哪个招式的前摇动画"取决于它刚刚经历了什么(比如上一招是不是刚放完近身攻击,这一招该不该改放远程技能来变化节奏),以及当前处于第几阶段(同一个"蓄力攻击"事件在阶段1和阶段3可能对应完全不同的招式集合)。
- **是否由事件驱动?** 是。玩家进入索敌范围、前摇动画播完、攻击动画播完、被弱点命中、血量跨越阈值、死亡——都是离散事件。
- **是否同一个事件在不同状态行为不同?** 是。`weakpoint_hit`(弱点被命中)这个事件,在阶段1(还没有弱点机制解锁)应该被忽略,在阶段2/3(弱点已解锁)会打出击晕(Staggered)。
- **是否存在明确状态切换?** 是,阶段之间(靠血量阈值)、招式之间(靠动画播放进度)都有明确的切换点。

**五条特征全部满足,说明"这是一个FSM问题"这个大方向没有错。** 但本课要暴露一个新问题:**"问题本身适合用状态机描述"和"应该用一台什么样的状态机去描述它"是两个独立的判断,五条特征满足只回答了第一个问题。** 如果不假思索地把Boss的"阶段"和"阶段内的招式/姿态"全部拍扁成一台单层FSM,会在Step 2/3看到状态和转移数量迅速失控。

**适合FSM: ★★★★★(问题结构本身)——但单层(扁平)实现会迅速退化为不可维护的状态爆炸,必须改用分层状态机(Hierarchical FSM, HFSM)。**

原因:这是本课最重要的一次"识别"训练——**不是识别"是否该用FSM"(答案显然是yes),而是识别"当前的FSM设计颗粒度是否已经到了该拆分层次的临界点"**。这个临界点的信号会在Step 2具体展示。

## Step 2: 发现状态(先看单层会长成什么样)

引导性问题:

- 当前系统有哪些阶段?哪些阶段互斥?
- Boss有几个"生命阶段"(比如按血量分段)?每个阶段里,Boss又有哪些行为姿态(待机/预警/攻击/受创)?
- 如果每个阶段的每个招式都要有自己的"预警"和"出招"两个姿态,状态数量会怎么增长?
- "阶段转换的过场演出"算不算一个独立状态,还是只是一个瞬间动作?

### 思考过程:先老实地把"单层FSM"的状态清单列完,看看会发生什么

假设这个Boss设计如下:

- **阶段1(血量 > 70%)**:招式池 {重扫(Swing)、地裂重击(Slam)},没有弱点机制。
- **阶段2(30% < 血量 ≤ 70%)**:招式池 {重扫、地裂重击、蓄力冲锋(Charge)},解锁弱点(可被弱点攻击打出击晕)。
- **阶段3(血量 ≤ 30%,狂暴)**:招式池 {重扫、地裂重击、蓄力冲锋、召唤陨石(Meteor)},保留弱点机制,移动/攻速加成。

如果每个招式都各自拥有"预警(Telegraph)"和"出招(Attack)"两个独立状态(因为不同招式的预警时长、出招动画、命中判定都不同,乍看确实"各自不同,该拆成独立状态"),那么单层状态清单会是:

| 阶段 | 该阶段的状态 | 数量 |
|---|---|---|
| 阶段1 | Idle、Telegraph_Swing、Attack_Swing、Telegraph_Slam、Attack_Slam | 5 |
| 阶段2 | Idle、Telegraph_Swing、Attack_Swing、Telegraph_Slam、Attack_Slam、Telegraph_Charge、Attack_Charge、Staggered | 8 |
| 阶段3 | Idle、Telegraph_Swing、Attack_Swing、Telegraph_Slam、Attack_Slam、Telegraph_Charge、Attack_Charge、Telegraph_Meteor、Attack_Meteor、Staggered | 10 |
| 全局 | Transitioning(阶段转换过场)、Defeated | 2 |

**合计25个状态。** 这还只是三个阶段、招式池只到4个技能的情况——如果后续策划要求"阶段3再加一个新技能",单层设计下要新增至少2个状态(它的Telegraph和Attack),而且**Idle、Telegraph_Swing、Attack_Swing这些名字在三个阶段里几乎重复了三遍**,行为逻辑(比如"Telegraph播完自动进入Attack"这条规则)在三个阶段里要写三份几乎一样的代码——这正是状态爆炸伴随的另一个更隐蔽的问题:**逻辑重复(违反DRY),不是状态数字大就完事了。**

更麻烦的是转移:每一个阶段1/阶段2的子状态,都需要额外挂一条"血量跨过阈值就跳到过场"的逃生边(哪怕当前正在播Attack_Slam的出招动作,只要这时候血量刚好掉过30%阈值,也得能跳出去),阶段1有5个子状态、阶段2有8个子状态,这就是**13条本质上完全相同("检查血量阈值,满足就跳出")但要在13个不同状态里各写一份的转移规则**。如果哪次改动忘了给新加的招式状态补上这条逃生边,就会做出一个真实存在的经典Boss战bug:**Boss卡在某个旧阶段的招式动画里出不来,或者阶段转换过场触发了但招式动画还在播,两者打架。**

**这就是"该拆分层"的临界信号:当你发现同一条逻辑规则,需要在成堆结构相似的状态上重复注册一遍,而不是集中定义一次,就是分层该登场的时候。**

### 重新审视:哪些"看起来是状态"的东西,其实是数据

在设计分层方案之前,先做一次和前三课同样的"假状态"审查——这次的审查结果会直接决定分层设计的样子:

1. **"正在预警哪个具体招式"(Telegraph_Swing vs Telegraph_Charge)**——**这其实是数据,不是状态本身该拆分的维度**。类比Lesson 1里"移动方向是数据不是状态"的教训:`Telegraph` 应该是**一个**状态,"当前预警的是哪个招式"是这个状态内部的一个数据字段(`current_move`),在进入Telegraph状态时从当前阶段的招式池里选一个赋值给它,而不是为每个招式单独建一个Telegraph状态。同理 `Attacking` 也应该是一个状态,不是N个。**这个发现直接把上面25个状态里,Telegraph_*、Attack_* 这些按招式细分的状态全部坍缩成2个通用状态(Telegraph、Attacking)+ 一个数据字段。**

2. **"当前是第几阶段"**——这确实是一个需要建模的真实状态(阶段1/2/3行为、招式池、是否有弱点机制都不同),但它和"Idle/Telegraph/Attacking/Staggered"这些**姿态类**状态,是两个不同维度、不同粒度的概念:阶段是"持续很长时间的宏观阶段",姿态是"几秒钟内快速切换的微观行为"。**当两个状态维度的时间尺度、变化频率差异很大时,这是分层的另一个信号:不要把"慢变量"和"快变量"拍扁进同一层状态清单。**

3. **"阶段转换过场演出"(Transitioning)**——这个值得单独讨论是不是需要一个真实状态,而不是一个瞬间动作。判断依据和前几课一样:**它是否会跨越多帧、期间是否有独特的、和其他状态不同的行为(比如免疫伤害、忽略玩家输入、Boss怪必须播完一段固定的咆哮/变身动画才能继续)?** 如果这些都成立(通常游戏里确实如此——阶段转换演出期间Boss往往无敌且不可交互),那么它就应该是一个真实的、独立的状态,只是这个状态该放在"阶段"这一层,而不是"姿态"这一层——它是阶段之间的一个过渡态,不属于任何具体阶段的招式循环。

4. **"是否解锁弱点机制"**——这是**阶段的配置数据**,不是状态。阶段2/3允许`weakpoint_hit`事件生效,阶段1不允许,这应该体现为"阶段配置里有一个`has_weakpoint`布尔字段",而不是为"有弱点的阶段"和"没弱点的阶段"分别设计不同的姿态状态集合。

### 确定的两层状态清单

**外层(阶段状态机, Phase FSM)**:

| 状态 | 说明 | 持续性 |
|---|---|---|
| `Phase1` | 血量>70%,招式池{Swing, Slam},无弱点 | 保持到血量≤70% |
| `Phase2` | 30%<血量≤70%,招式池{Swing, Slam, Charge},有弱点 | 保持到血量≤30%或恢复(通常Boss战不会回血,故本课不设回退) |
| `Phase3` | 血量≤30%,招式池{Swing, Slam, Charge, Meteor},有弱点,加速 | 保持到死亡 |
| `Transitioning` | 阶段切换过场,免疫伤害,忽略玩家输入与内层姿态子状态机 | 保持到过场动画播完 |
| `Defeated` | 死亡,终态 | 永久 |

**内层(姿态子状态机, Behavior Sub-FSM,同一份定义被Phase1/2/3三个阶段复用,只是招式池/弱点配置不同)**:

| 状态 | 说明 | 持续性 |
|---|---|---|
| `Idle` | 待机,等待玩家进入索敌范围 | 保持到玩家进入范围 |
| `Telegraph` | 预警中,`current_move`数据决定具体播哪个招式的前摇动画 | 保持到预警动画播完 |
| `Attacking` | 出招中,播放`current_move`对应的攻击动画和命中判定 | 保持到攻击动画播完(或被弱点命中打断) |
| `Staggered` | 被弱点命中后的击晕,仅在`has_weakpoint=True`的阶段可达 | 保持到击晕动画播完 |

内层4个状态穷尽了Boss在"招式循环"这个时间尺度上的所有姿态,外层5个状态穷尽了Boss在"整场战斗"这个时间尺度上的所有宏观阶段。**两层各自互斥穷尽,合起来共9个状态定义(不是25个),且没有任何一条逻辑被写第二遍。**

## Step 3: 寻找事件(两层各自的事件,以及"事件冒泡")

引导性问题:

- 哪些事件只影响"招式循环"这个内层,和阶段无关?
- 哪些事件只影响"宏观阶段"这个外层,和当前具体在放哪个招式无关?
- 当内层正在播放某个招式的动画,外层的阶段切换事件发生了,应该怎么处理——内层能"拦住"这个事件吗?

### 分析过程

| 候选事件 | 归属层级 | 理由 |
|---|---|---|
| `player_in_range` | 内层 | 只影响"是不是该开始预警",与当前是哪个阶段无关(哪个阶段都遵循同样的Idle→Telegraph规则) |
| `telegraph_done` | 内层 | 预警动画播完,进入出招,同样是通用的招式循环规则 |
| `attack_done` | 内层 | 出招动画播完,回到待机 |
| `weakpoint_hit` | 内层,**但受阶段配置的guard限制** | 事件本身在任何阶段都可能发生(玩家总能打弱点判定框),但只有`has_weakpoint=True`的阶段才会真正生效,阶段1会被guard拦下,行为上等价于忽略 |
| `stagger_done` | 内层 | 击晕动画播完,回到待机 |
| `hp_below_70` | **外层**,与当前Boss正在放哪个招式无关 | 触发Phase1→Transitioning,不管此刻内层是Idle还是正播到Attack动画一半 |
| `hp_below_30` | 外层 | 触发Phase2→Transitioning |
| `cutscene_done` | 外层 | 过场演出播完,进入下一阶段,并**重置内层子状态机为该阶段的Idle** |
| `hp_zero` | 外层,最高优先级 | 可以打断**任意**外层状态(包括Transitioning本身),直接进入Defeated |

**关键设计问题:`hp_below_70` 这个外层事件,如果这一帧内层正在播Attacking,应该怎么处理?** 这就是"事件冒泡(event bubbling)"该出场的地方:**内层状态机收到一个自己不认识的事件(比如`hp_below_70`,内层的Idle/Telegraph/Attacking/Staggered都没有为它注册任何转移),不应该报错或静默吃掉,而应该把这个事件原样"冒泡"给外层处理。** 外层收到后执行 `任意Phase→Transitioning`,同时**强制打断内层当前动作**(不管内层正播到哪一步,直接丢弃当前子状态,进入过场)。这是分层FSM区别于两台互不相干的独立FSM的核心机制:**内层处理不了的事件,自动交给外层;外层的决定可以强制覆盖内层当前的状态,而不需要内层每个状态都显式为此写一条转移。**

这也直接解决了Step 2里发现的"13条重复逃生边"问题:**分层之后,这13条重复规则被压缩成外层的1条规则(任意Phase收到hp阈值事件就转到Transitioning),内层完全不需要知道这条规则存在,因为事件冒泡机制自动帮内层"兜底"。**

### 确定的事件清单

- 内层事件:`player_in_range`、`telegraph_done`、`attack_done`、`weakpoint_hit`(受`has_weakpoint`guard限制)、`stagger_done`
- 外层事件:`hp_below_70`、`hp_below_30`、`cutscene_done`、`hp_zero`(最高优先级,可打断一切)

**应忽略的无效输入**:`weakpoint_hit` 在 `has_weakpoint=False` 的阶段(即阶段1)发生时,guard不通过,内层不产生任何转移,视觉上等价于忽略(但技术上是"guard拒绝"而不是"表里没有这一行",这个区分在Step 4会体现)。

## Step 4: 状态转移表(两张表,分别对应两层)

### 外层: 阶段转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| Phase1 | hp_below_70 | Transitioning(target=Phase2) | 强制打断内层当前动作,播放阶段1→2过场,内层子状态机挂起 |
| Phase2 | hp_below_30 | Transitioning(target=Phase3) | 同上,过场目标为Phase3 |
| Transitioning | cutscene_done | (读取target字段对应的Phase) | 恢复内层子状态机,重置为该阶段的Idle |
| Phase1 / Phase2 / Phase3 / Transitioning | hp_zero | Defeated | 打断一切(包括过场本身),播放死亡演出 |
| Defeated | 任意事件 | Defeated(忽略) | 终态 |
| (任意Phase内层产生的事件,如player_in_range等) | 内层事件 | **不在外层表中,由内层自行处理,外层不感知** | 这条不是真正的"转移行,而是提醒:外层转移表只关心宏观阶段事件,不应该出现任何招式类事件 |

### 内层: 姿态子状态机转移表(三个阶段共用同一份,仅靠阶段配置的`available_attacks`/`has_weakpoint`参数化)

| Current State | Event | Next State | Action |
|---|---|---|---|
| Idle | player_in_range | Telegraph | 从当前阶段`available_attacks`中选一个招式赋给`current_move`,播放对应预警动画 |
| Telegraph | telegraph_done | Attacking | 播放`current_move`对应的出招动画,开启命中判定 |
| Telegraph | weakpoint_hit,且`has_weakpoint=True` | Staggered | 打断预警,播放击晕动画 |
| Telegraph | weakpoint_hit,且`has_weakpoint=False` | **Telegraph(guard拒绝,忽略)** | 无动作(阶段1没有弱点机制) |
| Attacking | attack_done | Idle | 清空`current_move`,回到待机 |
| Attacking | weakpoint_hit,且`has_weakpoint=True` | Staggered | 打断出招,播放击晕动画 |
| Attacking | weakpoint_hit,且`has_weakpoint=False` | **Attacking(guard拒绝,忽略)** | 无动作 |
| Idle | weakpoint_hit,且`has_weakpoint=True` | Staggered | 待机时被弱点命中也可以被打出击晕(视具体设计,本课允许) |
| Staggered | stagger_done | Idle | 恢复待机 |
| (任意内层状态) | hp_below_70 / hp_below_30 / hp_zero | **内层无此转移,事件冒泡给外层处理** | 内层被外层强制打断,不需要内层自己处理 |

对比Step 2列出的"单层25状态、30+转移规则",分层后是"外层5状态5条规则 + 内层4状态9条规则(仅一份,复用三次)",**规则总数从30+降到14条左右,且新增一个招式(比如给阶段3加"Meteor Ⅱ")只需要在阶段3的`available_attacks`配置里加一项数据,内外两层的状态和转移规则都不需要改动一行。** 这就是分层设计相比单层设计在可维护性上的决定性差异。

## Step 6: Python实现

### v1: 最简单版本(单层Enum + match-case,故意展示"如果不分层会怎样")

这一版**故意**按Step 2里的天真设计实现:一个巨大的扁平 `BossStateV1` 枚举(为节省篇幅,代码里实现阶段1和阶段2的完整子状态集合,并在注释里说明阶段3该如何照此模式继续扩展),`handle_event` 里塞满 `match` 分支。跑一遍就能亲身感受到:**Idle/Telegraph/Attack 相关的处理逻辑在阶段1和阶段2里几乎逐字重复,只是状态名字的前缀从Phase1_变成Phase2_**,而且给每个子状态都要手写一条"血量阈值达到就跳转到过场"的逃生分支。这一版存在的目的就是让"状态爆炸"和"逃生边重复"这两个问题变得可以亲眼看见,而不是停留在文字描述。

### v2: Transition Table(数据驱动,但暴露"表格也无法消除结构性重复")

把v1的分支搬进一张 `dict[(state, event), Transition]` 表。可以清楚看到,即使转移规则变成了数据,**表里仍然有一大批结构相同、只是状态名字不同的行**(比如`(Phase1_Idle, PLAYER_IN_RANGE) -> Phase1_Telegraph_Swing`和`(Phase2_Idle, PLAYER_IN_RANGE) -> Phase2_Telegraph_Swing`,本质是同一条规则)。这一版用来说明一个重要教训:**"用表格代替if-else"和"消除重复"是两件不同的事,数据驱动只是换了个存储形式,不会自动带来复用——复用需要结构上的改变(分层/参数化),不是简单的"从代码搬到数据"。**

### v3: State Pattern(引入共享基类,开始出现分层的雏形)

到这一版,写代码的人几乎一定会本能地做一件事:把"Idle在阶段1/2/3里都一样的逻辑"提取成一个共享的基类或共享的处理函数,让`Phase1Idle`/`Phase2Idle`/`Phase3Idle`都继承它,构造时传入"这个阶段的招式池"作为参数。**这正是分层思想的雏形——你已经在用"参数化的共享逻辑"替代"逐阶段复制的独立类",只是还没有把"阶段"和"姿态"显式地拆成两台独立运作、通过事件冒泡通信的状态机。** 这一版的价值在于说明:**分层不是一个突然出现的高深技巧,而是当重复到达一定程度后,几乎所有认真重构代码的人都会自然滑向的方向,本课只是把这个自然而然的方向,提前显式地设计出来。**

### v4: 分层状态机(Hierarchical FSM)—— 复用前几课的框架并扩展出"内外两层 + 事件冒泡"

在前几课定义的 `GenericFSM`/`GenericTransition` 基础上,新增 `HierarchicalFSM`:它持有一个外层 `GenericFSM`(驱动Phase1/Phase2/Phase3/Transitioning/Defeated)和一个内层 `GenericFSM` 实例(驱动Idle/Telegraph/Attacking/Staggered,按当前外层阶段的配置参数化)。事件处理逻辑是:

1. 先把事件交给内层 `GenericFSM` 尝试处理。
2. 如果内层处理成功(找到匹配的转移),结束。
3. 如果内层没有对应这个事件的转移(即"内层不认识这个事件"),把事件原样冒泡给外层处理。
4. 外层处理阶段切换时,如果切换发生,重建/重置内层 `GenericFSM` 实例,换上新阶段的配置(新的招式池、新的`has_weakpoint`)。

这一版代码量并不比v2/v3大多少,但状态和转移规则的**数量**和**重复度**显著下降——这正是Step 4结尾那句话("规则总数从30+降到14条左右")在代码层面的真实体现。

完整代码见同目录 `04_boss_ai.py`。

## Step 7: 复杂度分析

**为什么FSM(这里specifically指分层FSM)比if-else更好,也比"单层FSM硬撑"更好?**

对比很直接:单层FSM在应对"多阶段 × 多姿态"的组合爆炸时,和一堆if-else在本质上没有区别——都是把组合关系拍扁列举出来,只是换了个语法外壳。分层FSM的优势不是"比if-else更好",而是**把一个二维的组合问题(阶段 × 姿态),真正拆成两个独立的一维问题**,阶段层不需要知道姿态层的任何细节,姿态层的实现被三个阶段完整复用,不需要知道自己此刻具体处于哪个阶段(只需要拿到"这个阶段给我的配置参数")。

**什么情况下FSM(尤其是分层FSM)反而是负担?**

如果Boss设计从始至终只有一个阶段、不多于3个招式,那么Step 2里那张"25个状态"的表格根本不会出现——一个单层FSM甚至一个简单的if-else完全够用,搭建"外层+内层+事件冒泡"的分层框架纯粹是过度设计。**分层带来的间接层(需要理解冒泡机制、需要在两个地方分别找转移规则)本身是有认知成本的,只有当省下来的重复代码/状态数量明显超过这个认知成本时才值得引入。**

**什么时候不应该使用FSM?通用判断标准,以及本案例是否接近这个边界**

通用标准(承接前几课并往前推一步):当"阶段"和"姿态"之间的交互变得**不是单纯的"外层可以强制打断内层、内层对外层无感知"**,而是双向的、姿态层的某些具体状态需要反过来影响阶段层的决策(比如"只有Boss当前正在Attacking某个特定招式时,才允许触发一种特殊的阶段跃迁"),分层FSM之间的边界就会变得模糊,这时候单纯的"外层FSM + 内层FSM + 单向事件冒泡"模型可能不够用,需要考虑更复杂的通信机制(比如内层主动发事件给外层,而不是外层单向查询/打断内层),或者转向更通用的行为树/HFSM框架(如UE的State Tree)。

本案例**没有触及这个边界**——阶段对姿态是单向、强制的控制关系(阶段可以随时打断姿态,姿态对阶段没有任何反向影响力),这正是"适合用简单的两层HFSM,不需要更复杂框架"的信号。如果后续设计要求"Boss只有在Idle姿态、且从没有被打断过一次攻击的情况下才能进阶到狂暴阶段"这类姿态反向影响阶段决策的规则变多,才是该考虑更复杂架构的时候。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 当一条转移规则(如"血量阈值触发跳转")需要在一大批结构相似的状态上重复注册,是分层FSM该登场的信号
✓ "具体招式是哪个"是数据(current_move),不是要新建的状态——姿态类状态的数量不该随内容量(招式数)线性增长
✓ 时间尺度差异大的两类状态(阶段是分钟级的宏观节奏,姿态是秒级的微观动作)不要拍扁进同一层
✓ 内层处理不了的事件,应该向外层冒泡,而不是每个内层状态都显式写一条"逃生边"
✓ 分层的方向是单向控制(外层可强制打断内层)时用简单HFSM即可;一旦内层需要反向影响外层决策,要考虑更复杂的架构
→ 应该考虑分层FSM,而不是继续加大单层FSM的状态数
```

## Step 9: 迁移训练题

1. **Roguelike游戏的"随机词条Boss"**:同一个Boss基础行为逻辑(阶段+姿态)不变,但每次进入战斗会随机获得1~3个"词条"修饰(比如"灵活":攻速+50%但阶段血量阈值不同;"分裂":血量低于50%会分裂出一个小怪物同时继续战斗;"护盾":每个阶段开始时会先获得一层需要先打破的护盾,护盾期间无法进入常规姿态循环)。这些词条会不会需要额外的一层状态机,还是应该做成"修饰当前层配置参数"的数据?

2. **多人团队副本的Boss"仇恨转移"机制**:Boss的攻击目标(仇恨对象)会在多个玩家之间根据"threat值"切换,某些技能只能对当前仇恨目标释放,某些技能是范围性的和仇恨无关;Boss进入某些特定阶段时会强制清空仇恨并随机选择新目标;仇恨目标玩家如果距离过近会触发"顺劈"额外攻击。这个"仇�24标切换"逻辑应该整合进已有的阶段/姿态两层结构里,还是应该设计成第三层,或者作为与状态机平行的独立系统?

3. **教学关卡里的"假Boss"(脚本化演出敌人)**:这个敌人外表和真Boss一样,但整场战斗其实是完全预先编排好的固定脚本(不管玩家做什么,Boss都会按固定的招式顺序、固定的时间点释放技能和进入下一阶段,玩家的输出、走位都不会影响它的任何决策,只有"玩家是否成功躲避"影响演出分支的极少数几个点),这种"看起来像Boss,但决策几乎不依赖外部事件"的对象,还需要为它设计一套Boss AI那样的状态机吗?

## 今天真正学会的一句话

**当你发现自己在往一台状态机里不断塞入"几乎一样,只是细节参数不同"的重复状态和重复转移规则时,不是继续加状态,而是要退一步问:这些重复的规则,是不是可以拆成"少量的宏观阶段状态"和"一份可被多个阶段复用、靠配置参数区分行为的微观姿态状态机",让重复的部分变成数据,让状态机本身只保留真正结构不同的部分。**
