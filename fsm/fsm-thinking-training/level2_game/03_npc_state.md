# Lesson 03: NPC状态 (Level 2 - 小游戏)

## Step 1: 是否适合FSM

- **是否存在有限状态?**
  是。一个具备基础AI的NPC(比如巡逻的哥布林)在行为层面的姿态是有限的:待机(`Idle`)、巡逻(`Patrol`)、追击(`Chase`)、攻击(`Attack`)、逃跑(`Flee`)、死亡(`Dead`)。这些是可枚举的行为模式,不是连续谱。

- **是否依赖历史状态?**
  是。举个例子:NPC当前处于 `Chase` 状态,玩家突然躲进草丛(视野丢失事件),NPC下一步该做什么?**取决于它之前在做什么**——如果它是从 `Patrol` 状态被拉进 `Chase` 的,视野丢失后大概率应该回到 `Patrol`,沿着原巡逻路线走;但如果游戏设计里还有"搜索(Search)"这个中间状态,NPC会先在最后目击位置停留几秒搜索,再回到 `Patrol`。无论哪种设计,"视野丢失事件发生后该去哪"都不是只看这一帧的距离数据就能确定,而要结合"当前处于追击链条中的哪个环节"。

- **是否由事件驱动?**
  是,但这是本课要重点辨析的地方:驱动这台状态机的事件**不是玩家的按键**,而是"感知系统"每帧计算出来的结果(距离、视野遮挡、血量比例)与预设阈值比较后产生的离散信号。这些信号本身是事件(离散、有明确的触发时刻),但它们的**来源**和Lesson 1/2里的玩家输入完全不同——这正是本课要训练的新直觉:**事件不一定来自外部输入,也可能来自系统自己对世界状态的持续采样与判断。**

- **是否同一个事件在不同状态行为不同?**
  是。`player_in_sight`(视野内发现玩家)这个事件:
  - 在 `Patrol`/`Idle` → 触发进入 `Chase`。
  - 在 `Chase`/`Attack` → 已经在响应玩家了,再次触发"发现玩家"没有意义,应被忽略(或者只是刷新一下"最后目击时间"这个数据,不引发状态转移)。
  - 在 `Flee` → 同样应该被忽略,NPC正在逃命,不会因为"又看到了玩家"就改变逃跑的决定(除非血量恢复到安全阈值以上,那是另一个独立事件)。

- **是否存在明确状态切换?**
  是,但需要澄清一点:切换的"临界点"不再是玩家按键的那一帧,而是**某个连续量(距离/血量比例)跨过预设阈值的那一帧**。只要阈值是明确定义的,跨越阈值这件事依然是离散、可精确定位的,不妨碍它是一个合法的"事件"。

**适合FSM: ★★★★☆**

原因:四条核心特征满足,状态互斥、事件驱动、同一事件不同状态行为不同、切换点明确。给4星而不是满分的原因是:**感知类事件的判定本身带有连续量转离散信号的模糊地带**——"距离小于10米"看似是一个干净的阈值,但如果每帧都严格用这一个阈值判断,角色在10.0米附近来回移动时会疯狂抖动式地反复触发进入/离开事件,产生"状态频繁抽搐"的问题。这个问题不是FSM本身的缺陷,而是提醒我们**感知驱动的FSM,必须额外设计"迟滞(hysteresis)"机制**才能稳定工作,这是比Lesson 1/2更贴近真实工程的复杂度,值得单独扣一点分来提醒读者不能照搬前两课的直觉直接下阈值。

## Step 2: 发现状态

引导性问题:

- 当前系统有哪些阶段?哪些是NPC在"没有察觉到玩家"时会做的事,哪些是"察觉到玩家后"才会做的事?
- 哪些阶段互斥?
- 哪些阶段的存在,依赖于持续满足某个感知条件(比如必须持续看到玩家才维持该状态),一旦条件不满足就必须离开?
- "是否已经发现玩家"本身算不算一个独立状态,还是应该被现有状态覆盖?

### 思考过程:先把容易被误认为状态的东西摆出来

1. **血量(HP)**——和前两课一样,**是数据,不是状态**。但本课要更进一步讨论:"血量是否低于阈值"这个**判断结果**,是不是应该做成一个独立的布尔标志(比如 `is_low_hp`)挂在NPC身上,和状态机分开维护?答案是:**不需要作为独立字段持久化,它应该是每帧根据当前HP实时计算出来的"感知结果",用于产生 `hp_below_threshold` 这个事件,事件发生后由状态机记录"现在处于Flee状态"这一件事,不需要再额外记一个is_low_hp标志**——否则你会有两份"低血量"的真相来源(状态本身 + 这个标志),一旦不同步就会产生bug。这是一个通用原则:**任何可以从"当前处于哪个状态"反推出来的信息,都不需要额外存储。**

2. **是否处于"仇恨"状态(是否已经锁定玩家为目标)**——这是本课最容易踩的陷阱。乍一看"仇恨"像是一个独立于Patrol/Chase/Attack之外的开关,但仔细分析:NPC处于 `Chase`/`Attack` 状态时必然是"有仇恨"的,处于 `Patrol`/`Idle` 时必然是"无仇恨"的——**"是否有仇恨"完全可以由"当前状态是否属于{Chase, Attack}集合"反推出来,不需要单独维护。** 唯一的例外是如果游戏设计里存在"仇恨值会随时间衰减,哪怕在Chase状态里,仇恨值归零也会主动脱离追击"这种数值化仇恨系统——这种情况下"仇恨值"变成了一个连续数据(和血量同类),而不是新的状态,只是它会产生额外的事件(`aggro_decayed_to_zero`)。

3. **视野检测的结果(能否看到玩家、距离多少)**——**是每帧计算的感知数据**,本身不是状态,而是产生事件的"传感器读数"。容易犯的错误是把"视野内有玩家"直接当成一个状态(`SeeingPlayer`),但这其实是与移动/战斗姿态**正交**的一个观测维度——NPC可以同时"在追击(Chase状态)"且"当前这一帧刚好视野被树挡住看不见玩家",这不代表它立刻要退出Chase(通常会有一个"丢失目标容忍时间"的缓冲)。所以"能否看到玩家"不是状态,而是驱动状态转移/维持的持续性感知输入。

4. **巡逻路径上的"当前巡逻点索引"**——这是**巡逻行为内部的数据**,不是需要拆分出来的新状态。`Patrol` 状态内部会持续在多个巡逻点之间移动,"走到了第几个点"只是这个状态内部维护的进度数据,不影响NPC在更高层面的行为分类,不需要为每个巡逻点建一个状态(那会导致状态数随巡逻点数量线性膨胀,这是典型的过度建模)。

5. **"逃跑"和"追击"是不是应该合并成同一种"移动到某个目标点"的状态,只是目标点不同(逃跑是远离玩家的点,追击是玩家所在的点)?**——这是一个值得认真权衡的设计问题,而不是有唯一答案。本课选择**不合并**,保留 `Chase` 和 `Flee` 两个独立状态,原因是:
   - 二者的**触发条件完全不同**(Chase由"发现玩家"触发,Flee由"血量过低"触发),合并后转移逻辑反而更复杂,需要在状态内部用一个字段区分"我现在的移动目的是追击还是逃跑",这又把状态转移逻辑重新藏回了状态内部的if判断,违背引入FSM的初衷(与Lesson 1里"Jump/Fall是否要合并成Airborne"是同一类判断题)。
   - 二者可能有**不同的优先级关系**(比如Flee通常应该比Chase优先级更高——都低血量了还在追玩家送死不合理),独立建模能更清晰地在转移表里体现"Flee可以打断Chase,但反过来不行"。

### 确定的状态清单

| 状态 | 说明 | 互斥性 | 持续性 |
|------|------|--------|--------|
| `Idle` | 原地待机,还没开始巡逻(通常只在NPC刚生成时短暂存在) | 与其余5个互斥 | 保持到巡逻计时器触发/发现玩家/死亡 |
| `Patrol` | 沿预设路径巡逻,内部维护当前巡逻点索引 | 同上 | 保持到发现玩家(→Chase)/死亡,期间感知不到玩家就一直巡逻 |
| `Chase` | 追击玩家,朝玩家当前位置移动 | 同上 | **依赖持续满足"能感知到玩家"这一条件**,一旦进入攻击范围(→Attack)、或血量过低(→Flee)、或长时间丢失目标(→Patrol)、或死亡,就会离开 |
| `Attack` | 在攻击范围内对玩家发起攻击 | 同上 | 保持到玩家脱离攻击范围(→Chase)、血量过低(→Flee)、或死亡 |
| `Flee` | 逃离玩家,朝远离玩家的方向移动 | 同上 | 保持到血量恢复到安全阈值以上(→Patrol)、或死亡(逃跑途中依然可能被击杀) |
| `Dead` | 死亡,终态 | 同上,终态 | 永久 |

六个状态互斥穷尽。需要特别强调 `Chase` 那一行的"依赖持续满足"表述:**这是本课和前两课最大的结构差异——Chase不是被某个瞬间事件"推入"之后就靠下一个瞬间事件"推出",它的维持本身依赖一个持续为真的条件(能感知到玩家),这个条件一旦转为假,状态机要能检测到这个"条件由真变假"的边缘,把它转成一个事件(`sight_lost`)来触发离开。** 这正是"感知驱动"和"按键驱动"最本质的区别:按键天然是边缘触发的,感知条件是电平信号,需要额外一层"电平转边缘"的检测逻辑才能变成事件。

## Step 3: 寻找事件

引导性问题:

- 什么条件的"由假变真"或"由真变假",应该产生一个事件?
- 哪些感知结果只是持续性的数据,不产生事件(除非跨越了阈值)?
- 距离、血量这些连续量,应该在哪里做"阈值判断",判断结果是不是要做迟滞处理?
- 有没有"NPC自己内部计时器"产生的事件,和玩家的行为完全无关?

### 分析过程

| 候选信号 | 分类 | 理由 |
|---|---|---|
| 每帧计算的"NPC到玩家的距离" | **持续性数据**,不是事件 | 只有当这个距离跨越某个预设阈值(进入/离开视野范围、进入/离开攻击范围)的那一帧,才产生事件 |
| 距离首次小于视野范围(sight_range) | **真事件** `sight_acquired` | 触发 `Patrol/Idle → Chase`。**必须做迟滞处理**:实际判定不应该用同一个阈值判断"获得"和"失去",而应该用两个略有差距的阈值(比如获得用 `sight_range`,失去用 `sight_range * 1.3`),否则NPC在边界附近来回抽搐 |
| 距离超过失去视野的阈值(且持续一段时间,比如3秒都没有重新看到) | **真事件** `sight_lost` | 触发 `Chase → Patrol`(或先进入一个"搜索"过渡状态,本课简化为直接回Patrol)。注意这里额外引入了"持续一段时间"的容忍窗口,这也是一种迟滞,针对的是"玩家一瞬间跑到掩体后又立刻出来"这种情况,不应该立刻丢失目标 |
| 距离首次小于攻击范围(attack_range) | **真事件** `in_attack_range` | 触发 `Chase → Attack` |
| 距离超过攻击范围 | **真事件** `out_of_attack_range` | 触发 `Attack → Chase` |
| 血量比例首次低于逃跑阈值(比如20%) | **真事件** `hp_below_threshold` | 触发 `Chase/Attack → Flee`,**优先级高于感知类事件**——即使此刻仍在攻击范围内,只要血量过低也应该切到Flee,不应该继续Attack |
| 血量比例恢复到安全阈值以上(比如50%,同样需要用比逃跑阈值更高的恢复阈值做迟滞,避免在20%上下反复抽搐) | **真事件** `hp_recovered` | 触发 `Flee → Patrol` |
| 生命值归零 | **真事件** `hp_zero` | 触发任意状态 → `Dead`,最高优先级 |
| 巡逻点计时器到期/到达巡逻点 | **真事件,但只是Patrol内部推进,不改变最外层状态** `patrol_waypoint_reached` | 严格来说这是Patrol状态内部的一个"自环事件",不引发对外可见的状态切换,只是驱动内部数据(巡逻点索引)前进,教学中不放进最外层转移表,而是作为Patrol状态内部逻辑 |
| NPC自身受到攻击(被玩家命中,但还没死) | **真事件** `hit_taken` | 本课简化处理:命中会立刻把状态推入 `Chase`(如果不是已经在Chase/Attack/Flee),即使还没进入视野范围——"被打了肯定知道是谁打的",这是感知驱动之外的另一种事件来源(伤害系统直接产生的事件,和视觉感知无关) |

### 确定的事件清单

- `sight_acquired` / `sight_lost`(带迟滞与容忍窗口的视野感知事件)
- `in_attack_range` / `out_of_attack_range`
- `hp_below_threshold` / `hp_recovered`(带迟滞的血量感知事件,优先级高于视野类事件)
- `hp_zero`(最高优先级)
- `hit_taken`(伤害系统直接产生,不经过视野判断)

**应忽略/不产生转移的信号**:`sight_acquired` 在已经处于 `Chase`/`Attack`/`Flee` 时重复触发(没有意义,忽略或仅刷新最后目击时间数据);`in_attack_range`/`out_of_attack_range` 在 `Flee` 状态下触发(逃跑中不关心是否进入攻击范围,忽略)。

## Step 6: Python实现

### v1: 最简单版本(Enum + match-case)

用 `NpcState` 枚举六个状态,`update(distance, hp_ratio)` 方法每帧被调用一次,内部先把"距离/血量比例"这两个连续量,通过一组预置阈值(含迟滞双阈值)转换成离散事件,再用 `match (state, event)` 分支处理。这一版直接暴露"感知转事件"这一层转换逻辑该放在哪里:**放在状态机接收事件之前,单独一个"感知层"函数里,状态机本身仍然只处理离散事件,不掺杂距离比较逻辑**——这是本课要固化的一个架构原则。

### v2: Transition Table(数据驱动)

把v1的转移规则搬进表里,同时把"感知转事件"的迟滞逻辑抽成一个独立的 `PerceptionFilter` 类,内部维护"上一帧是否已经获得视野"这个内部状态(注意:这不是NPC行为FSM的状态,是感知滤波器自己的两态状态机——`Seeing`/`NotSeeing`,用来产生干净的边缘事件,这是一个"用小型FSM来产生输入给大型FSM"的组合手法,值得留意)。

### v3: State Pattern(每个状态是一个类)

`Chase` 状态类内部持有"最后一次看到玩家的时间戳",用于计算"丢失视野后是否已经超过容忍窗口";`Patrol` 状态类内部持有"当前巡逻点索引"。这一版清晰展示:**感知驱动的FSM,状态对象往往需要携带更多与时间相关的内部数据(时间戳、计时器),而不仅仅是简单的枚举值**,这是相比Lesson 1/2的一个自然演进。

### v4: 可复用的通用FSM框架 + 感知事件生成器

复用前两课的 `GenericFSM`,额外提供一个独立的、可复用的 `HysteresisGate` 工具类(输入连续值和"进入阈值/离开阈值"两个参数,输出"进入/离开/无变化"三种离散结果),这个工具本身与"NPC"这个具体业务完全无关,可以被同样需要迟滞判断的其他系统复用(比如Boss AI的血量分阶段判断,见Lesson 4)。这体现了"可复用框架"不仅仅指FSM引擎本身,**任何"连续量转离散事件"的通用模式,都值得独立抽出来复用**。

完整代码见同目录 `03_npc_state.py`。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**

如果不用状态机,NPC的AI代码往往会变成每帧执行一遍的一长串条件判断,类似:

```python
if hp_ratio < 0.2:
    flee()
elif distance < attack_range:
    attack()
elif distance < sight_range:
    chase()
else:
    patrol()
```

这种写法乍看简洁,但它隐含了一个致命问题:**它是"无状态"的,每帧都从头重新判断该做什么,而不是"我现在在做什么,基于此我该怎么变化"。** 一旦引入"丢失视野后要容忍3秒才切回巡逻"这种依赖历史的规则,这种无状态if-elif链条完全无法表达(容忍窗口需要知道"我之前已经在Chase多久了""上次看到是什么时候"),必须引入某种记忆——而这份记忆本质上就是状态机想要正式化的东西。FSM把"当前处于哪个阶段"和"这个阶段已经持续了多久/携带了哪些历史数据"显式地组织起来,if-elif链条只能靠额外散落的变量七拼八凑地模拟同样的效果。

**什么情况下FSM反而是负担?**

如果NPC的AI足够简单——比如没有Flee、没有丢失视野容忍窗口,只是"看到玩家就追,追上了就打,打不着就一直追",那么一个三态if-elif链条就足够清晰,不需要正式的状态机框架、更不需要迟滞滤波器这种额外基础设施。本课引入的复杂度(迟滞、容忍窗口、多种事件来源)是"感知驱动AI"这个问题域本身自带的复杂度,不是刻意为了炫技加上去的,这一点在实际项目中决定了要不要值得为此建FSM——**如果目标问题本身没有这些复杂度,提前建立完整的感知层+FSM框架就是过度设计**。

**什么时候不应该使用FSM?通用判断标准,以及本案例是否接近这个边界**

通用标准:如果NPC的决策更依赖"多个连续因素的加权综合评分"而不是"离散阶段之间的跳变"(比如现代游戏AI里常见的Utility AI——给每个可选行为打一个连续分数,选分数最高的执行,分数由距离、血量、弹药、队友状态等多个因素连续加权得出),FSM会显得别扭,因为你会发现"到底该不该切换状态"变成了一个模糊的多因素比较问题,而不是"事件发生了没有"这种二元判断,这时候Utility AI或行为树(Behavior Tree)往往是更合适的模型。

本案例**部分接近这个边界**,但还没有跨过去:虽然引入了"距离""血量"这些连续量,但每个连续量到离散事件的映射仍然是**独立、单一维度**的阈值判断(不需要跨维度加权),转移逻辑依然可以被一张有限的表格清晰穷举,所以FSM仍然合适。一旦未来要求"NPC要综合考虑距离、血量、周围友军数量、玩家武器类型等5个因素来决定是否逃跑",这种多因素综合决策就不再适合用一堆离散事件+转移表来表达,是该考虑Utility AI或行为树的信号。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 事件不一定来自玩家输入,持续性感知数据(距离/血量)跨越阈值的那一帧本身就是事件
✓ 单一阈值会导致状态在临界点附近抽搐,感知驱动的转移几乎总需要"进入阈值"和"离开阈值"分开设的迟滞设计
✓ 能从"当前状态属于哪个集合"反推出来的布尔标志(如是否有仇恨),不需要单独维护,否则会有两份互相可能不同步的真相
✓ "丢失目标后要不要立刻切换"往往依赖一个容忍时间窗口,这类历史依赖是FSM相对无状态if-elif链条的核心优势
✓ 当决策开始依赖多个连续因素的加权综合,而不是单一离散事件,是FSM开始逼近边界、该考虑Utility AI/行为树的信号
→ 应该考虑FSM(但要为感知层单独设计迟滞机制)
```

## Step 9: 迁移训练题

1. **群体警觉系统**:一片区域内有5个巡逻中的NPC,任意一个NPC发现玩家后,会通过"呼叫"的方式让附近未发现玩家的NPC也一并进入警觉/追击状态(即使它们自己的视野根本没看到玩家),呼叫有一个范围限制,并且被呼叫进入警觉的NPC如果在一段时间内自己也没有真正看到玩家,会重新回到巡逻。

2. **潜行游戏的敌人视野等级系统**:敌人对玩家的"察觉"不是二元的(看到/没看到),而是有一个连续累积的"警觉值"——玩家在敌人视野边缘会缓慢累积警觉值,完全暴露在视野中心会快速累积,躲进阴影/掩体会让警觉值缓慢下降;警觉值达到不同阈值会依次表现为"疑惑(原地张望)""搜索(走向声源/最后目击点)""完全警报(呼叫支援并追击)"三个层级,警觉值降到零会恢复平静巡逻。

3. **动物驯服/驯服失败后的野化系统**:一只野生动物NPC平时会怕人(玩家靠近就跑),投喂足够次数食物后进入"信任"阶段(玩家靠近不会跑,但还不能骑乘/命令),信任值持续一段时间没有被打断(比如被攻击一次会让信任值大幅下降甚至清零)会转为"驯服完成"状态(可以被骑乘、跟随命令移动),驯服完成后如果玩家长时间不理睬/虐待,存在小概率随时间衰减跌回"野化"状态。

## 今天真正学会的一句话

**驱动状态机的不必是"外部输入",持续性的世界状态(距离、血量、时间)本身也能通过"跨越阈值"这个动作产出干净的离散事件,而识别这类事件的关键技巧,是先问"这个信号在临界值附近会不会抽搐",一旦会,就要在感知层单独设计迟滞,而不是把这团麻烦丢给状态机本身。**
