# Lesson 02: 角色攻击 (Level 2 - 小游戏)

## Step 1: 是否适合FSM

- **是否存在有限状态?**
  是。角色在战斗系统里的姿态有限:待机(`Idle`)、移动(`Moving`)、攻击中(`Attacking`)、受击硬直(`Staggered`)、死亡(`Dead`)。不会随时间无限增长。

- **是否依赖历史状态?**
  是,而且比Lesson 1更明显。举例:攻击键在 `Attacking` 状态、且处于"连击窗口"内被按下,会被记录为"下一击已排队",攻击动画播完后立即触发第二击;但如果同样的按键动作发生在攻击动画刚开始播放、还没进入连击窗口时,则会被彻底忽略。**同一个输入,是否生效,取决于"我现在处于Attacking状态的哪个阶段"这一段历史/上下文**,不是孤立看这一帧的按键就能判断的。

- **是否由事件驱动?**
  是。攻击键按下、攻击动画播放完毕、受到伤害、生命值归零,都是离散的、可以精确定位到某一帧的事件,不是连续渐变的量。

- **是否同一个事件在不同状态行为不同?**
  是,这是本课的核心教学点。`attack_pressed` 这同一个事件:
  - 在 `Idle`/`Moving` 状态 → 触发进入 `Attacking`。
  - 在 `Attacking` 状态的"连击窗口期"内 → 被记录为"排队的下一击",不立即生效。
  - 在 `Attacking` 状态但已经超出连击窗口(动作后段的收招阶段) → 被直接丢弃,什么也不发生。

  同时,`move_pressed` 这个事件:
  - 在 `Idle` → 触发进入 `Moving`。
  - 在 `Attacking` → **被忽略,角色的位置/朝向被锁定,直到攻击动作播放完毕**。这正是"不可打断状态"的定义:处于该状态时,原本"理应"生效的输入被系统性地吃掉。

- **是否存在明确状态切换?**
  是。攻击动作的开始(按键按下瞬间)、结束(动画播放完毕的那一帧)、被打断(受到伤害的那一帧)都是可以精确指出"发生在哪一帧"的临界点。

**适合FSM: ★★★★★**

原因:本案例是"不可打断状态"和"输入排队 vs 输入忽略"这两个概念的教学范本,五条特征全部满足,而且第2条和第4条结合得非常紧密——历史状态(处于连击窗口内还是外)直接决定同一个事件的三种不同结局(生效/排队/忽略)。这比Lesson 1的"地面/空中"二元判断更细腻,是训练"识别直觉"很好的进阶案例。

## Step 2: 发现状态

引导性问题:

- 当前系统有哪些阶段?哪些阶段互斥?
- 哪些阶段具有持续性(会锁定输入,直到某个事件把它解除)?
- "正在播放攻击动画"算不算一个独立的、需要建模的阶段,还是应该拆成好几个更细的阶段?
- 受到伤害算不算一个独立阶段,还是应该合并进已有阶段?

### 思考过程:先把容易被误认为状态的东西摆出来

1. **是否处于"连击窗口"内**——**这是最容易被误判为独立状态的候选项,但它其实是 `Attacking` 状态内部的一个"子阶段/计时窗口",不是与 `Attacking` 并列的独立FSM状态**。为什么不建成独立状态?因为它不满足"互斥且可被外部事件单独观察到明确切换点"的条件——它更像是 `Attacking` 状态内部一个随时间自动打开/关闭的时间窗(比如"攻击动画播放到40%~70%进度之间"),本质上是状态内部的一个**计时器驱动的内部数据**,而不是需要单独 `enter`/`exit` 的阶段。用一个字段 `combo_window_open: bool`(或直接用动画播放进度计算)挂在 `Attacking` 状态内部即可,没必要拆成 `AttackingComboWindowOpen`/`AttackingComboWindowClosed` 两个状态。

2. **是否有"排队的下一击"(queued_next_attack)**——**是数据,不是状态**。它是一个布尔标志/枚举值,记录"连击窗口期内是否又按了一次攻击键",攻击动画播放完毕后读取这个标志决定"要不要自动开始第二击的Attacking",而不是自己就是一个状态。把它做成状态会导致状态数量随着连击段数(一段、二段、三段连击)线性膨胀,而这些"连击段"在行为逻辑上是相似的(同样锁定输入、同样播完就检查是否有排队的下一击),更适合用"同一个 `Attacking` 状态 + 内部数据记录当前是第几段连击"来表达,而不是新增 `Attacking2`、`Attacking3` 这样重复的状态。

3. **是否处于"无敌帧"(i-frame,攻击或翻滚期间短暂免疫伤害)**——**是标志位,依附于某个状态存在,不是独立状态**。它只在 `Attacking`(或未来可能加入的翻滚状态)内部的某个时间段为真,离开该状态自动归false,不需要单独建模。这是Lesson 1里"is_grounded可以由状态反推"同一类陷阱的再次出现:**任何"只在某个状态内、某段时间内为真"的标志,先怀疑它是状态的衍生属性,而不是新的独立状态。**

4. **生命值(HP)**——仍然是**数据**,和Lesson 1的移动速度是一类。生命值本身不是状态,但生命值"归零"这个**事件**会触发状态转移到 `Dead`。区分清楚:HP是被持续追踪的连续数据,`hp_zero` 才是事件。

5. **"受到伤害但没有被打出硬直"(比如格挡成功,只是消耗少量体力/护盾,角色行为不受影响)**——这提示我们 `Staggered` 状态不是"只要挨打就进入",而是有一个前置判断(比如伤害是否超过硬直阈值、有没有开启格挡)。这个判断本身不是状态机要处理的内容,而是"要不要触发 `hit_taken` 这个事件"的前置逻辑,类似Lesson 1里"落地时判断按键状态"的guard——**状态机只负责'事件发生后怎么切状态',不负责'这一帧算不算发生了这个事件'的判定细节,那部分逻辑留在事件产生的上游。**

### 确定的状态清单

| 状态 | 说明 | 互斥性 | 持续性 |
|------|------|--------|--------|
| `Idle` | 站立,未在移动、未在攻击 | 与其余4个互斥 | 保持到移动/攻击/受击/死亡任一事件发生 |
| `Moving` | 正常移动(复用Lesson 1的移动子系统,此处简化为一个状态) | 同上 | 保持到停止移动/攻击/受击/死亡 |
| `Attacking` | 攻击动作播放中,**期间输入被锁定或排队**,内部维护"当前第几段连击"和"连击窗口是否打开"两个数据字段 | 同上 | 保持到动画播放完毕(可能自动续到下一段连击,仍算同一个Attacking状态的一次新播放),或被更高优先级的受击/死亡事件打断 |
| `Staggered` | 受击硬直,短暂的强制播放"挨打"动画,期间输入同样被锁定 | 同上 | 保持到硬直动画播放完毕 |
| `Dead` | 死亡,不再响应任何输入 | 同上,且**没有任何转移离开这个状态**(终态) | 永久 |

五个状态互斥穷尽。特别提醒:**`Attacking` 可以被 `Staggered`/`Dead` 打断,但不能被移动/再次攻击的普通输入打断**——这是"不可打断"的准确含义:不可打断的是"同优先级或更低优先级的常规输入",不是"任何情况都不可打断"。这也是本课要纠正的一个常见误解:很多人以为"不可打断状态"意味着状态机里没有任何转移能离开它,但真实游戏设计里几乎总会保留"受伤"和"死亡"这两个更高优先级的例外通道。

## Step 3: 寻找事件

引导性问题:

- 什么事情导致状态改变?
- 哪些输入只是动作(不改变角色所处阶段)?
- 哪些输入在特定阶段应该被"忽略"?哪些应该被"排队"?两者的区别是什么?
- 有没有"系统产生的事件"(不是玩家按键,而是动画播放/伤害计算的结果)?

### 分析过程:区分"动作" vs "真正触发转移的事件" vs "应忽略/应排队的输入"

| 候选输入/信号 | 分类 | 理由 |
|---|---|---|
| 按下方向键(在Idle) | **真事件** `move_pressed` | 触发 `Idle→Moving` |
| 松开方向键(在Moving) | **真事件** `move_released` | 触发 `Moving→Idle` |
| 按下方向键(在Attacking/Staggered期间) | **应忽略的无效输入** | 位置被锁定,不产生任何效果——这与Lesson 1里"空中方向键只改数据不改状态"不同,这里是**彻底不生效**,连数据都不更新,因为攻击动作往往有自己预设的位移曲线(比如突进斩击),不应该被玩家方向键干扰 |
| 按下攻击键(在Idle/Moving) | **真事件** `attack_pressed` | 触发 `Idle/Moving→Attacking`,开始第一段攻击 |
| 按下攻击键(在Attacking,且当前处于连击窗口内) | **应排队的输入**,记为数据 `next_attack_queued = True`,**不是立即生效的事件** | 这是"排队"而不是"忽略"的关键区别:忽略是"什么都不记录,输入彻底消失";排队是"暂时不生效,但记录下来,等特定时机(本段动画播完)再检查并使用"。教学重点:**排队的本质是把一个"当前不合法的转移请求",转成"未来某个转移事件发生时要参考的数据"**,而不是直接触发转移 |
| 按下攻击键(在Attacking,但已超出连击窗口,处于收招后摇阶段) | **应忽略的无效输入** | 此时即使再按攻击键也不会有连击效果,直接丢弃,不排队、不生效 |
| 按下攻击键(在Staggered/Dead) | **应忽略的无效输入** | 硬直和死亡期间攻击键完全无效 |
| 攻击动画播放完毕(单段攻击结束) | **真事件,系统产生** `attack_finished` | 根据是否有 `next_attack_queued`,决定是续下一段连击(仍是Attacking,重新播放下一段动画并清空排队标志)还是回到 `Idle`/`Moving`(取决于此刻是否仍按着方向键——但由于攻击期间方向键被忽略,这里更常见的实现是回到 `Idle`,再由玩家重新按方向键触发移动;两种设计都存在,教学中采用"直接回Idle"这一更常见、更简单的版本) |
| 受到伤害且判定为需要硬直 | **真事件,由伤害系统产生,优先级高于普通输入** `hit_taken` | 可以打断 `Idle`/`Moving`/`Attacking` 中的任意一个,直接进入 `Staggered`。这是本课要强调的"高优先级事件可以打断'不可打断状态'"的具体落地 |
| 硬直动画播放完毕 | **真事件,系统产生** `stagger_finished` | 触发 `Staggered→Idle` |
| 生命值归零 | **真事件,由伤害系统产生,最高优先级** `hp_zero` | 可以从**任意状态**(包括Attacking和Staggered)直接进入 `Dead`,不受"不可打断"规则限制——死亡永远是最高优先级 |

### 确定的事件清单

- `move_pressed` / `move_released`
- `attack_pressed`(仅在Idle/Moving下是"真事件";在Attacking连击窗口内降级为"排队数据";在其余情况下是"应忽略输入")
- `attack_finished` —— 系统产生,读取 `next_attack_queued` 决定去向
- `hit_taken` —— 系统产生,优先级高于普通输入,可打断Attacking
- `stagger_finished` —— 系统产生
- `hp_zero` —— 系统产生,最高优先级,可打断任意状态

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| Idle | move_pressed | Moving | 开始移动 |
| Idle | attack_pressed | Attacking | 播放攻击动画第1段,锁定移动输入,打开无敌帧(可选) |
| Idle | hit_taken | Staggered | 播放受击动画 |
| Idle | hp_zero | Dead | 播放死亡动画,禁用碰撞 |
| Moving | move_released | Idle | 停止移动 |
| Moving | attack_pressed | Attacking | 同上,并立即停止当前移动 |
| Moving | hit_taken | Staggered | 播放受击动画 |
| Moving | hp_zero | Dead | 播放死亡动画 |
| Attacking(连击窗口内) | attack_pressed | **Attacking(不切状态)** | 设置 `next_attack_queued=True`,**排队**,不立即生效 |
| Attacking(窗口外/后摇阶段) | attack_pressed | **Attacking(不切状态,忽略)** | 无动作,直接丢弃 |
| Attacking | move_pressed / move_released | **Attacking(忽略)** | 无动作,位置被锁定 |
| Attacking | attack_finished,且 `next_attack_queued=True` | **Attacking(不切状态,但重播下一段)** | 清空排队标志,播放下一段连击动画,重新打开新的连击窗口 |
| Attacking | attack_finished,且 `next_attack_queued=False` | Idle | 解除输入锁定,清空连击段计数 |
| Attacking | hit_taken | Staggered | **打断攻击**,立即停止当前攻击动画,播放受击动画,清空连击段计数与排队标志 |
| Attacking | hp_zero | Dead | 打断攻击,播放死亡动画 |
| Staggered | move_pressed / attack_pressed | **Staggered(忽略)** | 无动作,硬直期间任何常规输入无效 |
| Staggered | hit_taken(硬直期间又被打了一下) | **Staggered(不切状态,可选:重置硬直计时)** | 视具体手感设计,教学上标注为"允许被再次命中打断/刷新硬直",不新增状态 |
| Staggered | stagger_finished | Idle | 恢复正常输入响应 |
| Staggered | hp_zero | Dead | 播放死亡动画 |
| Dead | 任意事件 | **Dead(忽略)** | 无动作,死亡是终态,不接受任何输入或事件 |

## Step 6: Python实现

### v1: 最简单版本(Enum + match-case)

用 `AttackState` 枚举五个状态,在角色类里手写 `handle_event`,用 `match (state, event)` 分支处理。连击排队逻辑用一个 `bool` 字段 `combo_queued` 直接挂在角色对象上。这一版最直接地暴露出"不可打断"是怎么实现的:**大量分支的本质就是"在Attacking/Staggered状态下,除了少数几个高优先级事件,其余分支要么不存在(match不到)要么显式写成'什么都不做'。**

### v2: Transition Table(数据驱动)

把v1的规则搬进 `dict[(state, event), Transition]`。这一版特别演示"排队"和"忽略"两种不同处理方式在数据结构上的区别:

- **忽略**:表里根本没有这个 `(state, event)` 组合的条目,查表 miss,自然什么都不做。
- **排队**:表里**有**这个条目,但对应的 `action` 不是"切换状态",而是"设置一个数据标志",`target` 指向**自身状态**(自环转移,即"转移"了但状态没变,只是执行了副作用)。

这个区分在v1里容易被写成一堆散落的 `if`,v2把它显式地放进表里,复查代码时能一眼看出"哪些输入被完全忽略、哪些被记录"。

### v3: State Pattern(每个状态是一个类)

`Attacking` 状态类内部维护 `combo_step`(第几段连击)、`combo_window_open`(连击窗口是否打开)、`queued`(是否已排队下一击)这几个只属于这个状态的内部数据,`Idle`/`Moving`/`Staggered`/`Dead` 各自是更简单的类。这一版的价值在于:**"连击窗口""排队标志"这些第2步里判定为"不是独立状态"的数据,理应存在于`Attacking`状态对象内部,而不是散落在角色类的顶层字段里**——State Pattern天然地把这些数据的生命周期(创建于进入Attacking,销毁于离开Attacking)和状态本身的生命周期绑定,这是相比v1/v2这种"数据全部挂在角色对象上,永久存在"设计的一个结构性改进。

### v4: 可复用的通用FSM框架(复用Lesson 1的框架)

直接复用 `01_character_move.py` 里定义的 `GenericFSM`/`GenericTransition` 概念,提供攻击状态机自己的状态清单、事件清单和转移表。`hit_taken`/`hp_zero` 这类"可以打断几乎所有状态"的高优先级事件,在通用表里体现为"在每一个非终态状态下都注册了一条指向Staggered/Dead的转移",这提示了一个实践技巧:**当你发现某个事件需要在几乎所有状态下都注册同样的转移时,要么用代码循环批量生成这些表项(而不是手写5遍),要么就是分层FSM该出场的信号——本课先用批量生成表项的方式处理,Lesson 4会展示当"高优先级打断事件"和"阶段/子状态的组合"进一步复杂化后,分层FSM如何从根本上简化这个问题。**

完整代码见同目录 `02_character_attack.py`。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**

核心证据是Step 3那张表:同一个 `attack_pressed` 事件,在不同状态/不同子阶段下有三种完全不同的处理方式(触发攻击 / 排队 / 忽略)。如果不用状态机思维,直觉写法往往是在输入处理代码里堆一串条件:

```python
if attack_pressed:
    if state in (IDLE, MOVING):
        start_attack()
    elif state == ATTACKING and combo_window_open:
        combo_queued = True
    # 否则什么都不写,靠"没处理"来表示忽略
```

这种写法的问题是:"忽略"到底是"故意设计成忽略"还是"漏写了一个分支",从代码上完全无法区分,容易在后续维护里被误当成bug"修复"。FSM(尤其是v2的显式转移表)强制你把"忽略"也显式地表达出来(哪怕只是表里没有条目+一个默认兜底日志),复查转移表时一眼能看出规则是否完整,而不是靠读散落的if猜测。

**什么情况下FSM反而是负担?**

如果这个游戏的攻击系统**只有一段攻击、没有连击、没有硬直反打**,那么整套状态机可以简化成一个布尔值 `is_attacking` + 一个计时器,不需要正式的FSM框架。本课引入FSM的性价比来自于"连击排队 + 多种打断优先级"这两个真实存在的复杂度,如果这两者都不存在,提前上马State Pattern/通用框架就是过度设计。

**什么时候不应该使用FSM?通用判断标准,以及本案例是否接近这个边界**

通用标准:当"允许哪些转移"这件事**因为太多特例而无法用一张有限的表格穷举**,即需要写"除了A、B、C这几种情况外都允许"这类否定式规则,并且这些特例会随功能增加持续变积,这时候继续套FSM会让转移表本身变得比if-else还难读。本案例目前**没有触及这个边界**——所有转移仍能被Step 4那张表完整穷举。但如果后续要加入"格挡反击"“完美闪避后的处决连击”“武器切换时保留连击段数”等设计,`attack_pressed` 一个事件在不同状态组合下的分支会指数级增长,这就是这套单层攻击FSM开始逼近边界的信号——那时应该考虑把"攻击"本身拆成一台独立的子状态机(连击段1/段2/段3各是子状态),嵌套在角色总状态机的 `Attacking` 状态内部,这正是Lesson 4要系统讲解的分层思路的一个预告。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 同一个按键在同一个状态内,可能有"立即生效/排队等待/彻底忽略"三种截然不同的结局 → 需要显式区分,不能只用一个if
✓ "忽略"和"排队"的区别: 忽略=什么都不记录;排队=记录成数据,等未来某个事件发生时被读取使用
✓ "不可打断"从来不是绝对的,几乎总有比常规输入更高优先级的事件(受击/死亡)能打断它
✓ 只在某个状态内部才有意义的计时窗口/计数器(连击窗口、连击段数),应该作为该状态的内部数据,不要提升成独立状态
✓ 当同一个高优先级事件需要在几乎每个状态下都注册相同的转移时,是分层FSM该登场的早期信号
→ 应该考虑FSM
```

## Step 9: 迁移训练题

1. **格挡/招架系统**:角色可以按住格挡键进入防御姿态(移动速度大幅降低但可以缓慢移动),期间如果精确地在对方攻击命中前的极短时间窗口内松开并重新按下格挡键(招架),会触发一次短暂的"完美格挡"效果(短暂无敌+对方硬直),否则只是普通格挡(减少伤害但角色自身也会有轻微后退硬直)。如果格挡期间被攻击直接命中"防御不能格挡的重击",会被直接打成硬直,格挡姿态被强制取消。

2. **蓄力攻击系统**:按住攻击键会进入"蓄力"阶段,蓄力时间越长,松开后打出的攻击伤害和范围越大,分为"未蓄力(轻攻击)""蓄力1段""蓄力2段(最大)"三个阶段;蓄力期间移动速度降为0;如果蓄力期间被攻击命中,蓄力立即中断并进入硬直,不会打出任何攻击;蓄力超过一定时间没有松开,会自动打出最大蓄力攻击(不需要玩家主动松开)。

3. **闪避翻滚系统**:角色按下闪避键会执行一段短暂的翻滚位移,翻滚前段(起始0.2秒)享有完全无敌帧,翻滚后段没有无敌但仍然锁定输入直到翻滚动作完全结束;翻滚期间如果连续快速按闪避键,只有翻滚彻底结束后再按下的才会触发新的一次翻滚,翻滚过程中重复按键应该被忽略;某些"重击"类攻击被设计为可以无视翻滚的无敌帧直接命中角色。

## 今天真正学会的一句话

**"不可打断"描述的是相对优先级,不是绝对的锁死——判断一个状态是否要接收某个事件,先问"这个事件的优先级是否高于当前状态想要保护的连续性",而"忽略"和"排队"的选择,取决于这次被拒绝的输入,未来是否还有意义被重新拿出来使用。**
