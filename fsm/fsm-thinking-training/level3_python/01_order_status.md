# Lesson 01: 电商订单状态 (Level 3 - Python工程场景)

## Step 1: 是否适合FSM

先别看结论,逐条自己检查一遍这五个特征,再往下看分析。

**是否存在有限状态?**

一个订单从创建到结束,能处于的"阶段"是可以穷举的:待支付、已支付、已发货、已完成、已取消、退款中、已退款。不存在"介于已支付和已发货之间的第三种模糊状态"——运营系统里订单永远只能是这七种之一,不多不少。这满足"有限"。

**是否依赖历史状态?**

依赖,而且依赖得很明确。"退款中"这个状态本身不足以决定退款完成后回到哪里——一个从"已支付"就申请退款的订单(还没发货,买家反悔了),和一个从"已发货"才申请退款的订单(收到货但不满意,退货退款),退款被拒绝后应该回到的地方是不一样的。也就是说,系统必须记住"进入退款前处于哪个状态",这正是"依赖历史"最直接的证据——如果不记录历史,系统甚至不知道退款失败后该把订单退回哪。

**是否由事件驱动?**

是。订单状态几乎不会"自己"变化(除了支付超时这种定时器事件),而是由外部动作触发:买家付款、商家发货、买家确认收货、买家/商家取消、买家申请退款、平台审核退款。这些都是离散的、可命名的事件,不是连续变化的量。

**是否同一个事件在不同状态下行为不同?**

非常典型。"取消"这个操作:在"待支付"状态下,取消是允许的、免代价的(直接变成已取消);但如果订单已经"已发货",几乎所有电商系统都不允许直接"取消"——必须走"申请退款/退货"流程。同一个"CANCEL"意图,在不同状态下必须被处理成完全不同的结果(允许 vs 拒绝并提示走退款)。

**是否存在明确状态切换?**

存在,而且这个切换是电商系统里被审计、被记录、被用来做报表统计的关键字段(订单状态变更日志)。状态切换不是"顺带发生的副作用",而是这个系统建模的核心目标本身。

**结论:**

```
适合FSM: ★★★★★
```

原因:订单状态机是FSM里最标准的教科书案例之一——状态有限且互斥,事件离散,存在历史依赖(退款要回到哪),同一事件在不同状态有不同甚至相反的合法性判断。更重要的是,这是一个**业务状态机**而不是游乐场景状态机,这意味着"非法转移"不是一个可以被忽略的边缘情况,而是必须被系统明确拒绝并报错的核心需求——这正是本课要重点建立的直觉,也是它和 Level 1/Level 2 里那些"物理设备"状态机最大的区别:红绿灯不会有人"非法地"把它扳成不存在的颜色,但订单系统里,一个前端bug、一次重复点击、一个恶意请求,随时可能尝试把"已取消"的订单再次"发货"。FSM的价值不只是"描述合法路径",更是"拒绝一切不在表里的路径"。

## Step 2: 发现状态

先问自己几个引导性问题:

- 订单里有哪些"字段"看起来像状态,但其实只是数据?
- "退款中"和"已退款"是不是同一个状态的两个阶段?
- 一个订单能不能同时处于两个状态?

**思考过程:**

打开一个真实的订单模型,你大概会看到这些字段:`order_id`、`amount`(金额)、`shipping_address`(收货地址)、`created_at`、`status`、`fail_reason`......第一个陷阱出现了:**金额和收货地址不是状态,是数据**。它们的值会变(比如改地址),但改变它们并不代表订单"切换"到了另一个阶段——它们和"待支付/已发货"完全不是一个维度的东西。判断标准很简单:状态描述的是"这个订单现在处于生命周期的哪个阶段,阶段决定了接下来能做什么操作";数据描述的是"这个订单的属性值是什么,不直接决定接下来能做哪些操作类别"。金额多少不影响"能不能发货"这个操作类别是否合法,但"待支付"还是"已支付"直接决定"发货"这个操作是否合法。

第二个陷阱:"退款中"和"已退款"是不是该合并成一个状态,靠一个 `refunded: bool` 字段区分阶段?不应该。"退款中"和"已退款"在业务上是两个允许的操作集合完全不同的阶段——"退款中"状态下,系统在等待平台/银行处理结果,这时买家不能做任何操作,商家能做的只有"批准"或"拒绝";"已退款"是终态,谁都不能再对这个订单做任何操作。如果用一个bool字段叠加在别的状态上,你会发现"已发货 + refunding=true"和"已支付 + refunding=true"要各自处理一遍分支逻辑,状态数其实是隐式地翻倍了,只是没有被显式建模出来——这是一个常见的"伪装成数据的状态"陷阱,应该拆成显式状态。

第三个问题:能不能同时处于两个状态?不能,而且这正是订单状态机"互斥性"的核心保证——一个订单要么是待支付,要么是已支付,不存在"半支付"的订单(部分支付在真实系统里通常也是走"待支付"状态,靠金额字段记录已付比例,状态本身依然是互斥的单一值)。

**确定的状态清单:**

| 状态 | 说明 | 互斥性 | 持续性 |
|------|------|--------|--------|
| `PENDING_PAYMENT`(待支付) | 订单已创建,等待买家付款 | 与其余状态互斥 | 有时限(超时会自动取消) |
| `PAID`(已支付) | 买家已付款,等待商家发货 | 互斥 | 持续到发货或退款申请 |
| `SHIPPED`(已发货) | 商家已发货,等待买家确认收货 | 互斥 | 持续到确认收货或退款申请 |
| `COMPLETED`(已完成) | 买家已确认收货,交易结束 | 互斥,终态 | 永久 |
| `CANCELLED`(已取消) | 订单在支付前被取消或超时 | 互斥,终态 | 永久 |
| `REFUNDING`(退款中) | 退款申请已提交,等待审核 | 互斥 | 持续到审核完成 |
| `REFUNDED`(已退款) | 退款审核通过,交易以退款结束 | 互斥,终态 | 永久 |

## Step 3: 寻找事件

引导性问题:

- "买家点击确认收货"和"系统判定超时自动确认"算同一个事件吗?
- "取消"在待支付状态下和已发货状态下,应该是同一个事件触发不同转移,还是干脆是两个不同的事件?
- 收到一个当前状态不允许的事件(比如对"已取消"的订单调用"发货"),系统该怎么反应?

**分析过程:**

先区分三类东西,这是本课最容易混淆的地方:

1. **动作(Action)**:转移发生时顺带执行的副作用,比如"发送短信通知买家""扣减库存""记录审计日志"。动作不改变状态本身,它是转移的结果,不是转移的原因。
2. **真正触发转移的事件(Event)**:买家的付款回调到账、商家点击"发货"、买家点击"确认收货"、买家/商家发起"取消"、买家发起"申请退款"、平台"审核通过退款"、平台"拒绝退款"、支付超时定时器触发。这些都会让 `status` 字段的值发生跳变。
3. **应忽略/应拒绝的非法输入**:对一个"已完成"的订单调用"取消"接口,对一个"待支付"的订单调用"确认收货"接口——这些不是事件,而是**不在当前状态允许列表里的请求**,必须被系统识别并拒绝,而不是静默地什么都不做(静默忽略在这里是危险的:如果调用方以为操作成功了,却什么都没发生,会导致上下游数据不一致,比如物流系统以为订单已取消所以放弃发货,但订单系统其实还留在"已发货")。

第一个引导问题的答案:"买家确认收货"和"系统超时自动确认"(很多平台发货后N天无操作自动确认收货)在**结果**上是一样的转移(`SHIPPED -> COMPLETED`),但在事件语义上,把它们当成两个不同的事件(`CONFIRM_RECEIPT` 和 `AUTO_CONFIRM_TIMEOUT`)通常更清晰,因为它们的**触发来源**不同(用户操作 vs 系统定时器),在日志和审计上你会想区分"用户主动确认"还是"超时自动确认"。本课为了聚焦核心转移逻辑,把二者合并处理,但在真实系统里建议拆开。

第二个引导问题的答案:"取消"在"待支付"和"已发货"下不应该是同一个事件的两种结果,而应该设计成:`CANCEL` 事件只在 `PENDING_PAYMENT` 状态下合法(直接取消,不涉及资金);已经支付/发货的订单,买家想要的操作在业务语义上根本不是"取消",而是"退款"——所以已支付/已发货状态下,买家发起的应该是 `REQUEST_REFUND` 事件,而不是复用 `CANCEL`。这不是文字游戏,而是因为"取消"和"退款"背后触发的下游动作完全不同(取消不涉及资金流转,退款涉及资金流转和风控审核),用同一个事件名会诱使实现者在一个函数里塞进两套完全不同的业务逻辑分支,这正是"该拆事件却没拆"的典型坑。

第三个引导问题的答案(本课重点):必须**拒绝并明确报错**,不能静默忽略。具体反应方式取决于调用层:如果是内部服务间调用,应该抛出一个明确的异常(比如 `InvalidTransitionError`),让调用方的代码在编译期/测试期就能感知到"这条路径没处理";如果是暴露给外部的HTTP API,应该转换成一个明确的错误响应(比如 `409 Conflict`,并在body里说明"订单当前状态为已取消,不能执行发货操作"),绝不能返回200却什么都没做——那会让前端和商家都以为操作成功了。

**确定的事件清单:**

| 事件 | 说明 |
|------|------|
| `PAY` | 买家完成支付(支付网关回调) |
| `PAYMENT_TIMEOUT` | 待支付超时,系统定时任务触发 |
| `SHIP` | 商家发货 |
| `CONFIRM_RECEIPT` | 买家确认收货(或超时自动确认,本课合并处理) |
| `CANCEL` | 买家/商家取消订单(仅待支付阶段合法) |
| `REQUEST_REFUND` | 买家申请退款/退货退款 |
| `APPROVE_REFUND` | 平台/商家审核通过退款 |
| `REJECT_REFUND` | 平台/商家审核拒绝退款,订单回到申请退款前的状态 |

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| `PENDING_PAYMENT` | `PAY` | `PAID` | 记录支付时间,扣减库存 |
| `PENDING_PAYMENT` | `PAYMENT_TIMEOUT` | `CANCELLED` | 记录取消原因="支付超时",释放库存预占 |
| `PENDING_PAYMENT` | `CANCEL` | `CANCELLED` | 记录取消原因="用户取消",释放库存预占 |
| `PAID` | `SHIP` | `SHIPPED` | 记录发货时间,生成物流单号 |
| `PAID` | `REQUEST_REFUND` | `REFUNDING` | 记录 `pre_refund_state=PAID`,通知平台审核 |
| `SHIPPED` | `CONFIRM_RECEIPT` | `COMPLETED` | 记录完成时间,资金结算给商家 |
| `SHIPPED` | `REQUEST_REFUND` | `REFUNDING` | 记录 `pre_refund_state=SHIPPED`,通知平台审核,提示买家退货 |
| `REFUNDING` | `APPROVE_REFUND` | `REFUNDED` | 执行退款到账,记录退款时间 |
| `REFUNDING` | `REJECT_REFUND` | 回到 `pre_refund_state` | 记录拒绝原因,通知买家 |

**非法转移处理方式(必须覆盖,不能省略):**

任何不在上表中的 `(当前状态, 事件)` 组合都是非法转移,包括但不限于:

- 对 `PENDING_PAYMENT` 调用 `SHIP` / `CONFIRM_RECEIPT`(还没付款就想发货或确认收货)
- 对 `PAID` 调用 `CANCEL`(已支付订单不能走"取消",只能走"退款")
- 对 `COMPLETED` / `CANCELLED` / `REFUNDED` 调用**任何**事件(这三个是终态,终态的定义就是"不再接受任何转移")
- 对 `REFUNDING` 调用 `PAY` / `SHIP` / `CANCEL`(退款审核期间,原交易流程被冻结)

处理方式:抛出 `InvalidTransitionError`(内部调用)或返回明确的错误状态码+说明(对外API),错误信息里必须包含"当前状态"和"被拒绝的事件",方便排查是前端重复提交、还是有代码绕过了状态检查直接改库。

## Step 6: Python实现

### v1: Enum + match-case,一个类里手写转移逻辑

最直接的实现方式:用 `Enum` 表示状态,`Order` 类里每个"动作"方法(`pay()`、`ship()`……)都自己用 `match` 判断当前状态是否合法,合法就跳转,不合法就抛异常。

这一版的价值在于**能跑起来、能立刻看懂**,缺点也很明显:转移规则散落在N个方法里,每加一个新状态或新事件,就要去检查所有相关方法有没有漏改;而且"合法状态列表"是硬编码在 `if`/`match` 条件里的,想审计"待支付到底能转移到哪几个状态",得把所有方法读一遍才能拼出完整答案,没有一个地方能"一眼看全"。

### v2: Transition Table(数据驱动)

把"合法转移"整理成一张显式的表:`dict[(State, Event), State]`,外加一张 `Action` 表。转移方法变成通用的一句话:"查表,查不到就抛 `InvalidTransitionError`"。

相比v1的改进:转移规则第一次变成了**可以被打印、被审计、被单独测试**的数据,而不是隐藏在过程式代码的分支里。想知道"待支付能转移到哪些状态",直接把表按 `PENDING_PAYMENT` 过滤出来就是答案,不需要读代码。非法转移的处理也统一到了一个地方(查表失败),不会有"某个方法忘了做校验"的遗漏风险。

### v3: State Pattern(每个状态是一个类)

给每个状态定义一个类,实现自己的 `on_pay()`、`on_ship()` 等方法,默认实现直接拒绝,只有该状态真正支持的事件才被重写成"允许"。

适用场景:当**同一个状态下的转移逻辑本身就很复杂**(比如"退款中"状态还要区分退款金额是否超过限额、是否需要人工审核等一堆子逻辑),把这些逻辑封装进对应状态类里,比在一张扁平的转移表里塞一堆 `Action` 函数更容易维护和测试。对于订单状态机这种规则本身不算复杂、但状态多、转移条件清晰的场景,State Pattern 略显"过度设计",v2的转移表通常够用——这里展示v3是为了让你在真的遇到"每个状态的处理逻辑本身就是一大段业务代码"时,知道有这个选项。

### v4: 通用FSM框架片段

抽象出可复用的 `State` / `Event` / `Transition` / `FSM` 基类,让任何具体状态机(不只是订单)都能通过声明转移表来接入。

什么时候值得引入框架:当你的系统里**不止一个**地方需要状态机(订单状态机、退款单状态机、售后工单状态机……),且它们都需要同样的"非法转移报错""转移日志""转移前后钩子(before/after transition hook)"能力时,抽出一个通用框架能避免每个状态机都重新发明一遍相同的校验逻辑。如果只有一个状态机,直接用v2的转移表就够了,过早抽象框架是不必要的复杂度。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**

在订单系统的真实业务代码里,状态判断的 `if` 语句会散落在完全不同的模块里:支付回调处理器里有一处判断"当前必须是待支付才能改成已支付",发货接口里有另一处判断"当前必须是已支付才能发货",退款接口里又有一处判断"当前必须是已支付或已发货才能退款"。这些判断分散在不同文件、由不同人在不同时间写,极容易出现:某个新加的接口(比如"商家改地址")忘了检查订单状态,导致一个已完成的订单还能被改地址;或者两处判断对"能不能取消"的理解不一致(一处漏检查了 `REFUNDING` 状态)。FSM把"所有合法转移"集中到一张表里,任何新增接口在写之前都会先看这张表,漏掉某个状态组合会在表里"看得出来"(表里没有对应的行),而不是要等到线上出问题才发现某个if分支漏了。

**什么情况下FSM反而是负担?**

如果订单只有"未支付"和"已支付"两种状态,转移规则就一条(`PAY`),那么定义一整套 `Enum` + 转移表 + 异常类型,复杂度远超过直接写一个 `if order.paid: raise ...`。FSM的收益在状态数和转移规则数变多之后才会显现,状态少于3~4个、转移规则少于5条时,引入完整的FSM框架(尤其是v3/v4这种级别)通常是过度设计。

**什么时候不应该使用FSM?**

当"状态"之间的转移不是由离散事件决定,而是由连续变化的业务规则决定时(比如根据订单金额、用户等级、促销活动动态计算下一步能做什么,规则本身经常变且和"状态"关系不大),用规则引擎或策略模式可能比FSM更合适——因为FSM假设"下一步是什么"主要取决于"(当前状态, 事件)"这个组合,而不是取决于一堆动态业务参数的组合。当转移条件本质上是"任意布尔表达式的组合"而不是"事件"时,勉强套FSM会让转移表里出现大量重复的伪状态。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 状态之间互斥,某个时刻只能是其中一个
✓ 转移由外部事件触发,而不是数据的连续变化
✓ 同一事件在不同状态下的合法性/结果不同
✓ 存在"历史依赖"(不知道从哪来,就不知道该去哪)
✓ 非法转移必须被明确拒绝,而不是静默忽略——这是业务FSM的生命线
→ 应该考虑FSM
```

## Step 9: 迁移训练题

以下三个场景,自己先判断"是否适合用FSM建模",再决定要不要往下深挖状态和事件——不要跳过这一步直接看下一课。

1. **优惠券生命周期**:一张优惠券可能处于"未使用"、"已使用"、"已过期"、"已作废(被系统风控冻结)"。用户下单时使用优惠券,支付失败订单取消时优惠券要"退回"给用户,优惠券本身也有有效期,过期后即使没用过也不能再用。这个场景该用FSM建模吗?

2. **文件上传任务**:前端触发一个大文件分片上传任务,任务会经历"排队等待""上传中""暂停""失败重试""已完成"这些阶段,用户可以随时点击暂停/继续,网络断开会自动进入失败重试,重试超过N次后任务标记为"彻底失败"。这个场景该用FSM建模吗?

3. **审批流(报销单)**:一张报销单提交后要经过"直属主管审批""财务审批""出纳打款"三级流程,任何一级可以"驳回"打回给提交人修改后重新提交,也可以"通过"进入下一级,金额超过某个阈值还需要多加一级"总监审批"。这个场景该用FSM建模吗?(提示:留意"三级/四级审批"这种"根据数据决定要走几步"的情况,该怎么在状态设计里体现)

## 今天真正学会的一句话

**判断一个业务模块要不要用FSM,先问"收到一个不该发生的操作,系统现在会怎样"——如果答案是"什么都不会发生,数据库悄悄地没被改"或者更糟"数据库被改成了不一致的状态",那么这里缺的不是更多if,而是一张明确列出所有合法转移、并且把剩下所有组合都当作错误拒绝的转移表。**
