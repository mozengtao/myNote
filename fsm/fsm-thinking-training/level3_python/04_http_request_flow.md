# Lesson 04: HTTP请求处理流程 (Level 3 - Python工程场景)

> 这一课和前三课不一样:前三课的结论都比较干脆("适合",而且星级不低)。这一课的目的是训练一种更难的直觉——**识别"看起来复杂、但其实只是一条固定顺序流程"和"看起来简单、但确实需要按事件分支/循环的状态机"之间的边界**。请不要用前三课的思维定式来套这一课,先老老实实走一遍五个特征检查。

## Step 1: 是否适合FSM

先问自己一个更基础的问题:**你脑子里想的"HTTP请求处理流程"到底是哪个粒度?** 大多数人第一反应画出来的是这样一条线:

```
接收请求 -> 解析 -> 路由 -> 中间件(鉴权等) -> 业务处理 -> 生成响应 -> 发送响应
```

如果这就是你脑子里的全部内容,先看看这条线本身有没有FSM的特征:

**是否存在有限状态?**

严格说,"接收请求""解析""路由"……确实可以枚举,数量有限。但这里要警觉:**这些"阶段"和"状态"不是一回事**。它们更像是一条流水线上的工位,数据(这次请求)按固定顺序依次经过每个工位,而不是"这个请求现在处于某个状态,不同的事件会把它导向不同的下一个工位"。

**是否依赖历史状态?**

不依赖。"路由"这一步要不要执行、路由到哪里,只取决于这次请求本身的URL/方法,不取决于"这个请求之前经历过哪些阶段"。这是这条主线和前三课最大的不同:订单退款要不要回到 `PAID` 还是 `SHIPPED` 依赖历史;这条主线里每一步都只往前走一次,不存在"根据历史决定下一步去哪"的情况。

**是否由事件驱动?**

不是——如果只看"成功的一次请求",每一步都是上一步自动、确定地引发下一步,中间没有"外部事件"来决定走向哪个分支。这更像是函数调用的顺序执行(`parse(); route(); handle(); render();`),而不是"等待一个事件,再根据事件决定下一步"。

**是否同一个事件在不同状态下行为不同?**

在这条主线里,根本没有"同一个输入在不同阶段有不同解读"这种情况——每个阶段只会被走一次,不会有"路由阶段"和"业务处理阶段"都需要对同一个事件做反应的情况。

**是否存在明确状态切换?**

有阶段推进,但"阶段"更适合叫"步骤"——这条主线不会分支、不会循环、也不会因为外部事件被打断后走向完全不同的路径(至少在"只考虑成功路径"的前提下)。

**如果只看这条主线,结论会是:这基本上是一条Pipeline(顺序流水线),不是FSM。** 用状态模式或状态转移表来建模一条永远从头走到尾、不分支不循环的顺序流程,是过度设计——用函数组合/责任链模式(Chain of Responsibility)或者简单的顺序调用就足够清晰,还更容易读。

**但故事没有结束。** 现在把"只考虑成功路径"这个假设去掉,回到真实的服务端场景,继续检查:

- 如果解析请求头时发现格式错误,会发生什么?—— 直接跳过路由和业务处理,短路到"生成错误响应"。这是一次**分支**,不是顺序流程能表达的。
- 如果鉴权中间件发现没有权限,会发生什么?—— 同样短路,跳过业务处理,直接生成401响应。又一次分支。
- 如果业务处理过程中,客户端提前断开了连接(用户关闭了浏览器标签),会发生什么?—— 这时"生成响应"这一步可能已经没有意义了,而且如果业务处理里开了数据库事务,还需要做回滚清理——这个反应**取决于请求当前处于流水线的哪个阶段**(还在处理中被断开,和已经在发送响应时被断开,清理动作是不同的),这正是"同一个事件在不同状态下行为不同"。
- 如果这是一个HTTP/1.1的持久连接(Keep-Alive),这次请求处理完,连接不会关闭,而是**循环**回到"等待下一个请求"——这是一个真正的循环,不是顺序流程能表达的。
- 如果处理超时,会发生什么?—— 又是一次由"定时器事件"触发的分支。

**这里出现了问题的两个不同粒度:**

1. **单次请求"从解析到渲染"的业务逻辑主线**:确实基本是顺序流程,不需要FSM。
2. **一条连接上,请求的接收/处理/响应/复用/异常中断的完整生命周期**:这里出现了真正的分支、循环、以及"同一事件在不同阶段有不同后果",这部分具备FSM的特征。

**结论:**

```
适合FSM: ★★★☆☆ (部分适合,取决于你在哪个粒度建模)
```

原因:如果你要建模的是"一次请求business逻辑顺序执行的那条主线",FSM是不必要的负担,用Pipeline/责任链模式更合适,硬套FSM会引入一堆只会被走一次、不会分支也不会被重新进入的"伪状态",这是本课想让你识别的**反面案例**——不是所有"多步骤流程"都是状态机,"多步骤"只是必要条件,"事件驱动的分支/循环/历史依赖"才是充分条件。但如果你要建模的是"服务端如何管理一条连接上请求的完整生命周期"(接收、处理中断、超时、keep-alive复用),这部分确实有分支、有循环、有"同一事件不同后果",值得用FSM。这一课不给"要不要打五星"的简单答案,而是给你一个更重要的能力:**同一个业务名词("HTTP请求处理"),背后可能同时藏着一段不需要FSM的顺序流程和一段需要FSM的生命周期管理,建模前先把粒度拆清楚,不要笼统地问"这个东西该不该用FSM"。**

## Step 2: 发现状态

既然结论是"分层建模",Step 2开始我们只针对"值得用FSM的那一层"(请求/连接生命周期)展开,不再纠缠"顺序主线"那一层(它不需要状态清单,一个函数调用链表就是它的全部)。

引导性问题:

- "正在解析请求体"和"正在路由"要不要分成两个状态?
- HTTP状态码(200、404、500)是状态吗?
- "连接"和"这次请求"是同一个状态机,还是要分开?

**思考过程:**

第一个问题:本课**刻意选择不拆分**"解析""路由""中间件""业务处理"这几个子步骤为独立状态,而是把它们合并成一个粗粒度的 `PROCESSING` 状态。原因是:这几个子步骤之间的推进本身依然是顺序流程(没有分支/循环/历史依赖),真正需要FSM关心的是"`PROCESSING` 这个大阶段作为一个整体,在遇到错误/客户端断开/超时这些事件时该怎么反应",而不是"`PROCESSING` 内部具体走到哪个子步骤"——如果你的系统需要对"卡在鉴权中间件"和"卡在业务处理"做出不同的超时反应,那确实值得把 `PROCESSING` 再拆细,但这是一个具体工程判断,不是本课固定要下的结论,这里选择合并是为了聚焦"生命周期层面"的FSM特征,避免把顺序流程的细节也搬进状态清单里污染判断。

第二个问题:HTTP状态码(200/404/500)**不是**状态机的状态,是数据——它是"生成响应"这个动作产生的一个业务结果值,存在 `RESPONDING`/`ERROR` 阶段的response对象里,不影响"接下来能不能继续处理下一个请求"这类结构性问题。用一个精确的判断标准:状态机的"状态"要回答"接下来哪些事件是合法的、会导致行为不同",状态码不回答这个问题(不管是200还是404,发送响应之后都同样进入"已完成,等待复用或关闭"这一步)。

第三个问题,这一课的关键辨析:**"连接"和"这次请求"是两层生命周期,但为了简化教学,本课把它们合并成一个状态机**,用 `DONE` 状态之后的 `KEEP_ALIVE_REUSE` 事件让状态机"循环回到 `IDLE`",来表达"一条连接上处理下一个请求"这件事。在更严格的工程实现里(比如一个真正的异步HTTP服务器),通常会分成两层:"连接级状态机"(建立、保持、关闭,类似Lesson 03)和"请求级状态机"(每次新请求都是一个新的、独立的请求状态机实例,处理完就销毁),连接级状态机每次收到新请求就"孵化"一个新的请求状态机。本课为了避免引入两个状态机之间协作的复杂度,选择了合并版本,但你需要知道:**真实系统更可能是分层的,合并版本是本课为了聚焦教学重点做的简化**。

**确定的状态清单(合并版,连接与请求生命周期):**

| 状态 | 说明 | 互斥性 | 持续性 |
|------|------|--------|--------|
| `IDLE`(空闲) | 连接已建立,等待下一个请求到达 | 互斥 | 直到请求到达 |
| `RECEIVING`(接收中) | 正在读取请求行/请求头/请求体 | 互斥 | 直到接收完成、超时或客户端断开 |
| `PROCESSING`(处理中) | 路由+中间件+业务处理(内部仍是顺序流程,本课不再细分) | 互斥 | 直到处理完成、出错或客户端断开 |
| `RESPONDING`(响应中) | 正在生成/写出响应数据 | 互斥 | 直到发送完成或客户端断开 |
| `DONE`(本次完成) | 一次请求处理完毕,等待决定复用或关闭 | 互斥 | 瞬时,立刻转向 `IDLE` 或 `CLOSED` |
| `ERROR`(异常) | 发生解析错误/业务异常/超时/客户端断开,准备生成错误响应或直接关闭 | 互斥 | 直到错误响应发出或连接关闭 |
| `CLOSED`(已关闭) | 连接终止,终态 | 互斥,终态 | 永久 |

## Step 3: 寻找事件

引导性问题:

- "客户端断开连接"这一个事件,在 `RECEIVING`、`PROCESSING`、`RESPONDING` 三个阶段的合理反应是不是应该一样?
- "处理超时"和"处理出错"是不是同一个事件?
- 一条Keep-Alive连接处理完第一个请求后,"复用"和"关闭"分别由谁决定?

**分析过程:**

1. **动作**:记录访问日志、写响应头、执行业务SQL、清理临时资源——这些不改变状态,是转移或阶段内部执行的副作用。
2. **事件**:请求到达(`REQUEST_ARRIVED`)、请求接收完整(`REQUEST_COMPLETE`)、处理完成(`PROCESSING_COMPLETE`)、响应发送完成(`RESPONSE_SENT`)、超时(`TIMEOUT`)、客户端断开(`CLIENT_DISCONNECTED`)、发生错误(`ERROR_OCCURRED`)、决定复用连接(`KEEP_ALIVE_REUSE`)、决定关闭连接(`CONNECTION_CLOSE`)。
3. **应拒绝/需要谨慎处理的情况**:`IDLE` 状态收到"处理完成"这种只应该在 `PROCESSING` 阶段出现的事件——这通常说明状态机实现有bug(比如异步回调用错了连接对象)。

第一个引导问题的答案是本课最重要的辨析点:**不应该一样**,这正是"同一事件、不同状态下行为不同"的典型例子。`RECEIVING` 阶段客户端断开,通常什么业务资源都还没分配,直接关闭连接、丢弃这次请求即可,不需要额外清理;`PROCESSING` 阶段客户端断开,业务逻辑可能已经开启了数据库事务、拿到了某些锁,必须先执行回滚/释放资源,再关闭连接,否则会造成资源泄漏或数据不一致;`RESPONDING` 阶段客户端断开,响应可能已经写出去了一部分(比如分块传输的流式响应),需要终止还在进行的写入操作并释放输出流,清理动作又不一样。三个阶段收到同一个 `CLIENT_DISCONNECTED` 事件,合理的后续处理(是否要回滚、要不要停止某个写流)完全不同,这正是必须显式建模成状态机、而不是用一个全局 `if client_disconnected: cleanup()` 来"通用处理"的原因——通用处理很容易漏掉某个阶段特有的清理动作。

第二个引导问题:**不是同一个事件**,虽然两者最终都导向 `ERROR` 状态,但触发原因和携带的信息不同(超时通常没有异常堆栈,只有"等待时长超过阈值"这个事实;出错通常有明确的异常对象和堆栈),把它们分开有利于监控和排查——如果合并成一个笼统的 `FAILURE` 事件,日志里就分不清"这次是慢查询卡住了"还是"代码抛了异常"。

第三个引导问题:"复用"还是"关闭"由多方面因素共同决定——客户端请求头里的 `Connection: keep-alive`/`close`、服务端配置的最大连接空闲时间、服务端配置的单连接最大请求数上限。这个决定的过程本身不是状态机要关心的细节(那是一个独立的策略判断函数),状态机只需要关心"决定做出之后,触发的是 `KEEP_ALIVE_REUSE` 还是 `CONNECTION_CLOSE` 这两个不同事件,分别导向 `IDLE`(循环)还是 `CLOSED`(终止)"。

**确定的事件清单:**

| 事件 | 说明 |
|------|------|
| `REQUEST_ARRIVED` | 新请求数据开始到达 |
| `REQUEST_COMPLETE` | 请求行/头/体接收完整 |
| `PROCESSING_COMPLETE` | 路由+中间件+业务处理全部完成 |
| `RESPONSE_SENT` | 响应完整发送给客户端 |
| `TIMEOUT` | 某阶段等待超过配置的时长 |
| `CLIENT_DISCONNECTED` | 客户端提前断开连接 |
| `ERROR_OCCURRED` | 处理过程中出现未捕获异常 |
| `KEEP_ALIVE_REUSE` | 决定复用当前连接处理下一个请求 |
| `CONNECTION_CLOSE` | 决定关闭当前连接 |

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| `IDLE` | `REQUEST_ARRIVED` | `RECEIVING` | 分配请求上下文,开始计时 |
| `RECEIVING` | `REQUEST_COMPLETE` | `PROCESSING` | 请求解析完毕,进入路由+业务处理 |
| `RECEIVING` | `TIMEOUT` | `ERROR` | 记录"接收超时",准备408响应 |
| `RECEIVING` | `CLIENT_DISCONNECTED` | `CLOSED` | 直接释放资源,无需回滚(还没进入业务处理) |
| `PROCESSING` | `PROCESSING_COMPLETE` | `RESPONDING` | 业务处理完毕,开始生成响应 |
| `PROCESSING` | `ERROR_OCCURRED` | `ERROR` | 记录异常堆栈,准备500响应 |
| `PROCESSING` | `CLIENT_DISCONNECTED` | `ERROR` | 回滚未完成的事务,释放已获取的资源 |
| `RESPONDING` | `RESPONSE_SENT` | `DONE` | 记录访问日志(状态码、耗时) |
| `RESPONDING` | `CLIENT_DISCONNECTED` | `ERROR` | 终止未完成的响应写入,释放输出流 |
| `ERROR` | `RESPONSE_SENT` | `DONE` | 记录访问日志(错误状态码、耗时) |
| `DONE` | `KEEP_ALIVE_REUSE` | `IDLE` | 重置请求上下文,循环等待下一个请求 |
| `DONE` | `CONNECTION_CLOSE` | `CLOSED` | 释放连接资源 |
| `ERROR` | `CONNECTION_CLOSE` | `CLOSED` | 释放连接资源(严重错误通常不再keep-alive) |

**非法转移处理方式(必须覆盖):**

- `IDLE` 状态收到 `REQUEST_COMPLETE` / `PROCESSING_COMPLETE` / `RESPONSE_SENT`:拒绝,记录严重日志——这些事件只应该在对应的中间阶段出现,`IDLE` 收到它们几乎肯定意味着"上一个请求的回调用错了连接对象",是需要立刻修的实现bug,绝不能静默吞掉继续运行,否则可能把上一个请求的响应写进这一个连接的下一个请求里。
- `CLOSED` 状态收到任何事件:拒绝——连接已经终止,任何迟到的事件都应该被丢弃并记录一条警告日志(而不是抛出让整个服务器崩溃的异常,这里的"拒绝"更接近"安全地丢弃并告警",这是和订单/登录课"抛异常给调用方"略有不同的处理策略,因为触发方通常是一个已经不再被任何代码持有引用的旧连接对象的迟到回调,没有"调用方"可以捕获这个异常)。
- `DONE` 状态收到 `REQUEST_ARRIVED`:拒绝——必须先经过复用判断走到 `IDLE`,才能接收新请求,不能跳过这个决策步骤。

## Step 6: Python实现

> 提醒:下面的代码只实现"值得用FSM的那一层"(请求/连接生命周期状态机)。Step 1里提到的"解析->路由->中间件->业务处理"这条顺序主线,不需要状态机,代码里用一个普通的函数调用序列表示 `PROCESSING` 状态内部发生的事情即可——这是刻意的对照,提醒你顺序流程不需要为了"看起来统一"而硬套状态机写法。

### v1: Enum + match-case

用 `Enum` 表示七个状态,一个 `RequestLifecycleV1` 类的方法对应每个事件,`CLIENT_DISCONNECTED` 事件的处理方法内部用 `match self.state` 展示"同一事件在三个不同阶段执行不同清理动作"这一核心教学点。

### v2: Transition Table

转移表里 `CLIENT_DISCONNECTED` 在 `(RECEIVING, ...)`、`(PROCESSING, ...)`、`(RESPONDING, ...)` 三行分别映射到不同的处理函数(分别对应"无需清理""回滚事务""终止响应流"),清晰地把"同一事件不同后果"变成表里天然分开的三行,不需要在一个函数里用大段 if 区分。

### v3: State Pattern

`ProcessingHandler` 类里可以把"客户端断开时需要回滚事务"这个业务相关的清理逻辑,和 `RespondingHandler` 类里"终止响应流"的清理逻辑完全隔离在两个类里,新增一种资源清理逻辑时,只需要修改对应阶段的状态类,不会不小心影响到其他阶段。

### v4: 通用FSM框架

用同一个 `GenericFSM` 抽象承载这一课的转移表,进一步验证:即使是"部分适合FSM"的场景,一旦确定了值得建模的那一层(生命周期层),它依然可以用和前三课完全相同的通用框架落地——框架的通用性不代表"所有粒度都要用FSM看待",框架只负责"用给定的转移表驱动状态跳转",要不要用它、用在哪个粒度,是Step 1~3的判断结果决定的。

完整代码见 `04_http_request_flow.py`。

## Step 7: 复杂度分析

**为什么FSM比if-else更好(在值得用的那一层)?**

一个真实的HTTP服务端实现,如果没有显式的状态机,"客户端断开时该怎么清理"这类逻辑往往是靠在很多不同的地方各自加 `try/except ConnectionResetError` 来"打补丁"式地处理的——一个负责数据库访问的模块加了一个,一个负责响应流的模块又加了一个,彼此并不知道对方的存在,也没有一个地方能回答"我们到底覆盖了所有可能断开的阶段吗"。用状态机把"当前处于哪个阶段"显式化之后,`CLIENT_DISCONNECTED` 事件在每个阶段该做什么清理,可以被写成一张完整的表,新增一个阶段(比如未来加一个"响应前的最后一次权限复核"阶段)时,能立刻意识到"这个新阶段的断开清理逻辑我还没写"。

**什么情况下FSM反而是负担?**

如果你的HTTP服务端框架(比如某个现成的Web框架)已经在底层帮你处理好了连接生命周期、Keep-Alive、超时、客户端断开检测这些事情,应用代码里写的Handler函数基本只需要关心"顺序主线"那一层(解析好的请求进来,返回一个响应对象出去),这时候应用层完全没必要重新发明这套连接生命周期状态机——框架已经做了。这也是为什么这一课的星级是"部分适合":大多数应用开发者实际接触到的HTTP处理代码,是Step 1里那条"不需要FSM"的顺序主线,生命周期层的FSM通常隐藏在框架/服务器内部,只有你在实现服务器本身、或者需要精细控制超时和资源清理行为时才会直接接触它。

**什么时候不应该使用FSM?**

当"请求处理"指的就是Step 1里那条固定顺序、不分支不循环的业务主线时,不应该用FSM,应该用责任链模式(每个中间件是链上的一个节点,可以选择"继续往下传"或"短路返回")或简单的函数组合——责任链模式已经能优雅表达"鉴权失败就短路"这种分支,不需要为此定义状态和转移表,状态机的"状态携带、历史依赖"的能力在这里根本用不上,是浪费。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 一条只会被走一次、不分支不循环的固定顺序 —— 这是Pipeline,不是FSM
✓ 出现"根据事件短路跳过后续步骤" —— 开始有FSM的味道
✓ 出现"同一事件在不同阶段需要不同的清理/响应" —— FSM信号增强
✓ 出现"处理完一轮之后可能循环回到起点"(如Keep-Alive) —— 真正需要FSM
✓ 同一个业务名词可能同时包含"不需要FSM的主线"和"需要FSM的生命周期管理"两层
  —— 先拆粒度,再分别判断,不要笼统下结论
→ 该不该用FSM,要看你问的是哪一层
```

## Step 9: 迁移训练题

1. **文件上传后的异步处理链**:用户上传一张图片后,系统依次执行"病毒扫描 -> 生成缩略图 -> 提取EXIF信息 -> 上传到对象存储 -> 更新数据库记录",全部成功才算完成,任何一步失败都要重试3次,3次都失败则整个任务标记失败并通知用户。这个"处理链"本身该用FSM建模吗?和本课的"顺序主线"有什么相似或不同?
2. **GraphQL/gRPC流式响应**:一个gRPC服务端流接口,客户端发起一次请求后,服务端会持续推送多条消息,期间客户端可以随时发送"取消"信号,服务端也可能因为内部错误中途终止流,正常情况下流会在发送完所有消息后正常结束。这个场景和本课讨论的"HTTP响应中的客户端断开"有什么相似之处?
3. **中间件链中的重试与熔断**:一个微服务的HTTP客户端在调用下游服务时,配置了"超时重试(最多3次)+熔断器(连续失败5次后熔断60秒,期间直接拒绝请求不再重试)"。这个"重试+熔断"逻辑本身该用FSM建模吗?它和"单次请求该走的顺序步骤"是同一层还是不同层?

## 今天真正学会的一句话

**"这个流程有好几个步骤"不等于"这个流程需要FSM"——真正的判断标准永远是"有没有事件驱动的分支、循环、历史依赖、同一事件不同后果";遇到复杂的业务名词时,先把它拆成"顺序主线"和"生命周期管理"这两层分别判断,不要在一个粒度上强行给出唯一结论。**
