# Lesson 02: 登录流程 (Level 3 - Python工程场景)

## Step 1: 是否适合FSM

**是否存在有限状态?**

一个账户在登录这件事上,能处于的阶段是:未登录(`ANONYMOUS`)、已登录(`AUTHENTICATED`)、已锁定(`LOCKED`)。表面上只有三种,比订单状态机还简单。但先别急着打五星——这一课真正的难点不在"状态数够不够少",而在"哪些东西看起来该是状态、实际上不该是"(下一步会展开)。

**是否依赖历史状态?**

依赖,而且是这一课的核心。"账户会不会被锁定"这件事,不取决于"这一次"登录失败,而取决于"最近连续失败了几次"——这是一个**跨越多次事件、累积出来的历史**。如果不记录历史(失败次数),系统无法判断第5次失败该不该触发锁定。这比订单状态机的历史依赖更"深":订单只需要记住"上一个状态是什么"(一步历史),登录流程需要记住"最近N次同类事件发生了几次"(累积历史)。

**是否由事件驱动?**

是。登录尝试(成功/失败)、主动登出、锁定到期、管理员解锁,都是离散、可命名的事件。

**是否同一个事件在不同状态下行为不同?**

是,而且这里藏着一个容易被忽视的细节:"登录失败"这个事件,在"未登录"状态下,行为其实**不是单一的**——如果失败次数还没到阈值,行为是"计数+1,留在未登录状态";如果失败次数刚好到达阈值,行为是"计数+1,同时跳转到已锁定状态"。这是同一个事件、同一个起始状态,但根据"状态里携带的数据"(失败次数)导致了两种不同的转移结果。这种现象在状态机理论里叫"带守卫条件的转移"(guarded transition),它比订单状态机里"同一事件在不同状态下行为不同"更进一步:**这里是同一状态、同一事件,靠数据决定行为**,严格来说已经不是最初等的"有限状态机"(FSM),而是"扩展状态机"(Extended FSM,状态携带数据、转移可以有条件判断)。这不是缺陷,而是工程实践中几乎所有"安全类"状态机的常态——你要提前建立这个认知,不要以为FSM只能是"纯标签"之间的跳转。

**是否存在明确状态切换?**

存在,而且和订单一样,是需要被审计的:账户被锁定、被解锁,这些都是安全事件,通常要写入安全日志。

**结论:**

```
适合FSM: ★★★★☆
```

原因:三个核心状态清晰互斥,事件离散,存在强烈的历史依赖,同一事件在同一状态下会因数据不同产生不同结果——这些都是FSM的强信号,应该用状态机思维来设计。打四星而不是五星的原因是:这个场景天然需要"扩展状态机"(状态+数据+守卫条件)才能优雅表达,如果生搬硬套"纯FSM不能带数据"的教条(比如试图把"失败1次""失败2次""失败3次"都建模成独立状态),反而会导致状态数随阈值线性膨胀,变成一种反模式。识别"这里需要的是扩展状态机而不是纯FSM"本身就是一种更高阶的识别直觉,这也是这一课想让你建立的认知。

## Step 2: 发现状态

引导性问题:

- "失败次数"是不是一个独立的状态?
- "已登录"和"已登录且是管理员"要不要分成两个状态?
- 账户"已锁定"期间,还有没有必要区分"因为失败次数过多被锁"和"被管理员手动封禁"?

**思考过程:**

第一个陷阱,也是本课最重要的一个:**失败次数(`failure_count`)不是状态,是状态内部携带的数据**。判断依据和订单课一样——它的值变化(从2变到3)本身不代表账户"跳转"到了一个新的、行为完全不同的阶段;账户在失败1次、2次、3次(未到阈值前)的时候,能做的事情是完全一样的("可以继续尝试登录"),唯一变化的是"距离被锁定还有几次机会"这个内部计数。如果强行把"失败1次""失败2次"建成独立状态,你会发现转移表要为每一个计数值单独写一行(`FAIL_1 + LOGIN_FAILURE -> FAIL_2`,`FAIL_2 + LOGIN_FAILURE -> FAIL_3`……),阈值改成10次,状态数就得跟着变成10个——这是状态数应该随"业务阶段"变化,而不是随"一个可以无限增长的计数值"变化的典型反例。正确做法:`ANONYMOUS` 状态本身携带一个 `failure_count: int` 字段,状态跳转前先判断这个数据是否达到阈值(这就是"守卫条件"),不新增状态。

第二个问题:"已登录"要不要按角色再拆细?不需要——除非"是不是管理员"这件事本身会导致**登录流程**的转移规则发生变化(比如管理员登录后必须二次验证才能算真正"已登录")。如果只是登录之后、在别的业务模块里用角色做权限判断,那是权限系统的职责,不是登录状态机的职责。一个状态机只应该建模"它自己负责的那部分生命周期",不要把不相关的业务维度也塞进状态定义里。

第三个问题:同样不需要拆分。"因失败次数被系统自动锁定"和"被管理员手动封禁"在**转移规则**上是否有区别?如果解锁方式不同(自动锁定可以"到期自动解锁",管理员封禁只能"人工解封",到期不会自动解锁),那么它们的转移规则确实不同,值得考虑拆成 `LOCKED_AUTO`(可自动解锁)和 `LOCKED_BY_ADMIN`(只能人工解锁)两个状态,而不是共用一个 `LOCKED` 状态再靠一个 `locked_reason` 字段在解锁逻辑里做 if 判断——如果一个数据字段会导致"同一状态下,某些转移对这条数据的某些取值合法、对另一些取值不合法",这通常是"该拆状态却硬塞进数据"的信号,和第一个陷阱刚好相反,提醒你数据和状态的界限要双向检查。本课为了聚焦核心流程,先只建模最常见的"失败次数触发的自动锁定"(可自动到期解锁),把这个拆分留给你在Step 9自己判断。

**确定的状态清单:**

| 状态 | 说明 | 互斥性 | 持续性 |
|------|------|--------|--------|
| `ANONYMOUS`(未登录) | 初始状态,或登出/锁定解除后回到的状态,携带 `failure_count` | 与其余状态互斥 | 直到登录成功或达到失败阈值 |
| `AUTHENTICATED`(已登录) | 登录成功,持有有效会话 | 互斥 | 直到主动登出或会话过期(本课不建模会话过期,留作练习) |
| `LOCKED`(已锁定) | 失败次数达到阈值,拒绝一切登录尝试,携带 `locked_until` | 互斥 | 直到锁定到期或管理员解锁 |

## Step 3: 寻找事件

引导性问题:

- "登录尝试"本身是事件,还是"登录成功"和"登录失败"是两个不同的事件?
- 账户在 `LOCKED` 状态下再次尝试登录,系统该怎么反应,是不是应该"悄悄地再给一次机会"?
- "失败次数+1"这个动作,是转移的一部分,还是它本身也算一次转移?

**分析过程:**

先明确动作、事件、非法输入三者:

1. **动作**:发送锁定通知邮件、写安全审计日志、重置 `failure_count`。这些是转移发生后的副作用。
2. **事件**:`LOGIN_SUCCESS`、`LOGIN_FAILURE`、`LOGOUT`、`LOCK_EXPIRE`(锁定到期,通常由定时任务或"下次访问时检查时间"触发)、`ADMIN_UNLOCK`。
3. **应拒绝的非法输入**:对 `LOCKED` 状态的账户调用登录接口——**这是本课要重点强调的地方**。

第一个引导问题:"登录尝试"不应该建模成一个模糊的事件,必须拆成 `LOGIN_SUCCESS` 和 `LOGIN_FAILURE` 两个独立事件,因为它们触发的转移结果完全相反(一个走向 `AUTHENTICATED`,一个可能走向"继续留在 `ANONYMOUS`"或"跳转到 `LOCKED`")。如果笼统地用一个 `LOGIN_ATTEMPT` 事件,状态机内部还要再判断一次"这次尝试到底是成功还是失败",这个判断逻辑事实上又变成了一个隐藏的、没有被显式建模的"事件",不如一开始就拆干净。

第二个引导问题,也是本课的安全重点:`LOCKED` 状态下收到 `LOGIN_SUCCESS` 或 `LOGIN_FAILURE`,系统绝对不能"悄悄放过"——即使这次密码是对的,也必须拒绝登录并返回"账户已锁定,请稍后再试",而不能因为"密码验证通过了"就顺便让用户登进去。这是安全类状态机和普通业务状态机相比,对"非法转移拒绝"要求更严格的地方:订单系统里非法转移主要是为了数据一致性,登录系统里非法转移的拒绝直接决定了"暴力破解攻击是否能被有效阻止"——如果实现时一不小心让 `LOCKED` 状态"顺便"处理了 `LOGIN_SUCCESS` 并放行,锁定机制就形同虚设。正确的做法是显式抛出异常或返回明确的"账户已锁定"错误,同时**不能透露**"其实密码是对的"这种信息(避免帮攻击者做验证),这是状态机拒绝逻辑和安全需求结合的一个实际例子。

第三个引导问题:"失败次数+1"不是一次独立的状态转移,它是 `LOGIN_FAILURE` 事件触发的转移中,**转移动作的一部分**(修改状态携带的数据),状态本身(`ANONYMOUS`)在计数没到阈值前并没有变化。只有当这次+1使计数达到阈值,才会同时发生"状态跳转到 `LOCKED`"这个真正的转移。这正是Step 1提到的"守卫条件":`LOGIN_FAILURE` 事件的转移目标 = `if 新失败次数 >= 阈值 then LOCKED else ANONYMOUS`。

**确定的事件清单:**

| 事件 | 说明 |
|------|------|
| `LOGIN_SUCCESS` | 用户名密码验证通过 |
| `LOGIN_FAILURE` | 用户名密码验证失败(转移目标依赖 `failure_count` 是否达到阈值) |
| `LOGOUT` | 用户主动登出 |
| `LOCK_EXPIRE` | 锁定时长到期 |
| `ADMIN_UNLOCK` | 管理员手动解锁 |

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| `ANONYMOUS` | `LOGIN_SUCCESS` | `AUTHENTICATED` | 重置 `failure_count=0`,创建会话,记录登录日志 |
| `ANONYMOUS`(`failure_count + 1 < threshold`) | `LOGIN_FAILURE` | `ANONYMOUS` | `failure_count += 1`,记录失败日志 |
| `ANONYMOUS`(`failure_count + 1 >= threshold`) | `LOGIN_FAILURE` | `LOCKED` | `failure_count += 1`,设置 `locked_until = now + lock_duration`,记录安全告警日志,发送锁定通知 |
| `AUTHENTICATED` | `LOGOUT` | `ANONYMOUS` | 销毁会话,重置 `failure_count=0` |
| `LOCKED` | `LOCK_EXPIRE` | `ANONYMOUS` | 重置 `failure_count=0`,清空 `locked_until` |
| `LOCKED` | `ADMIN_UNLOCK` | `ANONYMOUS` | 重置 `failure_count=0`,清空 `locked_until`,记录管理员操作日志 |

**非法转移处理方式(必须覆盖):**

- `LOCKED` 状态收到 `LOGIN_SUCCESS` 或 `LOGIN_FAILURE`:**拒绝**,返回"账户已锁定",且不透露密码是否正确;记录一次"锁定期间尝试登录"的安全日志(这本身是有价值的攻击线索,但不代表放行)。
- `AUTHENTICATED` 状态收到 `LOGIN_SUCCESS` / `LOGIN_FAILURE`:**拒绝**——已经登录的会话不应该再走登录流程,这通常意味着客户端状态和服务端不一致,应该报错而不是"重复登录一次"。
- `ANONYMOUS` 状态收到 `LOGOUT`:**拒绝**——没有登录,谈不上登出,直接报错比静默返回"成功"更能帮助排查客户端bug。
- `ANONYMOUS` / `AUTHENTICATED` 状态收到 `LOCK_EXPIRE` / `ADMIN_UNLOCK`:**拒绝**——账户根本没被锁定,不存在"解锁"这件事。

统一用 `InvalidTransitionError` 表达,内部日志记录"当前状态+被拒绝的事件",对外API统一转换成不泄露内部细节的错误提示。

## Step 6: Python实现

### v1: Enum + match-case

用 `Enum` 表示三个状态,`Account` 类里的 `login()` 方法内部先判断 `self.state`,再在 `ANONYMOUS` 分支里根据 `failure_count` 判断是否触发锁定。这一版能直接体现"守卫条件"怎么用简单的 if 表达,但缺点和订单v1一样:转移规则和阈值判断混在方法体里,不方便审计。

### v2: Transition Table + 显式的非法转移异常

把"结构性转移"(哪个状态收哪个事件合法)放进表里,把"依赖数据的守卫条件"(失败次数是否达到阈值)放进处理函数内部。这一版展示的重点是:**转移表不需要、也不应该把所有业务条件都塞进 `(state, event)` 的key里**——`(ANONYMOUS, LOGIN_FAILURE)` 始终只有一行,行为分支交给处理函数内部读状态数据决定,这样表的规模不会因为阈值大小而变化。同时展示对 `LOCKED` 状态下任何登录事件的显式拒绝。

### v3: State Pattern

`LockedHandler` 类里可以清楚地把"拒绝登录但记录攻击线索"这个安全逻辑单独封装,不会和 `AnonymousHandler` 的"计数+判断阈值"逻辑混在一起,每个状态的安全考量都局部化在自己的类里,便于安全审计时只读这一个类。

### v4: 通用FSM框架

复用Lesson 01的 `GenericFSM`,验证同一个框架能不能既支撑订单场景又支撑登录场景——这正是"什么时候值得抽框架"的实证:如果连着两三个不同业务场景都能套进同一个 `State/Event/Transition/FSM` 抽象里而不用改框架代码本身,说明抽象是合适的。

完整代码见 `02_login_flow.py`。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**

登录相关的判断通常散落在:登录接口("检查是否被锁定""检查密码""失败计数")、定时任务("扫描过期锁定并解锁")、管理员后台("解锁账户")。这几处如果各自维护一套"什么时候算锁定"的判断逻辑,极容易出现不一致——比如管理员解锁时忘了重置 `failure_count`,导致解锁后立刻又因为"历史失败次数"被误判为再次锁定。集中到一张转移表和统一的状态跳转函数后,"解锁"这个动作只有一处定义,不会有多处实现各自遗漏字段重置的问题。

**什么情况下FSM反而是负担?**

如果系统的登录策略非常简单(不限制失败次数,只有"登录/登出"两个状态),那么这里描述的整套阈值判断、锁定超时、管理员解锁机制根本不存在,当然也不需要FSM,一个 `is_logged_in: bool` 字段就够。

**什么时候不应该使用FSM?**

当"锁定策略"本身变得高度动态(比如结合IP信誉、设备指纹、行为评分等风控系统,是否锁定由一个实时计算的风险分数决定,而不是简单的"连续失败N次"),这时候真正需要的是一个风控规则引擎/评分系统,状态机只应该保留"最终决定"落地后的两三个粗粒度状态(正常/锁定),不要试图把风控评分逻辑本身也塞进状态机的转移条件里。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 计数器、金额、名单之类会持续增长/变化的字段,是数据不是状态
✓ 但"数据是否达到某个阈值"可以作为转移的守卫条件
✓ 安全类状态机的"拒绝"必须显式且不泄露多余信息
✓ 历史依赖不止"上一个状态是谁",也可以是"累积发生了几次"
→ 应该考虑扩展状态机(状态 + 数据 + 守卫条件)
```

## Step 9: 迁移训练题

1. **验证码发送限流**:一个手机号每天最多发送5次验证码,每次发送后60秒内不能再次发送("发送冷却"),超过5次后当天不能再发,第二天0点重置。这个场景该用FSM建模吗?
2. **API密钥的生命周期**:一个API密钥创建后是"生效中",可以被开发者"手动吊销",到期后自动变成"已过期",过期或吊销的密钥不能再被用来调用API,但可以被开发者查看历史调用记录。是否需要引入FSM,还是简单的时间戳比较就够了?
3. **多因素认证(MFA)登录流程**:用户输入正确密码后,如果开启了MFA,还需要输入一次性验证码才能算登录成功;验证码有5分钟有效期,输入错误3次后本次登录尝试失效需要重新输入密码。这个流程比本课的单因素登录复杂在哪里?是否需要新增状态,还是可以复用本课的 `ANONYMOUS/AUTHENTICATED/LOCKED` 加一点数据字段就够?

## 今天真正学会的一句话

**"依赖历史"不止意味着"记住上一个状态",也可能意味着"记住某类事件累积发生了几次"——这种累积计数应该作为状态携带的数据、配合"守卫条件"参与转移判断,而不是被展开成一堆随计数值线性增长的新状态。**
