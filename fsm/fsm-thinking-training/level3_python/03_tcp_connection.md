# Lesson 03: TCP连接状态(应用层视角) (Level 3 - Python工程场景)

> 本课的视角限定:我们站在"用 `socket.connect()` / `socket.send()` / `socket.close()` 的应用开发者"这一侧,不是TCP协议本身的实现者。协议内部真实的11状态机(`SYN_SENT`、`ESTABLISHED`、`FIN_WAIT_1`……)是Level 4要讲的内容,本课刻意只建模"应用代码能观察到、需要对之做出反应的几个粗粒度阶段"。这个"视角收窄"本身就是一次重要的识别训练:同一个"TCP连接"这个东西,在不同抽象层上应该建出完全不同粒度的状态机。

## Step 1: 是否适合FSM

**是否存在有限状态?**

从应用代码的角度看,一次连接只会处于:还没开始连(`CLOSED`)、正在连接中(`CONNECTING`)、已连接可以收发数据(`CONNECTED`)、正在关闭中(`CLOSING`)。四个阶段,互斥,有限。

**是否依赖历史状态?**

依赖,但比订单课简单一些:主要体现在"`CLOSING` 状态是怎么进来的"会影响后续该做什么收尾动作(是本地主动 `close()` 触发的,还是对端先断开、我方被动进入关闭流程),这类似订单退款课里"记住退款前的状态"。但这里的历史依赖不涉及"回退到之前的状态"——`CLOSING` 之后永远走向 `CLOSED`,不会因为历史不同就走向不同的目标状态,只是清理动作(要不要再多读一次剩余数据、要不要通知上层"对端主动断开"这类事件)不同。

**是否由事件驱动?**

是。应用层能感知到的转移几乎全部来自底层socket API的返回结果或回调:`connect()` 调用完成(成功/失败)、`recv()` 返回0字节(对端关闭)、应用自己调用 `close()`。这些都是离散事件,不是连续变化的量。

**是否同一个事件在不同状态下行为不同?**

是。最典型的例子是"尝试发送数据"这个动作:在 `CONNECTED` 状态下是合法操作;在 `CLOSED`、`CONNECTING`、`CLOSING` 状态下都必须被拒绝,但拒绝的原因和该给调用者的报错信息是不同的("还没连接" vs "还在连接中,请等待" vs "连接正在关闭,不能再发送新数据")。同一个"想发数据"的意图,在不同状态下必须被翻译成不同的错误反馈,这正是应用层需要显式建模状态的原因——直接调用底层 `send()` 很多情况下不会立刻报错,而是会产生更难排查的异步错误或数据丢失。

**是否存在明确状态切换?**

存在。而且这几个切换点,正是应用代码里最容易漏处理的地方:很多bug报告"网络异常时程序卡死/崩溰",根源往往就是没有正确处理 `CONNECTING` 失败或 `CONNECTED -> CLOSING` 这个转移(比如对端主动断开后,应用代码还在傻傻地往一个已经半开的连接写数据)。

**结论:**

```
适合FSM: ★★★★☆
```

原因:应用层视角下的连接状态清晰、互斥、事件驱动,且同一操作(发送数据)在不同状态下必须有不同的、明确的拒绝反馈,这是FSM的强适用信号。打四星(不是五星)的原因是:这个状态机相比订单/登录场景要"轻"一些——大部分应用代码不会自己手写这个状态机,而是直接使用更高层的库(比如 `asyncio` 的 `Protocol`/`Transport`,或者一个成熟的HTTP客户端库)替你管理这几个状态,自己重新实现的场景相对有限(比如你在写一个底层网络库、连接池、或者需要精细控制重连逻辑的场景)。识别"这个FSM是否值得自己实现,还是应该找现成的抽象来复用"也是一种工程判断,不完全是"适合不适合用FSM思维"本身的问题——思维上肯定适合,只是"要不要自己造轮子"要另外权衡。

## Step 2: 发现状态

引导性问题:

- "已发送了多少字节""接收缓冲区里还有多少数据"是状态吗?
- "连接超时"算不算一个独立状态?
- 服务端的"监听中"(`listening`)和客户端这里讨论的连接状态,是同一个状态机吗?

**思考过程:**

第一个问题:"已发送字节数""接收缓冲区数据"是数据,不是状态。它们的变化不会导致"能不能调用send()/recv()"这类操作合法性发生改变——只要处于 `CONNECTED`,不管缓冲区里有多少字节,发送和接收操作在"状态机层面"都是合法的(至于操作系统层面的流控、缓冲区满了要阻塞,那是传输层内部的机制,不影响我们这个应用层粗粒度状态机的合法性判断)。

第二个问题:"连接超时"不是一个独立状态,而是导致 `CONNECTING -> CLOSED` 这个转移的**触发原因之一**(和"对端主动拒绝连接"、"网络不可达"一样,都是"连接失败"这个转移背后的具体原因)。是否要把"超时"和"被拒绝"细分成不同的目标状态?通常不需要——应用代码在这两种情况下要做的下一步动作往往是一样的(记录错误、可能重试、通知上层),没有必要为了区分失败原因而拆出新状态,失败原因作为数据(比如一个 `error: OSError | None` 字段)记录下来即可,这和订单课"取消原因是数据不是状态"是同一个道理。

第三个问题:不是同一个状态机。"监听中的服务端socket"和"一条具体的连接"在生命周期语义上完全不同——监听socket本身没有"已连接/已关闭"的概念,它只是不断地产生新的、已经处于 `CONNECTED` 状态的连接对象(每次 `accept()` 返回的新socket,从应用层看,直接就是 `CONNECTED` 状态,不会经历 `CONNECTING`,因为三次握手已经在内核里完成了)。这提示一个重要原则:**同一个"连接"概念,客户端视角和服务端视角的状态机可能不完全对称**,建模时要问清楚"我在为哪一端的哪个对象建模",不要想着用一个状态机同时描述监听socket和已连接socket——它们的生命周期起点不一样。本课只建模客户端视角(或者说"一条已经存在的连接对象"的视角,服务端 `accept()` 出来的连接对象也适用,只是起点直接是 `CONNECTED`)。

**确定的状态清单:**

| 状态 | 说明 | 互斥性 | 持续性 |
|------|------|--------|--------|
| `CLOSED`(已关闭) | 初始状态,或连接结束后的终态 | 互斥 | 直到调用 `connect()` |
| `CONNECTING`(连接中) | 已发起连接请求,等待底层握手完成 | 互斥 | 直到握手成功或失败 |
| `CONNECTED`(已连接) | 可以正常发送/接收数据 | 互斥 | 直到本地关闭或对端关闭 |
| `CLOSING`(关闭中) | 关闭流程已开始(本地或对端触发),等待收尾完成 | 互斥 | 直到底层资源完全释放 |

## Step 3: 寻找事件

引导性问题:

- "调用 `send()`"本身会不会触发状态转移?
- "对端主动关闭连接"和"本地主动关闭连接",是应该建模成同一个事件还是两个不同的事件?
- 在 `CONNECTING` 或 `CLOSING` 期间调用 `send()`,系统该怎么反应?

**分析过程:**

1. **动作**:发送数据、接收数据(在 `CONNECTED` 状态下合法执行,不改变状态本身)、记录连接日志、触发重连逻辑。
2. **事件**:发起连接(`CONNECT`)、底层握手成功(`CONNECT_OK`)、底层握手失败(`CONNECT_FAILED`)、本地主动关闭(`CLOSE`)、检测到对端关闭(`PEER_CLOSED`,通常表现为 `recv()` 返回0字节或抛出连接重置异常)、关闭流程收尾完成(`CLOSE_DONE`)。
3. **应拒绝的非法输入**:在 `CLOSED`/`CONNECTING`/`CLOSING` 状态下调用"发送数据"。

第一个引导问题:"调用 `send()`"本身**不是**一个会触发状态转移的事件,它是一个"动作",前提是当前状态必须是 `CONNECTED`——这和"取消"在订单课里的角色类似:操作本身不改变阶段,但操作的合法性完全取决于当前阶段。

第二个引导问题:必须建模成两个不同事件(`CLOSE` vs `PEER_CLOSED`),原因和退款课的"取消 vs 退款申请"类似——虽然它们最终都走向 `CLOSING`,但触发来源不同,导致后续该执行的收尾动作不同:本地主动 `CLOSE` 时,应用通常还想先把发送缓冲区里剩下的数据发完(优雅关闭,类似TCP的"半关闭");被动收到 `PEER_CLOSED` 时,应用通常需要判断"我这边是否还有数据要发",如果对端已经不会再收数据了,继续发送是没有意义的,应该尽快转入清理。把这两种情况混在一个事件里,会让"到底该不该继续发送剩余数据"这个判断逻辑变得含糊。

第三个引导问题(本课重点):必须明确拒绝,而且给调用者的报错信息要能区分原因,不能笼统一句"发送失败"——`CLOSED` 状态下发送应该报"连接尚未建立";`CONNECTING` 状态下发送应该报"连接正在建立中,请等待完成或使用异步回调";`CLOSING` 状态下发送应该报"连接正在关闭,不能再发送新数据"。这三种错误对调用者来说,该采取的修复动作完全不同(第一种是代码逻辑错误——用之前没连;第二种可能只是时序问题,加个等待或回调即可;第三种说明连接生命周期已经到了末尾,重新连接才是正确做法),笼统地抛一个 `ConnectionError` 会让调用方很难写出正确的容错逻辑。

**确定的事件清单:**

| 事件 | 说明 |
|------|------|
| `CONNECT` | 应用发起连接 |
| `CONNECT_OK` | 底层握手成功 |
| `CONNECT_FAILED` | 底层握手失败(超时/拒绝/网络不可达,原因作为数据记录) |
| `CLOSE` | 应用主动关闭连接 |
| `PEER_CLOSED` | 检测到对端关闭(recv返回空/连接被重置) |
| `CLOSE_DONE` | 关闭收尾完成,底层资源已释放 |

## Step 4: 状态转移表

| Current State | Event | Next State | Action |
|---|---|---|---|
| `CLOSED` | `CONNECT` | `CONNECTING` | 发起底层 `connect()`,记录开始时间 |
| `CONNECTING` | `CONNECT_OK` | `CONNECTED` | 记录连接建立时间,通知上层"已就绪" |
| `CONNECTING` | `CONNECT_FAILED` | `CLOSED` | 记录错误原因,可选择触发重连逻辑 |
| `CONNECTED` | `CLOSE` | `CLOSING` | 停止接受新的发送请求,尝试flush已有缓冲区 |
| `CONNECTED` | `PEER_CLOSED` | `CLOSING` | 通知上层"对端已关闭",停止发送新数据 |
| `CLOSING` | `CLOSE_DONE` | `CLOSED` | 释放底层socket资源,记录连接结束时间 |

**非法转移处理方式(必须覆盖):**

- 在 `CLOSED` / `CONNECTING` / `CLOSING` 状态下尝试"发送数据":拒绝,分别返回"未连接" / "连接建立中" / "连接关闭中"三种不同的明确错误,不能统一成一句模糊的"发送失败"。
- 在 `CONNECTING` / `CONNECTED` / `CLOSING` 状态下再次收到 `CONNECT` 事件:拒绝——不允许在一条连接对象还没完全关闭前重新发起连接,应用如果想重连,必须先走完 `CLOSING -> CLOSED`,再创建新的连接尝试(或者显式定义一个独立的"重连"状态机包装这条状态机,那是更高层的关注点,不属于本课范围)。
- `CLOSED` 状态收到 `CONNECT_OK` / `CONNECT_FAILED` / `PEER_CLOSED` / `CLOSE_DONE`:拒绝——这些事件只应该在特定的中间状态下出现,如果 `CLOSED` 状态收到了它们,通常意味着底层实现有bug(比如一个旧连接的回调在对象已经被重置后才迟到触发),必须报错而不是静默忽略,否则这种"迟到事件"可能污染一条全新的连接。

## Step 6: Python实现

### v1: Enum + match-case

用 `Enum` 表示四个状态,一个 `TcpLikeConnection` 类里的方法(`connect()`、`on_connect_result()`、`send()`、`close()`、`on_peer_closed()`、`on_close_done()`)分别用 `match` 判断当前状态。这一版能直观展示"同一个 `send()` 方法,在不同状态下要给出不同的错误信息"——三个不同的 `raise` 分支写在同一个方法里,读起来一目了然,但转移规则本身仍然分散在各方法中。

### v2: Transition Table

把"结构性转移"整理成表,`send()` 这种"只读状态、不改变状态"的操作依然保留为独立方法(因为它不是一次转移,把它塞进转移表里会让表的语义变得混乱——转移表应该只回答"事件如何驱动状态变化",不该回答"当前状态下哪些非转移性操作是合法的",后者更适合单独的一个"合法操作检查"函数)。这一版展示了一个重要边界:**转移表不是万能容器,不要把所有"状态相关的合法性检查"都塞进转移表**,只有真正的状态转移事件才属于这张表。

### v3: State Pattern

每个状态类里实现"这个状态下 `send()` 应该给出的具体错误信息",把三种不同的错误提示逻辑局部化到各自的状态类中,新增一个状态时,提示信息写在哪里一目了然。

### v4: 通用FSM框架

复用前两课的 `GenericFSM` 思路,展示同一个抽象在第三个不同领域(网络连接)下依然适用,进一步验证这个抽象的通用性。

完整代码见 `03_tcp_connection.py`。

## Step 7: 复杂度分析

**为什么FSM比if-else更好?**

网络编程里最常见的一类bug是"连接状态和实际处理逻辑不同步"——比如接收数据的回调函数里没检查"连接是不是已经在关闭中了",对端已经断开却还在尝试写数据,导致抛出难以理解的底层异常,或者更糟糕的,静默丢失最后一批数据。把状态检查集中到状态机层,所有想要"发送数据"的代码路径都必须先通过统一的状态校验,不会出现某个新加的功能模块忘了检查连接状态的情况。

**什么情况下FSM反而是负担?**

如果你的应用从来不直接操作socket,而是通过一个成熟的高层库(比如HTTP客户端库、消息队列SDK)使用网络连接,这些库内部已经处理好了连接状态管理,应用层完全不需要重新实现这套状态机——这也是为什么Step 1只打四星:这个FSM"该不该用"在思维上是明确的,但"该不该自己写"要看你所在的抽象层。

**什么时候不应该使用FSM?**

当你需要的只是"连没连上"这一个布尔判断,且不关心中间过程(比如一个简单的健康检查脚本,只在乎最终 `connect()` 是否在超时前成功),这时候一个简单的 try/except + 超时参数就够了,引入完整的状态机是不必要的。

## Step 8: FSM思维总结

```
==========
FSM识别口诀
==========
✓ 同一个操作(如send)在不同状态下必须给出不同的、明确的拒绝理由
✓ 转移由底层事件驱动(握手结果、对端关闭),不是应用主动轮询出来的
✓ "谁触发了关闭"决定了收尾动作,但不决定最终状态(都走向CLOSED)
✓ 转移表只放"真正的转移",非转移性的合法性检查不要混进表里
→ 应该考虑FSM(但同时要判断这一层由谁负责实现)
```

## Step 9: 迁移训练题

1. **数据库连接池中的单条连接**:一条连接在池子里可能处于"空闲可用"、"被某个请求借用中"、"正在做健康检查(定期PING)"、"已失效等待被剔除"这几种情况,借用超时要被强制归还,健康检查失败要被标记失效。这个场景该用FSM建模吗?
2. **WebSocket连接(区别于普通HTTP请求)**:一个WebSocket连接建立后可以长时间保持双向通信,期间可能收到"心跳ping/pong"、"业务消息"、"对端主动发起关闭握手(close frame)"、"网络中断"。这个场景相比本课的普通TCP连接视角,复杂在哪里?是否需要新增状态?
3. **消息队列消费者的连接与订阅**:一个消费者先要"建立到MQ broker的连接",连接建立后还要"订阅某个topic"才能开始收消息,连接断开后需要"自动重连并重新订阅"。这里出现了两层生命周期(连接 + 订阅),应该建一个状态机还是两个独立但互相关联的状态机?

## 今天真正学会的一句话

**同一个"连接"概念,在不同的抽象层次(应用层粗粒度视角 vs 协议内部实现)上,应该建出完全不同粒度的状态机——建模前先问清楚"我站在哪一层、只需要对哪些事件做出反应",而不是想着做一个大而全的状态机同时服务所有层次。**
