# 第 13a 课：五个代表例（复合状态）

主例「播放器 `ACTIVE` 盒子」的完整实现在 `code/`。其余四例只建立「共享退出应收进父框」的直觉。不要在本课例子里画历史、正交或伪状态。

---

## 例 1：播放器活动盒子（主例）

**问题**：第 07 课三个活动叶子各自画 `STOP`。再加 Seek、分档重试，箭按叶子数复制。

**状态图**：见 `LESSON.md` 的嵌套图。扁平爆炸图只对照，不实现。

**状态表**：叶子仍是 `STOPPED` / `CONNECTING` / `PLAYING` / `BUFFERING`；`STOP` 写成「`ACTIVE` 的任一子状态」。

**实现**：`code/c/player_hsm.c`、`code/cpp/player_hsm.cpp`、`code/python/player_hsm.py`。

**复杂度**：4 个叶子 + 1 个盒子谓词；`STOP` 从 3 行变成 1 行。

**工业用途**：流媒体播放器的启动与停止。

**常见缺陷**：`current = ACTIVE` 而不进入子叶子；或 `STOP` 仍抄三遍。

**重构**：重试次数保持为数据，不要做成 `ConnectingRetry1`。进入 / 退出动作留给 13b。

## 例 2：第 12 课 Wi-Fi 的「已连接」盒子

**问题**：第 12 课禁止把省电画成与 `CONNECTED` 并列的顶层状态。扁平六状态没有地方干净地放下「已关联但射频关了」。

教学只画盒子，不实现省电：

```
+---------------------------+
| CONNECTED（复合）         |
|   ONLINE                  |
|   （省电叶子留给后面）    |
+---------------------------+
        |
        | LOST / 用户断开
        v
   DISCONNECTED
```

`LOST` 应画在 `CONNECTED` 框上：无论里面将来是在线还是睡觉，丢链路都离开整段会话。

**复杂度**：本课 0 行新代码；图上 +1 个盒子。

**工业用途**：典型 Wi-Fi 请求端「已关联」超状态。

**常见缺陷**：`CONNECTED_SLEEP` 做成顶层兄弟，唤醒后还去重新关联。

**重构**：13e 才会把「播放」和「无线质量」做成同一盒子里的两列。现在只承认 `CONNECTED` 是盒子。

## 例 3：教学 TCP 的「已建立」盒子

**问题**：第 08 课把 ESTABLISHED、FIN_WAIT、CLOSE_WAIT 摊在一层。许多实现把「连接还活着、只是在关」收进一个更大的局面，RST 画在父框上。

```
+----------------------+
| LIVE（复合，教学）   |
|   ESTABLISHED        |
|   FIN_WAIT_1         |
|   CLOSE_WAIT         |
+----------------------+
         |
         | RST
         v
      CLOSED
```

本例 **不实现 TCP**。你只要认出：RST 对所有「还活着」的子局面是同一条出路，不应按子状态复制。

**复杂度（若真做）**：叶子数不变，公共复位少抄 N-1 次。

**工业用途**：传输层连接拆除与复位。

**常见缺陷**：每个子状态一份 `abort()`，漏掉 CLOSE_WAIT。

**重构**：表驱动仍然可以用；盒子是图和谓词，不必先换引擎。

## 例 4：向导对话框的「步骤中」

**问题**：安装向导有许可、路径、复制三个步骤。取消键在每一步都出现。扁平机要画三支 `CANCEL`。

```
+------------------+
| WIZARD_ACTIVE    |
|   LICENSE        |
|   PATH           |
|   COPY           |
+------------------+
         |
         | CANCEL
         v
      IDLE
```

下一步 / 上一步仍画在叶子之间，因为它们不是整段向导的共同行为。

**复杂度**：3 个叶子 + 1 个盒子。

**工业用途**：GUI 向导、配置助手。

**常见缺陷**：取消时只退出当前步骤控件，父窗口还留着，用户以为取消失败。

**重构**：13b 会把「关掉向导窗口」绑在离开 `WIZARD_ACTIVE` 上。本课先把箭收拢。

## 例 5：协议的「出错就拆会话」超状态

**问题**：会话里有握手、传输、收尾。任何一步收到 `FATAL` 都应拆掉会话。扁平表为每个叶子抄一行 `FATAL`。

| Current State | Event | Guard | Action | Next State |
|---------------|-------|-------|--------|------------|
| SESSION 的任一子状态 | FATAL | — | tear down | IDLE |
| HANDSHAKE | OK | — | — | TRANSFER |
| TRANSFER | FIN | — | — | CLOSING |

**复杂度**：公共致命错误 1 行，与播放器的 `STOP` 同构。

**工业用途**：应用层会话、VPN 控制通道。

**常见缺陷**：只在 `TRANSFER` 处理 `FATAL`，握手阶段的致命错误把进程卡在半开。

**重构**：不要为每种致命原因各做一个终点状态（第 12 课已经反对过）。父框指向同一个 `IDLE`。
